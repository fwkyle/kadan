# 제동·판단·복구

## 등급

| 등급 | 뜻 | 행동 |
|---|---|---|
| GREEN | 확인한 작업에 이상 없음, PID 일치 | 계속하고 침묵 |
| AMBER | 작업 정체·근거 부족·반복 검증 위험 | 영향받는 작업과 근거를 확인하고 범위 조정 |
| RED | 실제 세션 부재·계속되는 오입력·폭주로 피해 진행 | 정확한 피해 실행 하나 제동 |

watch의 AMBER·RED는 작업 이상을 확인할 입력 신호다. 화면·PID·실제 작업 영향을 보고
판단하며, 경고가 사라졌다는 사실만으로 원인이 제거됐다고 가정하지 않는다. 자원 수치는
[자원 확인](../../kadan-conductor/references/operating-contract.md#자원-확인) 기준에 따라 발령 규모를 판단할 참고값이며, 자원 색상만으로 제동하거나 상위 AI를 깨우지 않는다.

## 감독 질문에 답하기 (2026-09-05 사용자 결정)

슈퍼감독은 일반감독이 근거를 대조해도 못 푼 질문에 답한다. 승인 범위 안의 방법 선택·
진단·복구는 일반감독이 결정하며, 슈퍼는 우선순위·판 간 자원 충돌·승인 범위를 조정한다.
답에는 다음 같은 유형을 일반감독이 처리할 공통 기준과 실제 예외를 남긴다. 구체적인
위임은 [일반감독의 결정 범위](../../kadan-conductor/references/operating-contract.md#일반감독의-결정-범위)를 따른다.

`kadan send <판>-감독 "답 <판> <카드>: 결정 / 이유 / 다음 행동"`

- 감독 질문을 사용자에게 올리는 것은
  `../../kadan-conductor/references/tiki-taka.md`의 "감독의 질문 사다리" 5) 목록과,
  감독이 우편으로 올린 제품 방향·취향 질문 중 기존 결정·조사로 못 정하는 것뿐이다.
  올릴 때는 `decision request`([중앙 결정 경로](../../kadan-conductor/references/central-cards.md#사용자-결정-요청-전용-경로))를
  쓰고 감독에게도 "사용자에게 올림"이라고 한 줄 보낸다. 감독의 질문은 우편으로만 온다.
  카드 메모(`card note --kind question`)는 기록이라 알림이 없으니 그것을 질문으로 기다리지 않는다.
- 답 없이 방치하지 않는다. 질문 받은 주기 안에 답 또는 "보류 이유"를 보낸다.
- 원장에는 이 우편이 `send` 줄로 남으므로 `wall` 우편함에서 `by=슈퍼감독`으로 보인다.
- watch의 작업 이상·전달실패 상신은 별개이며 기존 규칙을 그대로 따른다.

## 반복 검증 판정 (AMBER의 "반복 검증 위험"을 재는 표, 2026-09-02 이식)

같은 전체 테스트를 여러 역할이 반복하면 컴퓨터가 느려진다. 검수자·작업자가 전체
테스트를 다시 돌리려 할 때 아래 5항목이 작업자 결과 파일의 증거와 **모두 같으면**
재사용 가능한 증거다. 새 발령을 보류하고 focused 검증으로 줄이라고 판 감독에게 지시한다.

| # | 같아야 하는 것 |
|---|---|
| 1 | 기준 commit SHA 또는 미커밋 변경 지문 |
| 2 | 테스트에 영향을 주는 설정·환경 |
| 3 | 실행 명령과 테스트 선택 범위 |
| 4 | 성공 개수·실패 개수·종료 코드가 기록돼 있음 |
| 5 | 결과가 나온 뒤 관련 파일이 바뀌지 않았다는 확인 |

전체 재실행을 허용하는 경우는 다섯뿐이다: (1) 관련 입력이 바뀜 (2) 기존 실행이 0개
선택·timeout·부분 실행·환경 오류 (3) focused 결과가 기존 전체 결과와 충돌
(4) 릴리즈·마이그레이션·보안 관문 (5) 사용자가 명시. 작업자·검수자가 지켜야 할 같은
규칙의 원문은 `../../kadan-conductor/references/tiki-taka.md` 검수 규칙에 있다.

## 무진행 판정 순서 (2026-09-02 이식)

역할이 멈춘 것처럼 보이면 원인을 **이 순서로** 좁힌다. 순서를 건너뛰면 오판한다
(2026-08-06 429를 "정상 대기"로 봐서 다섯 시간 정체, 2026-08-05 정상 장고를 정체로 오탐).

1. **화면 하단 오류 원문부터 읽는다.** 있으면 아래 표로 즉시 분류한다. 오류 원문은
   잔상이 아니라 그 턴이 죽었다는 증거다. 제목의 스피너는 증거가 아니다.
2. 오류가 없으면 **원장의 미완료 카드 수·마지막 활동 시각**과 화면 지문을 비교한다.
   화면은 도는데 카드가 제자리면 논리 교착 후보다.
3. 둘 다 아니면 **정상 장고**다. 고강도 모델은 도구 실행 없이 수 분간 생각만 한다.
   개입하지 않는다. 섣부른 재주입은 작업을 되돌린다.

| 화면 신호 | 뜻 | 처방 | 하면 안 되는 것 |
|---|---|---|---|
| `429`, `rate limit`, `exceeded retry limit` | 호출 제한 후보 — 에이전트 실행기와 작업 중 외부 API를 구분 | 일반감독이 해당 호출만 보류·읽기 진단, 새 근거의 제한된 복구는 공통 기준 적용 | 원인 단정, 같은 근거 재호출, 새 ID 순회, 무단 계정·비용 변경 |
| `502`, `unreachable`, `ENOTFOUND`, `stream error` | 끊김 | 재개 — SKILL.md "끊김을 만나면" 순서 | 새 카드 생성, 무한 재개 |
| `can't be shown`, `cybersecurity`, `Trusted Access` | 안전 필터 차단 — 품질 실패가 아니라 가용성 사건 | 카드 문구에서 공격·위조·적대 어휘를 빼고 재발령. 그래도 막히면 다른 실행기로 교체를 올림 | 카드 failed 처리, 같은 문구 재시도 |
| `oauth/token`, `Reconnecting 5/5` | 인증·세션 실패 | 하네스 장애와 실행기 장애를 나눠 확인한 뒤 교체를 올림 | 같은 세션 무한 재연결 대기 |
| `No API key`, 모델 이름 오류 | 설정 오류 | 즉시 중단, 정확한 이름으로 다시 세우도록 올림 | 재시도 반복 |
| 폴더 신뢰·명령 허용 창 뒤로 출력 정지 | 사람 승인 대기 | 승인 창임을 실측 → 그 판·그 CLI에 사전 신뢰 설정 → 재기동. `dispatch-wait.md` 2단계대로 자동 통과 금지 | 무진행으로 오판, 사람이 대신 눌러주고 원인 기록 안 함 |
| 오류 없음, 화면은 도는데 카드가 제자리 | 논리 교착 | 판 감독에게 무엇을 기다리는지 한 번 묻고 답을 원장과 대조 | 화면 활동만 보고 정상 판정 |
| 오류 없음, 도구 실행 줄 없음, 카드 진행 정상 | 정상 장고 | 개입하지 않는다 | 재주입, 정체 상신 |

### 끊김 재개 순서 (SKILL.md에서 옮김, card-42)

1. `kadan read <역할> --lines 30`으로 어디까지 했는지 읽고, `kadan status`·`kadan log`도
   다시 재어 같은 일을 중복 발령하지 않는다.
2. 인터넷·DNS·로컬 프록시가 정상인지 읽기 전용으로 확인한다.

```bash
ping -c 1 1.1.1.1
nslookup chatgpt.com
lsof -nP -iTCP:10101 -sTCP:LISTEN
```

3. 하나라도 정상 확인이 안 되면 해당 접점의 근거를 남긴다. 일반감독이 승인 안에서 해결할 수
   없는 공유 서비스·권한 문제만 슈퍼에게 상담한다. 모두 정상이고 같은 실행의 실제 처리 중단을
   확인했으면 일반감독이 새 카드 없이 같은 역할에 이어서 하도록 지시한다.
4. 매번 재개 전에 화면과 원장을 읽고, 같은 지점에서 3회 반복되면 해당 재개를 멈추고 슈퍼에게
   조정을 요청한다. 슈퍼도 자기 권한 밖 조치만 사용자에게 올린다.
   원본 서명 목록은 `src/watch.mjs`의 끊김 서명. 복사하지 않는다.

- 재개, 같은 모델의 소유 역할 교대, 다른 실행기·계정으로의 전환은 구분한다. 앞의 두 방법은
  위임된 범위에서 일반감독이 판단하며, 실행기·계정·모델·권한 전환은 기존 승인 밖이면 상신한다.
  복구 때문에 새 업무/실행 카드를 만들거나 원실패·미완료를 완료로 바꾸지 않는다.
- 판정 근거(오류 원문 일부)를 보고에 남긴다. "정체"라고만 쓰지 않는다.
- 사고 원문이 필요하면 관리자 개인 스킬 저장소의 사고표를 읽고 요약은 `scars.md`를 본다.
  여기로 복사하지 않는다.

## 정확한 하나만 제동

1. `kadan status`에서 대상 역할과 PID 일치를 확인한다.
2. `kadan read <역할> --lines 30`으로 오류·폭주 근거를 확인한다.
3. 피해가 진행 중이고 소유권이 분명할 때만 `kadan stop <역할>`을 실행한다.
4. 다른 역할, 판, 사용자 앱, worktree는 보존한다.
5. 근거·대상·영향·복구 조건을 즉시 사용자에게 보고한다.

`pkill`, 이름이 넓게 맞는 종료, 판 전체 종료는 금지한다. 소유권·PID가 모호하면
stop하지 않고 사용자 결정으로 올린다.

## RED 해제

1. 원인 실행이 멈췄고 PID 변경·새 폭주가 없는지 확인한다.
2. AMBER로 내려 focused 검증 하나만 재개한다. 새 무거운 발령은 금지한다.
3. 결과가 정상이고 자원 압박·오입력·프로세스 증식이 없으면 GREEN으로 내린다.
4. 같은 원인이 재발하면 RED로 돌아가며 같은 실행을 반복 발령하지 않는다.

## 판단 사다리

슈퍼감독이 스스로 정한다:

- GREEN·AMBER·RED와 단계 해제
- 정확한 과부하 역할 제동, 검증 범위 축소, 승인된 판의 안전한 재개
- 이미 합의된 비용·안전 범위 안의 역할 배치 조정

사용자에게 묻는다:

- 판 전체 중단·폐기, 목표·제품 방향 변경
- push·merge·배포·삭제·마이그레이션
- 프로젝트 충돌로 하나를 희생해야 하는 우선순위
- RED 재발 뒤 안전한 대안이 없음
- 소유권이 불명확해 다른 판이나 사용자 앱을 건드릴 가능성

질문이 필요해도 안전한 읽기 전용 조사와 다른 판의 정상 작업은 계속한다.
