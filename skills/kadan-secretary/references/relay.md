# 발송 절차 — 사용자의 말을 판에 전하는 법

아래 표의 `kadan`은 PATH에 없으면 `node <저장소>/src/cli.mjs`로 치환한다.

## 전달 종류

[맥락 우편과 실행 카드](../../kadan-conductor/references/operating-contract.md#맥락-우편과-실행-카드-2026-10-13-사용자-정정)가 기준이다.
새 업무 요청도 기본은 맥락 우편이다. 비서·슈퍼감독은 전달용 카드를 먼저 만들지 않고,
담당 일반감독이 설계·작업 분할·카드 작성·배정·작업자 발령을 맡는다.
기존 작업의 방향 정정·현황 질문도 일반 우편으로 전달하며, 수신 감독이 기존 카드의 최신 판단에 반영한다.

자동 첨부의 원본은 [공통](../../kadan-conductor/references/role-templates/common.md)과
[역할별 템플릿](../../../docs/role-instructions.md)이다. 역할 안내나 우편 수신이 실행 승인을 대신하지 않는다.

## 순서

1. **사용자의 맥락을 정리한다.** 문제·확인한 사실·원하는 결과·기존 승인 범위·금지선·관련 자료를 적는다.
   실행 카드나 구현 지시서를 대신 쓰지 않고, 설계·작업 분할은 담당 일반감독에게 맡긴다.
2. **받는 사람을 정한다.** 사용자가 감독을 지정했으면 그 감독에게 보낸다.
   지정이 없거나 확인할 수 없으면 슈퍼감독에게, 없으면 해당 판 감독에게 보낸다.
   `kadan tree`·`kadan status`로 기존 담당을 확인하고, 선택한 감독과 이유를 사용자에게 밝힌다.
3. **일반 우편으로 보낸다.**

```bash
KADAN_ROLE=비서 kadan mail <감독> "<문제·사실·원하는 결과·승인 범위·금지선·자료>. 담당 일반감독이 카드 작성과 발령을 맡아 주세요."
```

기존 업무·실행에 관한 우편이면 확인된 `--work`·`--execution` 주소를 연결한다.
`mail --execution`은 수신자의 배정 카드를 연결해도 발령으로 바뀌지 않는다.
기존 `send --execution`의 추론과 구분하며, 세부 조건은 위 공통 기준을 따른다.
주소가 없다는 이유로 전달용 카드를 만들지 않는다. `mail`은 `--task`를 거절하며, 일반 우편에 DONE 요구를 붙이지 않는다.

4. **CLI 전달 결과를 확인한다.** 정상 전달 뒤 같은 목적의 `read`를 반복하지 않는다.
   전달 불명확·오류·보고 불일치 등 추가 확인 조건은 [전달 후 확인 범위](../../kadan-conductor/references/dispatch-wait.md#전달-후-확인의-범위)를 따른다.
5. **사용자에게 보고한다.** 어느 감독에게 어떤 맥락을 전달했고 무엇까지 확인됐는지 짧게 말한다.
   전달 성공을 착수·완료로 보고하지 않는다.

## 직접 카드 작성·발령을 맡은 예외

사용자가 비서에게 직접 카드 작성을 맡겼을 때만 [카드 쓰기](../SKILL.md#명시적으로-카드-작성을-맡은-경우)와
[중앙 카드 절차](../../kadan-conductor/references/central-cards.md)를 적용한다.
작성만 맡았으면 등록한 원본 경로를 일반 우편으로 감독에게 넘긴다. 배정·발령까지 자동으로 맡은 것으로 보지 않는다.
발령까지 명시적으로 맡았을 때만 승인·배정과 필요한 `rally` 또는 조율 카드 조건을 갖춘 뒤 `dispatch --task`를 쓴다.
기존 수신자 제한을 지키며, 작업자·검수자에게 직접 보내지 않는다.
발령 지문에는 카드 경로와 DONE 마커 형식만 적고 완성된 마커 문자열은 넣지 않는다.

## 보내면 안 되는 경우

- 사용자가 시키지 않은 것 — 비서가 자기 판단으로 지시하는 순간 두 번째
  지휘자가 된다.
- 사용자가 지정한 감독도 슈퍼감독도 판 감독도 없으면 보내지 않는다. 먼저 슈퍼감독을
  세울지 사용자에게 묻는다. 작업자에게 우회 발송하지 않는다(07-23).
- 작업자·검수자에게 직접 보내는 것 — 2026-07-23 이중 개입 흉터. 반드시
  사용자가 지정한 감독이나 슈퍼감독·판 감독을 거친다.
- 받는 세션이 죽었거나 PID가 다른 경우 — send가 실패 닫힘으로 거절한다.
  재시도하지 말고 사용자에게 보고한다.
- 내용이 모호한 경우 — 자동 재시도·재전송 없이 되묻는다.
- 이미 같은 이상을 받은 역할에게 같은 내용을 또 보내는 것.
- 비서가 직접 해결할 수 있는 것처럼 보여도 구현·수정 지문 — "제가 해둘까요?"는
  비서의 말이 아니다. 알아내서 말씀드리는 데까지가 비서다.

## 원장에 남는 것

발송·세우기에 `KADAN_ROLE=비서`를 붙이므로 원장에 `by:"비서"`로 남는다(card-28).
비서 세션은 사용자와 대화하는 창이라 카단 세션이 아니다 — 그래서 신분은 환경
변수로 명시한다. 나중에 "누가 시켰어?"에 한 줄로 답할 수 있는 근거다.
