# 영상 제작 흐름 (video-flow)

## Why

영상은 대본·자산(음성·자막·썸네일)·편집·렌더·게시가 서로 다른 담당과 도구로 나뉘고, 결과물이 코드가 아니라 파일이다. 개발용 [표준 흐름](standard-flow.md)의 검수 계약(검수 자리·커밋 SHA·테스트)을 그대로 쓰면 검수자가 git 저장소가 아닌 곳에서 `slot acquire`를 시도하다 실패한다. 이 흐름은 같은 카드·묶음·DONE 규약 위에서 영상 결과물에 맞는 단계와 검수 기준을 정한다.

## 흐름 선택

- 사용자가 흐름을 지정하지 않으면 개발용 [표준 흐름](standard-flow.md)과 [티키타카](tiki-taka.md)를 쓴다.
- "영상 흐름", "영상 제작", "video-flow"처럼 이 흐름을 지정했을 때만 이 문서를 따른다.
- 코드는 흐름 문서를 읽지 않는다. 이 문서가 바꾸는 것은 단계표·카드 양식·합격 기준·검수 계약의 적용 범위이고, 카드 단계는 코드가 정한 네 가지(`implementation`·`fix`·`review`·`research`)에 매핑한다.

## 결과물의 이름

업무 카드에 **납품 형식**(해상도·길이·코덱·자막 포함 여부)과 **게시 대상**을 적는다. 최종 결과는 "완성본 파일 + 검수 기록"이며, 렌더가 끝났다는 사실이 게시 승인이 아니다.

## 단계와 카단 연결

업무 카드 한 장(`kadan work create`)에 목적·대상 시청자·길이·톤·납품 형식·승인 범위(사용 가능한 자산·음성·외부 도구·게시 권한)를 적는다. 아래 단계는 그 업무의 실행이다. 번호는 두 가지다. 업무 실행 등록(`work execute --round`)은 1부터 받고, 실행 카드의 묶음 번호(`--rally-round`)는 묶음마다 1부터(조사는 0) 센다. **묶음은 결과물 단위**다: 대본 묶음, 자산 레인마다 한 묶음, 편집 묶음. 한 묶음 안에서는 라운드마다 구현(또는 수정) 1장 + 검수 1장이 짝이어야 집계가 `unconfirmed`가 되지 않는다([표시 기준](../../../docs/review-flow.md)).

| 단계 | 하는 일 | 단계 값 | 업무 실행 `--round` | 묶음 | 카드 `--rally-round` |
|---|---|---|---|---|---|
| 0. 준비 | 브리프·스타일 가이드·레퍼런스 수집, 렌더·TTS 도구 probe(실측 날짜 기록), `resource-limits.json`에 `render`·`tts` 동시 개수 등록 | `research` | 1 | (없음) | 0 |
| 1. 대본·스토리보드 | 대본, 컷 목록, 자막 초안 → `result.md`, `evidence/`에 스토리보드 | `implementation` | 1 | 대본 | 1 |
| 1'. 대본 검수 | 사실 확인·톤·길이(예상 러닝타임)·저작권 → `pass\|changes` | `review` | 1 | 대본 | 1 |
| 2. 대본 수정 | 지적 반영 | `fix` | 2 | 대본 | 2 |
| 2'. 대본 재검수 | 수정 지점 + 인접 | `review` | 2 | 대본 | 2 |
| 3. 취향 결정 | 두 안 중 톤·구성 선택 → 슈퍼감독이 `kadan decision request`(확인 경로 = 결과 파일 절대경로) | (카드 note + decision) | — | — | — |
| 4. 자산 제작 (병렬) | 음성(TTS)·자막·썸네일·B-roll. 레인마다 새 묶음, 레인마다 1라운드 구현 | `implementation` | 3 | 레인별 | 1 |
| 4'. 자산 검수 (병렬) | 레인마다 1라운드 검수 | `review` | 3 | 레인별 | 1 |
| 5. 편집·렌더 | 자산 합치기·렌더. 렌더는 `kadan limit run render -- …`, 긴 렌더는 `card progress --activity waiting` + 일회성 대기 프로그램 → 완료 시 `kadan send` 1회 | `implementation` | 4 | 편집 | 1 |
| 5'. 완성본 검수 | 화질·싱크·자막 타이밍·길이·오탈자 → `evidence/`에 프레임 캡처 | `review` | 4 | 편집 | 1 |
| 6. 수정 / 6'. 재검수 | 지적 반영·재렌더 / 수정 지점 재검수 | `fix` / `review` | 5 | 편집 | 2 |
| 7. 게시 승인·게시 | 사용자 결정(게시 여부) → 게시 실행. 카드는 관리·조율 카드(`--work-type coordination`, 묶음 없음) | 업무 `release` | 6 | (없음) | — |

같은 번호에 병렬 자산 실행이 여러 개 있는 것은 정상이다. 레인마다 역할 이름을 다르게 둔다(`<판>-음성`, `<판>-자막`). 왕복 상한·수렴 판단은 [티키타카](tiki-taka.md)를 따르되, LIGHT/HEAVY 대신 아래 무게 기준을 쓴다.

## 카드에 적는 것 (영상 고유)

[카드 템플릿](card-template.md)의 양식에 아래를 더한다.

- **합격 기준**: 길이(±초), 싱크(자막·음성 오차 허용), 자막 오탈자 0, 톤(브리프의 낱말로), 저작권(사용 가능한 자산 목록 안), 납품 형식 일치.
- **무게**: 새 포맷·새 도구·외부 게시·유료 자산이 들어가면 HEAVY(정상 + 엣지 + 다른 기기에서 재생 확인). 그 외 LIGHT(정상 경로 + 가장 위험한 엣지 하나).
- **검수 공통 계약 중 적용하지 않는 항목**: `kadan slot acquire`(git 저장소 전제), 커밋 SHA 고정, 검증 근거 5항목의 "명령·종료 코드" — 대신 **파일 지문(SHA-256)·길이·해상도·재생 확인 기기**를 적는다. 결과 등록(`card report`)은 그대로 한다.
- **외부 도구 대기**: 렌더·TTS는 [외부 실행 대기](dispatch-wait.md#외부-실행-대기--프로그램은-기다리고-ai는-응답-종료)를 따른다. 작업자는 `card progress --activity waiting`을 남기고 응답을 끝내며, 대기 프로그램이 결과 파일과 `kadan send` 1회로 깨운다.

## 하지 않는 것

- 결과물 파일(영상·음성)을 `evidence/`에 넣지 않는다. 작업 공간에 두고 경로·지문만 적는다([근거 폴더](card-template.md#근거-폴더와-작업-공간)).
- `limit run render`를 설정하지 않은 채 렌더를 병렬로 돌리지 않는다. 설정이 없으면 명령은 "알 수 없는 종류"로 거절되므로 0단계에서 먼저 등록한다(2026-10-02 병렬 빌드로 스왑 포화 사고와 같은 유형).
- 게시는 사용자 결정 없이 하지 않는다. 렌더 완료·검수 합격은 게시 승인이 아니다.
- 취향 결정을 판 감독이 사용자에게 직접 올리지 않는다. 판 감독은 `card note --kind question`으로 슈퍼감독에게, 슈퍼감독이 `decision request`로 사용자에게([중앙 결정 경로](central-cards.md#사용자-결정-요청-전용-경로)).
