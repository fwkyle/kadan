# 발령과 대기

## Why

카단 라이트에는 중계기·companion·훅 감시기가 없다. 감독은 CLI 편지가 새 입력으로 들어오면
재개하고, 결과 파일과 DONE 마커를 확인해 다음 행동을 정한다.

[진행·승인 공통 기준](operating-contract.md)을 따른다. 응답 종료는 폴링 중지이며,
비서에게 판의 다음 행동을 넘기는 절차가 아니다. 독립 가능한 승인된 후속은 먼저 연결한다.

## 자동 역할 지침과 발령

[공통](role-templates/common.md)과 [역할별 템플릿](../../../docs/role-instructions.md)이 메시지의 기본 책임을 보완한다.
자동 첨부는 새 발령·승인이 아니며, 현재 실행의 범위·수신자·시작·완료 계약은 카드가 정한다.
수신자는 받은 본문·최신 카드/판단을 읽고 이번 행동에 필요한 상세 절만 다시 읽는다.
안내가 붙는 것과 실제 착수·완료는 별개다. 카드 작성자가 빠뜨린 수신자·승인값을 추측하지 않는다.

## 전달 후 확인의 범위

`send`가 확인한 생존·입력 전달을 AI가 같은 목적의 `read/status/log`로 다시 확인하지 않는다.
성공은 입력 전달까지만 뜻한다. 정상 발령 뒤 착수 화면이나 첫 도구 출력을 기다리지 않고
기존 완료/질문 경로로 돌아간다. 새 세션 준비·전달 불명확·실제 오류·사용자 실착수 확인 요청은
필요한 화면 확인을 한다. 아래 수동 절차의 도착 확인도 이 기준을 따른다.

## 구현·검수 자동 전달 — 명시 설정한 업무만

감독이 기존 구현·검수 중앙 카드와 두 담당·상위 수신자·기존 시한을 `work auto-configure`에
명시한 업무만 `work auto-run` 프로그램으로 다음 담당에게 전달한다.
원본 기준은 복제하지 않는다. 새 실행ID는 기존 업무의 `work execute`로 만들고,
작업자·검수자는 결과 파일을 완성한 뒤 현재 실행ID로 `work auto-report`하고 DONE을 출력한다.
프로그램이 현재 실행의 마커를 확인해 원장 done을 기록한다. 감독이 같은 done을 중복하지 않는다.
이 경로의 정상 중간 완료 편지는 감독에게 보내지 않는다. PASS·예외·3라운드 경계에서만
프로그램이 상위에 1회 통지한다. 실행 failed를 품질 수정 필요로 해석하지 않는다.
블록 안 같은 두 세션 유지, 다음 블록 두 세션 교대, 업무 전체 18라운드 상한이다.
검수자는 수정하지 않으며 최종 완료·체크포인트·배포는 감독이 판단한다.

구체적 명령·보고 값·예약 상태·재시작과 불명확 전달의 처리 원본은
[자동 전달 안내](../../../docs/automatic-review.md)에 둔다.
프로그램의 실행 환경·PID·종료 확인 책임을 기록한 뒤 AI는 응답을 끝낸다.
공용 watch를 바꾸거나 과거 업무를 자동 설정하지 않는다. 아래 수동 흐름은 미설정 업무에 계속 적용한다.

## 순서

판을 열면 `kadan plan <판> <카드id>...`로 카드 전부를 먼저 원장에 적는다. watch는 plan ∪ send − done으로 남은 일을 센다.

1. **start**

   새 세션에만 프로필을 지정한다. 기존 세션은 재사용하며 프로필 추가를 위해 재시작하거나 소급 변경하지 않는다.
   일반감독·슈퍼감독 생성은 [역할별 명령](worker-creation.md#새-역할의-프로필)을 따른다.

   ```bash
   cd <작업공간>
   kadan start <판>-작업자 --profile worker --cmd "<agent-runners.json의 command>"
   ```

2. **창 확인**

   사람은 창(Rottie 패널·Ghostty)으로 본다. 감독이 AI면
   `kadan read <역할> --lines 30`으로 하단을 읽어 (a) 실행기 프롬프트·입력창이
   보이는지 (b) 훅 검토·폴더 신뢰·업데이트·로그인 창이 있는지 판정한다.
   (b)가 있으면 **자동 통과 금지** — 사람에게 넘긴다. 둘 다 아니면
   (빈 화면·셸 프롬프트) 실행기가 안 뜬 것이니 send하지 않는다.

3. **send**

   ```bash
   kadan send <판>-작업자 --task <카드id> "<카드 절대경로>를 읽고 수행하라. 끝나면 결과를 <결과 파일>에 쓰고 마지막 줄에 완료 마커를 출력하라. 형식은 KADAN:DONE <카드id> <ok 또는 failed>, 카드 id는 <카드id>."
   ```

   완성된 마커 문자열을 지문에 넣지 않는다. 긴 지시는 카드 파일에 두고 경로만
   보낸다. `send`가 직전에 세션 생존과 pane PID를 대조하므로 죽은 역할에는 발령되지 않는다.

   지시문에 **착수 즉시 진행 기록 1회**를 함께 넣는다: `시작할 때 카드에 진행 기록을 1회 남겨라.`
   감시체계가 발령 5분 뒤 진행 기록이 없으면 "시작 보고 누락"으로 보기 때문이다. 실제로는
   일하고 있는데 기록만 없어서 울리는 알림이 반복되고, 직속 감독이 매번 화면을 대조해 수동으로
   보완하게 된다. 이것은 정상 ACK 편지가 아니며, 편지는 여전히 보내지 않는다.

4. **응답 종료·입력 대기**

   아래 완료 편지 계약으로 전달받는다. 외부 작업은 아래 외부 실행 대기 절의 통지 담당을 먼저 확보한다.
   발령 후 독립적으로 진행할 다른 승인 작업을 연결하고, 기다릴 실제 역할/외부 실행과 깨움 경로를 남긴 뒤 현재 응답을 끝낸다. 세션은 유지한다.

5. **결과 파일 확인**

   결과 전문과 변경 파일, 검증 결과를 읽는다. 터미널 한 줄이나 스피너는 증거가 아니다.

6. **검수 발령**

   새 역할을 `kadan start <판>-검수자 --profile reviewer --cmd ...`로 띄우고 창을 확인한다. 검수 카드에는
   `standard-flow.md`의 gajae 계약, 대상 카드·변경 파일, 합격 기준, 검수 결과 파일,
   완료 마커 형식을 적어 `kadan send`한다.

7. **검수 대기와 판정**

   검수자의 완료 통지를 받은 뒤 검수 결과 파일을 읽는다. 치명·중요가 없고 실물 검증이
   통과했으면 감독이 그 브랜치를 통합 브랜치에 합류시킨다(작업자 커밋은 이미 브랜치에 있다). 발견이 있으면 검수자가
   고치지 않고, 지휘자가 발견 전문을 인용한 수정 카드로 작업자에게 보낸다.
   합격 뒤 승인된 환경 적용·실물 확인이 남으면 이어간다. 보고 송신이나 비서 확인은 이 후속의 관문이 아니다.

## 옛 흉터 중 라이트에도 남는 것

- 스피너는 증거가 아니다. `wait`의 quiet도 완료가 아니다.
- 죽은 터미널에 발령하지 않는다. `send`가 생존과 PID를 대조한다.
- 훅·신뢰 창은 발령 전에 사람이 창에서 확인한다.
- 긴 결과는 파일로 남긴다.
- 죽은 역할을 다시 세울 때 같은 이름을 재사용하지 않는다.
  `kadan stop <역할>` 뒤 `<역할>-2`로 시작해 원장에 세대 흔적을 남긴다.

## 완료 편지와 입력 대기 — 기본 경로

1. 카드에 직속 감독 역할을 반드시 적는다. 작업자·검수자는 결과 파일을 완성하고
   `KADAN_ROLE=<자기 역할> kadan send <직속 감독> "완료 통지: <자기 역할> / <카드id> / <ok 또는 failed> / 결과: <절대경로>"`
   를 한 번 실행한다. 완료 통지는 새 발령이 아니므로 `--task`를 붙이지 않는다.
   실제 완성된 DONE 마커는 편지 본문에 넣지 않는다. 상대 화면에 찍힌 마커가 오인될 수 있다.
2. 발신자는 이어서 자기 터미널에 결과 경로 한 줄과 DONE 마커를 출력하고 응답을 끝낸다.
   발송 성공은 도착·검수 성공이 아니다. 발송 실패는 결과에 남기고 재전송 루프를 만들지 않는다.
3. 감독은 최초 발령의 CLI 전달 결과를 확인한 뒤 응답을 끝내고 입력 대기한다. 정상 착수 화면을 기다리지 않으며, 전달 불명확 때만 추가 확인한다. 세션을 종료하지 않는다.
   `kadan wait`, sleep, 도구 세션 poll, `read/status/log`를 정상 대기용으로 반복 호출하지 않는다.
   “기다립니다” 중간 응답도 반복하지 않는다. CLI 메시지·watch 알림·사용자 지시로 새 입력이 올 때 재개한다.
4. 수신 후 발신 역할·카드·현재 세대의 start/send·결과 경로·완료 원장을 대조한다.
   결과와 발신자 화면의 DONE을 확인한 감독이 `kadan done <발신 역할> <카드id> <ok|failed>`로 기록한다.
   ok는 완료 상태이며 품질 합격은 별도 검수 결과로 판단한다. 원장 확정 전 역할을 stop하지 않는다.
5. 편지가 마커보다 먼저 도착할 수 있다. 결과는 완성됐지만 마커가 아직 없으면 완료를 확정하지 않고
   응답을 끝낸다. 이후 watch 완료후보에서 다시 확인한다. 마커를 기다리는 AI 조회 루프를 만들지 않는다.
6. 같은 역할·카드의 완료 편지와 watch 완료후보가 중복되면 원장과 해당 카드의 후속 발령을 대조한다.
   done이 있다는 이유로 빠진 검수를 건너뛰지 않고, 이미 발령한 검수/다음 카드는 다시 보내지 않는다.
   중복 메시지는 확인 뒤 응답을 끝낸다. 완료후보 자체는 완료 확정이나 검수 합격이 아니다.
7. 감독이 작업 중이면 CLI 메시지는 대기열에 들어갈 수 있다. 강제 중단·즉시 처리 보장이 아니다.
   세션 종료·PID 불일치·인증/제공자 오류는 깨우기로 해결되지 않는다. 실패 원문을 상위에 보고한다.

## 감시와 예외

- `watch`는 기계당 하나로 화면·원장·자원을 주기적으로 확인하고 완료후보·이상을 CLI로 전달한다.
  각 판은 직속 감독에게 route, 감독 이상/상위 판단은 슈퍼감독에게 전달되도록 실제 수신자를 확인한다.
  별도 우편 중계기·반복 깨우기 타이머를 추가하지 않는다. 정상 입력 대기를 이유로 자동 재발령하지 않는다.
- watch가 켜져 있고 라우팅이 맞는지 발령 전에 확인한다. 감시 부재는 조용한 정상 대기로 숨기지 않는다.
- `kadan wait`는 CLI 진단용으로 남아 있다. 명시적인 한정 검사/복구에서만 사용하고 종료 코드
  0=완료 마커, 2=마커 없는 정지/출력누락, 3=시간 초과, 1=오류를 구분한다. 정상 감독 대기의 기본값은 아니다.
- 이미 실행 중인 wait는 새 카드를 재발령하지 말고 해당 감독이 자기 대기 도구만 정리한다.
  작업자·watch·다른 판 프로세스를 죽이지 않는다. 진행 중 구형 카드는 완료후보를 복구 경로로 사용하고,
  다음 안전한 카드 경계부터 직속 감독/완료 통지 계약을 넣는다.

## 외부 실행 대기 — 프로그램은 기다리고 AI는 응답 종료

GitHub Actions처럼 자체적으로 카단 편지를 보내지 않는 외부 실행은 완료 통지 담당을
확보한 뒤 입력 대기한다. **금지하는 것은 AI의 반복 대기 응답이지 프로그램의 wait가 아니다.**
기존 중계기 추가 금지는 이 한 실행에 묶인 일회성 대기·통지 프로그램을 금지하지 않는다.

1. 외부 실행을 시작한 역할이 저장소·정확한 실행 ID·attempt·직속 감독·근거 경로·대기 상한을
   카드/결과에 적는다. 같은 실행의 대기 담당은 하나다. 기존 실행과 담당을 먼저 확인하고
   배포나 대기 프로그램을 중복 생성하지 않는다.
2. GitHub 예: `gh run watch <run-id> --repo <owner/repo> --exit-status --interval 30`.
   이 명령만으로 카단 편지가 오지는 않는다. 종료 뒤 상태 확인·결과 저장·CLI 통지까지 이어지는
   일회성 프로그램으로 실행한다. 셸의 `set -e` 때문에 실패 경로의 통지가 생략되지 않게 한다.
3. 프로그램은 제한 시간 안에서 한 실행만 기다린다. GitHub에서는 대기 종료 후 같은 실행의
   `status`, `conclusion`, attempt와 URL을 조회해 기록한다. watch 명령의 비0 종료만으로
   배포 실패를 단정하지 않는다. 통신/인증 오류·시간 초과·취소·원격 실패를 구분하고,
   최종 조회도 실패하면 **모름**으로 남긴다. 원격 완료 전 대기 종료는 배포 취소/실패가 아니다.
4. 정상·실패·취소·시간 초과·조회 오류 모두 결과를 파일에 먼저 기록한 뒤
   `KADAN_ROLE=<담당 역할> kadan send <직속 감독> "외부 실행 결과: <카드id> / <저장소·run-id·attempt> / <상태> / 근거: <절대경로>"`
   로 한 번 전달한다. `--task`·완성된 DONE 마커·비밀값·원문 로그는 편지에 넣지 않는다.
   외부 실행 성공은 카드 전체의 검수/실물 확인 완료가 아니다. 카드 done을 대신 확정하지 않는다.
5. AI 도구 호출/현재 응답이 끝나도 프로그램이 살아 있도록 전용 tmux 세션 등 확인된 실행
   방법을 쓴다. 도구가 반환한 세션 ID나 셸의 `&`만으로 지속 실행을 가정하지 않는다.
   대기 PID/세션·정확한 대상·결과/전달 기록 경로와 직속 수신자 생존을 한 번 확인한 뒤
   AI는 응답을 끝낸다. AI가 write_stdin/poll/sleep로 대기 프로그램을 반복 확인하지 않는다.
6. 감독은 편지를 받으면 같은 외부 실행의 근거를 확인하고 기존 승인된 검증/다음 단계를
   이어간다. 배포를 다시 시작하지 않는다. 동일 실행·attempt의 중복 통지는 기록과 후속
   발령을 대조해 한 번만 처리한다. 실패/시간 초과는 원인 판단 대상이지 자동 재배포 사유가 아니다.
7. 통지 실패는 파일에 보존하고 자동 재전송하지 않는다. 대기 프로그램 비정상 종료·통지 실패를
   누가 발견할지 카드에 지정한다. 기존 감시가 임의 외부 PID나 GitHub 상태까지 감시한다고
   가정하지 않는다. 감독 정체 알림을 받았으면 그 감독이 기록된 대기 담당과 외부 실행을
   한 번 확인한다. 단지 “정상 대기”라고 넘기지 않는다. 통지와 실패 확인 책임이 없으면
   외부 작업을 인계 완료로 처리하지 말고 막힌 점을 상위에 보고한다.

이미 종료된 실행은 다시 watch하지 말고 정확한 실행을 한 번 조회해 결과를 전달한다.
이 예외는 외부 실행의 읽기 대기/통지에 한정하며, 새 배포·외부 설정 변경 권한을 추가하지 않는다.
