# 발령과 대기

## Why

준비한 실행을 전달하고 결과를 다음 담당에게 연결하되, 정상 왕복마다 감독의 재작성·조회·중계를 반복하지 않는다.

[진행·승인 공통 기준](operating-contract.md)에 따라 신규 반복 왕복은 자동 전달을 우선 검토하고, 기존 수동 업무나 자동 계약이 맞지 않는 일은 수동으로 잇는다. 자동은 명시 설정한 업무에만 적용한다. 응답 종료는 폴링 중지이며 후속 책임을 비서에게 넘기는 일이 아니다.

## 자동 역할 지침과 발령

[공통](role-templates/common.md)과 [역할별 템플릿](../../../docs/role-instructions.md)이 메시지의 기본 책임을 보완한다.
자동 첨부는 새 발령·승인이 아니며, 현재 실행의 범위·수신자·시작·완료 계약은 카드가 정한다.
수신자는 받은 본문·최신 카드/판단을 읽고 이번 행동에 필요한 상세 절만 다시 읽는다.
안내가 붙는 것과 실제 착수·완료는 별개다. 카드 작성자가 빠뜨린 수신자·승인값을 추측하지 않는다.

일반 터미널 우편에는 우편 ID와 수신자용 `inbox ack` 명령이 붙는다. 내용을 확인한 수신자가
직접 실행하며, 조회·답장·DONE으로 자동 읽음 처리하지 않는다. ack는 로컬 읽음 사건만 남기고
회신 우편을 보내지 않는다. `--raw`는 본문을 보존하므로 영수증 또는 자기 inbox에서 ID를 확인한다.
미확인 우편을 다시 알리는 메시지에는 ack 안내를 붙이지 않는다.

## 전달 후 확인의 범위

`send`가 확인한 생존·입력 전달을 AI가 같은 목적의 `read/status/log`로 다시 확인하지 않는다.
성공은 입력 전달까지만 뜻한다. 정상 발령 뒤 착수 화면이나 첫 도구 출력을 기다리지 않고
기존 완료/질문 경로로 돌아간다. 새 세션 준비·전달 불명확·실제 오류·사용자 실착수 확인 요청은
필요한 화면 확인을 한다. 아래 수동 절차의 도착 확인도 이 기준을 따른다.

## 구현·검수 자동 전달 — 명시 설정한 업무만

감독이 기존 구현·검수 중앙 카드와 두 담당·상위 수신자·기존 시한을 `work auto-configure`에
명시한 업무만 `work auto-run` 프로그램으로 다음 담당에게 전달한다.
원본 기준은 복제하지 않는다. 새 실행ID는 기존 업무의 `work execute`로 만들고,
작업자·검수자는 결과 파일을 완성한 뒤 현재 실행ID로 `work auto-report`하고 DONE을 출력한다.
프로그램이 현재 실행의 마커를 확인해 원장 done을 기록한다. 감독이 같은 done을 중복하지 않는다.
이 경로의 정상 중간 완료 편지는 감독에게 보내지 않는다. PASS·예외·3싸이클 경계에서만
프로그램이 상위에 현재 `executionKey`를 연결해 1회 통지한다. 실행 failed를 품질 수정 필요로 해석하지 않는다.
블록 안 같은 두 세션 유지, 다음 블록 두 세션 교대, 업무 전체 18싸이클 상한이다.
검수자는 수정하지 않으며 최종 완료·체크포인트·배포는 감독이 판단한다.

구체적 명령·보고 값·예약 상태·재시작과 불명확 전달의 처리 원본은
[자동 전달 안내](../../../docs/automatic-review.md)에 둔다.
프로그램의 실행 환경·PID·종료 확인 책임을 기록한 뒤 AI는 응답을 끝낸다.
공용 watch를 바꾸거나 과거 업무를 자동 설정하지 않는다. 아래 수동 흐름은 미설정 업무에 계속 적용한다.

## 순서

### 수동 발령

자동 설정 업무의 중간 실행에는 이 수동 절차를 중복 적용하지 않는다. 수동 경로는 [중앙 카드](central-cards.md)의 최신 승인·배정과 `kadan plan <판> <카드id>...` 기록을 갖춘 뒤 발령한다. plan은 미발령 카드도 보이게 하며, 실제 미완료 발령 감시는 [감시 기준](../../../docs/watch-overview.md)을 따른다.

1. **역할 준비:** [작업자 생성](worker-creation.md)에 따라 새 작업은 새 세션, 같은 대상의 연속 작업만 기존 세션을 쓴다. 새 역할은 `kadan start <판>-작업자 --profile worker --cmd "<확인한 실행 명령>"`으로 시작한다. 검수자는 reviewer 프로필이다.
2. **새 세션 확인:** `kadan read <역할> --lines 30`으로 TUI 입력창·훅·신뢰·업데이트·로그인 창을 확인한다. 막는 창은 자동 통과하지 않고 사람에게 넘긴다. 셸 프롬프트·빈 화면이면 준비 완료로 간주하지 않는다. 준비된 연속 세션의 정상 send마다 이 확인을 반복하지 않는다.
3. **전달:** `kadan send <역할> --task <현재실행키> "<카드 절대경로>와 읽고 시작할 것을 확인해 수행하라. 시작 기록은 1회, 결과와 완료는 카드의 수동 계약을 따르라. 마커 형식은 KADAN:DONE <현재실행ID> <ok 또는 failed>."`처럼 경로와 형식만 보낸다. 실제 ID·결과를 조립한 완성 마커는 입력에 넣지 않는다. send가 직전 생존·PID를 확인한다.
4. **대기:** 전달 성공 뒤 정상 착수 화면을 기다리지 않는다. 독립적인 승인 작업을 연결하고 실제 대기 대상·깨움 경로를 남긴 뒤 응답을 끝낸다. 외부 실행은 아래 일회성 통지 담당을 먼저 확보한다.
5. **완료와 후속:** 아래 계약으로 결과·DONE을 확정하고 독립검수를 연결한다. 첫 검수는 새 독립 역할, 같은 대상 재검수는 [유지 기준](cleanup.md)을 따른다. 발견은 같은 업무의 작업자에게 원문으로 전달한다. 진행 중 실행에는 추가 입력, 종료된 실행 뒤에는 원본 기준을 참조하는 새 실행을 쓴다. 합격 뒤 승인된 적용·실물 확인도 이어간다.

독립 소유로 나눌 수 있고 자원이 허용하면 병렬 발령하되, 같은 방식의 연속 처리를 임의 개수마다 쪼개지 않는다. 죽은 역할은 같은 이름으로 재생성하지 않고 정확한 기존 역할을 정리한 뒤 `<역할>-2`처럼 새 이름으로 세운다. 역할을 새 프로필로 바꾸려고 기존 세션을 재시작하지 않는다.

## 완료 편지와 입력 대기 — 기본 경로

실행 done을 기록하면 코어가 원본 발령자의 우편함에 결과 통지를 한 번 저장한다. 이 통지는 `notificationOnly: true`인 기록용 결과이며, 작업 발령·터미널 입력·미확인 우편 깨움 대상이 아니다. 실제 알림은 아래 직속 감독 완료 편지 또는 자동 왕복의 최종 통지가 맡으며 DONE 확인 절차를 유지한다. 결과 우편의 `executionKey`·`workKey`·`replyTo` 또는 과거 실행의 `completionTaskId`로 대상을 확인한다. 저장·읽음·최종 답변과 실행 완료·검수 합격·업무 최종 완료는 구분한다.

질문은 `send --expect-reply`, 최종 답장은 `send --reply-to <우편ID> --reply-final`로 연결한다. `inbox to-reply --role <자기 역할>`은 내가 답할 질문, `inbox waiting --role <자기 역할>`은 내가 답을 기다리는 질문이다. 읽음과 중간 답장은 대기를 끝내지 않는다. [공통 원장 계약](../../../docs/mail-task-ledgers.md)을 따른다.

현재 실행에 관한 답변을 기다리는 질문은 `send <직속 상위> --execution <현재 카드의 전체 키> --expect-reply <질문>`으로 정확히 연결한다. 카드 없는 일반 대화까지 실행에 묶거나 여러 실행 중 하나를 추정하지 않는다. 인계 뒤 회신 주소는 `inbox read <우편ID>`의 현재 안내로 확인한다.

수동 작업자·검수자의 결과 등록·완료 편지·DONE 순서는 [실행 공통 계약](card-template.md#결과-등록과-완료)을 따른다. 카드에 실제 직속 감독과 전달 방식을 적고 자동 경로에 수동 편지를 추가하지 않는다.

감독은 다음 기준으로 처리한다.

1. 발신 역할·현재 실행·현재 세대의 start/send·결과 경로를 대조하고, 결과와 발신자 자기 화면 DONE을 확인해 `kadan done <역할> <현재실행ID> <ok|failed>`로 확정한다. 작업자에게 확정을 시키지 않는다. 실행 ok는 품질 합격이 아니다.
2. 완료 편지가 마커보다 먼저 도착하면 확정하지 않고 응답을 끝낸다. 이후 watch 완료후보에서 다시 확인하며 마커를 기다리는 AI 조회 루프를 만들지 않는다.
3. 완료 편지·watch 후보가 중복되면 원장과 후속 발령을 대조한다. 이미 done이면 중복하지 않고, done이 있어도 빠진 검수는 연결하며 이미 발령한 후속은 다시 보내지 않는다.
4. 결과·done 확정 뒤 남은 담당 일과 [종료·정리](cleanup.md)를 확인해 정확한 역할만 종료한다. 역할 종료가 검수·업무 마감을 대신하지 않는다.
5. 감독이 작업 중이면 우편이 대기열에 들어갈 수 있다. 즉시 처리나 강제 중단을 보장하지 않는다. 세션 종료·PID 불일치·인증/제공자 오류는 깨우기로 해결하지 않고 실패 원문을 상위에 보고한다.

정상 대기에는 `wait`·sleep·도구 세션 poll·read/status/log 반복과 “기다립니다” 중간 응답을 만들지 않는다. 전달 불명확·실제 오류·사용자의 실착수 확인 요청 때만 필요한 추가 확인을 한다. 완료·질문 통지, watch 알림 또는 사용자 지시가 새 입력이다.

## 감시와 예외

- `watch`는 기계당 하나로 화면·원장·자원을 주기적으로 확인하고 완료후보·이상을 CLI로 전달한다.
  각 판은 직속 감독에게 route, 감독 이상/상위 판단은 슈퍼감독에게 전달되도록 실제 수신자를 확인한다.
  별도 우편 중계기·반복 깨우기 타이머를 추가하지 않는다. 정상 입력 대기를 이유로 자동 재발령하지 않는다.
- watch가 켜져 있고 라우팅이 맞는지 발령 전에 확인한다. 감시 부재는 조용한 정상 대기로 숨기지 않는다.
- `kadan wait`는 CLI 진단용으로 남아 있다. 명시적인 한정 검사/복구에서만 사용하고 종료 코드
  0=완료 마커, 2=마커 없는 정지/출력누락, 3=시간 초과, 1=오류를 구분한다. 정상 감독 대기의 기본값은 아니다.
- 이미 실행 중인 wait는 새 카드를 재발령하지 말고 해당 감독이 자기 대기 도구만 정리한다.
  작업자·watch·다른 판 프로세스를 죽이지 않는다. 진행 중 구형 카드는 완료후보를 복구 경로로 사용하고,
  다음 안전한 카드 경계부터 직속 감독/완료 통지 계약을 넣는다.

## 외부 실행 대기 — 프로그램은 기다리고 AI는 응답 종료

GitHub Actions처럼 자체적으로 카단 편지를 보내지 않는 외부 실행은 완료 통지 담당을
확보한 뒤 입력 대기한다. **금지하는 것은 AI의 반복 대기 응답이지 프로그램의 wait가 아니다.**
기존 중계기 추가 금지는 이 한 실행에 묶인 일회성 대기·통지 프로그램을 금지하지 않는다.

1. 외부 실행을 시작한 역할이 저장소·정확한 실행 ID·attempt·직속 감독·근거 경로·대기 상한을
   카드/결과에 적는다. 같은 실행의 대기 담당은 하나다. 기존 실행과 담당을 먼저 확인하고
   배포나 대기 프로그램을 중복 생성하지 않는다.
2. GitHub 예: `gh run watch <run-id> --repo <owner/repo> --exit-status --interval 30`.
   이 명령만으로 카단 편지가 오지는 않는다. 종료 뒤 상태 확인·결과 저장·CLI 통지까지 이어지는
   일회성 프로그램으로 실행한다. 셸의 `set -e` 때문에 실패 경로의 통지가 생략되지 않게 한다.
3. 프로그램은 제한 시간 안에서 한 실행만 기다린다. GitHub에서는 대기 종료 후 같은 실행의
   `status`, `conclusion`, attempt와 URL을 조회해 기록한다. watch 명령의 비0 종료만으로
   배포 실패를 단정하지 않는다. 통신/인증 오류·시간 초과·취소·원격 실패를 구분하고,
   최종 조회도 실패하면 **모름**으로 남긴다. 원격 완료 전 대기 종료는 배포 취소/실패가 아니다.
4. 정상·실패·취소·시간 초과·조회 오류 모두 결과를 파일에 먼저 기록한 뒤
   `KADAN_ROLE=<담당 역할> kadan send <직속 감독> "외부 실행 결과: <카드id> / <저장소·run-id·attempt> / <상태> / 근거: <절대경로>"`
   로 한 번 전달한다. `--task`·완성된 DONE 마커·비밀값·원문 로그는 편지에 넣지 않는다.
   외부 실행 성공은 카드 전체의 검수/실물 확인 완료가 아니다. 카드 done을 대신 확정하지 않는다.
5. AI 도구 호출/현재 응답이 끝나도 프로그램이 살아 있도록 전용 tmux 세션 등 확인된 실행
   방법을 쓴다. 도구가 반환한 세션 ID나 셸의 `&`만으로 지속 실행을 가정하지 않는다.
   대기 PID/세션·정확한 대상·결과/전달 기록 경로와 직속 수신자 생존을 한 번 확인한 뒤
   AI는 응답을 끝낸다. AI가 write_stdin/poll/sleep로 대기 프로그램을 반복 확인하지 않는다.
6. 감독은 편지를 받으면 같은 외부 실행의 근거를 확인하고 기존 승인된 검증/다음 단계를
   이어간다. 배포를 다시 시작하지 않는다. 동일 실행·attempt의 중복 통지는 기록과 후속
   발령을 대조해 한 번만 처리한다. 실패/시간 초과는 원인 판단 대상이지 자동 재배포 사유가 아니다.
7. 통지 실패는 파일에 보존하고 자동 재전송하지 않는다. 대기 프로그램 비정상 종료·통지 실패를
   누가 발견할지 카드에 지정한다. 기존 감시가 임의 외부 PID나 GitHub 상태까지 감시한다고
   가정하지 않는다. 감독 정체 알림을 받았으면 그 감독이 기록된 대기 담당과 외부 실행을
   한 번 확인한다. 단지 “정상 대기”라고 넘기지 않는다. 통지와 실패 확인 책임이 없으면
   외부 작업을 인계 완료로 처리하지 말고 막힌 점을 상위에 보고한다.

이미 종료된 실행은 다시 watch하지 말고 정확한 실행을 한 번 조회해 결과를 전달한다.
이 예외는 외부 실행의 읽기 대기/통지에 한정하며, 새 배포·외부 설정 변경 권한을 추가하지 않는다.
