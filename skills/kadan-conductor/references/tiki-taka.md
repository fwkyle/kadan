# 티키타카 루프 — 유일한 왕복 루프 + 검수 규칙 원본

모든 구현 판은 구현↔검수 왕복으로 돈다. 방향이 갈릴 때만 첫 라운드를 배틀
오프닝으로 시작한다. 지휘자는 외부 터미널, 구현과 검수는 서로 다른 카단 역할이다.
같은 작업공간을 보되 검수자는 새 세션이어야 한다.

## 자동 전달 블록의 세션 예외

`work auto-configure`로 명시 설정한 업무는 블록 시작에 작업자·독립검수자 두 세션을
확인하고 3라운드 블록 안에서는 같은 두 세션을 유지한다. 아래의 매 검수 새 역할 원칙은
이 경로에서는 블록 경계에 적용한다. 다음 블록에는 둘 다 새 세션으로 교대하며 과거 블록
세션도 재사용하지 않는다. 전체 18라운드는 업무 한도다. PASS는 즉시 감독 최종 판단으로
넘기고 세 번째 수정 필요 뒤 자동 네 번째 발령은 없다.
명령·통지·시한·중복 방지는 [자동 전달 계약](dispatch-wait.md#구현검수-자동-전달--명시-설정한-업무만)을 따른다.

## 라운드 밖 3가지

**라운드 = 작업+검수 왕복 1회**다. 아래는 검수 왕복이 없어 라운드에 세지 않는다.

1. **probe** — 실행기·환경·가용성 확인. 발령 전 1회.
2. **investigation(조사)** — 읽기 전용 조사 카드. 코드 변경이 없으므로 지휘자가
   결과의 파일:줄 근거를 대조해 종결한다.
   - **파괴적 결정 전 2차 의견**: 조사 결과가 삭제·초기화·마이그레이션의 근거가 되면
     조사 카드 하나만 믿지 않는다. 다른 조사자 한 명이 같은 근거를 다시 확인하는
     2차 의견 카드 1개를 추가하고, 둘이 맞을 때만 사용자 결정 관문으로 올린다.
   - **RESEARCH 선행 카드**: 외부 사례·공식 문서가 구현 카드의 합격 기준이나 접근법을
     바꿀 가능성이 있을 때만(설계 선택지 여럿, 새 라이브러리·API·표준 도입, 같은 실패
     2회 이상 반복) 읽기 전용 리서치 카드를 구현 앞에 둔다. 문구·설정값 변경, 원인이
     확실한 버그, 저장소 기존 패턴을 따르는 작업은 생략한다. 결과는 패턴 최대 3개,
     각각 출처·핵심 원리·적용 가능한 부분·적용하면 안 되는 부분·확인 안 된 가정.
     지휘자가 채택·보류·기각을 정하고 채택한 것만 구현 카드로 옮긴다.
3. **micro-fix(마이크로 정정)** — 검수의 사소/관찰 1~2건을 작업자가 고치고
   지휘자가 대조한다. 치명·중요에는 금지한다. 한 카드에서 3건 이상이면 정식
   재검수로 승급한다.

## 기본 왕복

```text
1. 카드 파일 → kadan send → 작업자
2. 응답 종료 → 완료 편지·DONE 확인 → 결과 파일 확인
3. 새 검수 카드 → kadan send → 검수자
4. 응답 종료 → 완료 편지·DONE 확인 → 검수 결과 파일 확인
5. 발견 없음: 통합 브랜치 합류
6. 발견 있음: 발견 전문을 인용한 수정 카드로 작업자에게 재발령
```

## 라운드 사다리 (2026-07-22 사용자 개정 v3)

**라운드 = 작업+검수 왕복 1회**, **블록 = 연속 3라운드**, **총 상한 = 6블록,
18라운드**다. 구현·수정·재설계를 구분하지 않고 모두 같은 라운드로 센다.

- **수렴 중이면 방향 유지**: 치명 0 유지 + 중요 감소 추세면 수정 카드 블록을
  계속한다. 같은 검수 범위끼리만 비교한다.
- **정체·재생산이면 재설계 전환**: 발견 수가 줄지 않거나 같은 부류가 반복되면
  패치 누적을 멈추고 접근 구조를 바꾼다.
- **조기 탈출**: 재설계를 거쳐도 정체 블록 3개(9라운드)가 이어지면 슈퍼감독에게 먼저 묻는다.
- **총 상한**: 수렴 중이어도 18라운드면 사용자에게 묻는다.
- 재설계 전환 때 이 파일의 사다리·검수 규칙과 옛
  `../../kadan-super/references/scars.md`의 관련 사고를 다시 읽는다.
- 사용자가 별도 라운드 한도를 주면 그것이 우선한다. 기존 승인 밖 파괴적 결정·범위 변경은 즉시 묻는다.
- 모델 교체는 라운드 실패의 자동 결과가 아니다. 실행기 자동 교체는 지금 없으므로
  (금지가 아니라 아직 없는 것, 2026-09-02 사용자 정정) 필요하면 사람이
  `agent-runners.json`에서 다시 고른다.

## 한 라운드 안의 진행 조정 (2026-09-07 사용자 결정)

Why: 작업자가 움직여도 같은 실패를 반복할 수 있다. 일반감독이 실제 진전을 확인하고
방법·범위를 조정하되, DB나 복잡한 검수에 필요한 시간을 단순 지연으로 오판하지 않는다.

진행 방법·절차를 바꾸거나 작업을 나누기 전 [단순화 규칙](operating-contract.md#단순화-규칙)을 적용한다.

- **횟수와 시간은 별개다.** 3라운드 블록·18라운드 상한은 구현과 독립검수의 왕복을 센다.
  작업자 혼자 시험을 다시 돌린 횟수는 라운드가 아니며, 감독은 3라운드가 되기 전에도 조정한다.
- **30분은 감시 관찰 기준이다.** 현재 감시체계의 진행 조정/판단 불가 알림을 받으면 직속
  일반감독이 카드·결과·필요한 화면만 대조한다. 이 스킬 때문에 별도 AI 폴링·타이머를 만들지 않는다.
- **60분은 감독 판단 기준이다.** 같은 실행 단계가 60분 이상 이어지는 것을 알림·진행 보고에서
  확인하면 계속할 이유와 남은 일을 기록한다. 현재 감시sh에 별도 60분 알림이나 카드 상한의
  자동 강제가 구현됐다는 뜻은 아니다. 단순히 마지막 보고가 오래됐다는 이유만으로 정체로 판정하지 않는다.
- 판단은 기존 카드의 판단 기록에 짧게 남긴다: **지난 확인 이후 해결된 것 / 제품 코드·도구·검증
  방법 중 병목 / 계속·방법 변경·분리 중 조치 / 다음 확인 시점 또는 조건**. 기존 사건은 고치지 않는다.
  기록은 판정과 근거를 뜻하며 실제 조치는 별도로 전달하고 확인한다.
- **계속이 합리적이면 유지한다.** DB·복잡한 검수라도 실제 진전과 남은 작업이 명확하면
  일반감독이 계속할 이유를 적고 유지한다. 한 번 실패·시간 경과·감시ai 판단만으로 중단하지 않는다.
- **같은 실패 반복·목표 밖 범위 확장·끝낼 방법 불명확**이면 일반감독이 자기 권한에서 검증 방법을
  바꾸거나 독립 작업을 분리한다. 도구 실패를 제품 결함으로 단정하지 않는다. 구현·원인 탐색은
  작업자에게 맡기고 감독은 직접 구현하지 않는다. 조정 뒤 같은 근거 없는 재시도를 반복시키지 않는다.
- 일반감독이 결정하기 어렵거나 다른 판과 충돌·목표/승인 범위 변경이 필요하면 슈퍼감독에게
  상황·선택지·추천·답 없이 가능한 일을 보낸다. 감시의 연속 조정2회 알림은 상위 상담을 촉구하는
  추가 신호이며, 두 번을 기다려야 질문할 수 있다는 뜻이 아니다.
- **카드의 명시 시간 상한은 별도 계약이다.** 상한 도달 전에 남은 일과 연장/분리 제안을 슈퍼에게
  올리고, 허용된 연장 결정 없이 넘기지 않는다. 슈퍼의 권한 밖이면 사용자에게 묻는다.
  데이터/WIP·진행 중 안전한 명령 경계를 보존하며 강제 종료로 시간을 맞추지 않는다.
- 질문 대기는 답에 종속된 행동에 한정한다. 같은 카드 안에서도 영향 없는 승인 작업은 계속한다.
  이미 합격한 동일 범위는 재검증을 발령하지 말고 결과와 이번 조정 근거만 확인한다. 필요한 최초·변경 검수는 유지한다.

기록 예: “타입 검사 통과. 화면 검증은 업로드 입력 방식에서 반복 실패. 기존 사진 제거 후
선택하는 실제 흐름으로 바꾼다. 다음 검증도 같은 원인으로 실패하면 대체 검증 방법을 판단한다.”

승인된 일의 진행·재개 판단은 일반감독과 슈퍼감독이 맡는다. 비서 보고의 확인/회신을
추가 승인 관문으로 만들지 않는다. 상세 책임은 [슈퍼감독 진행 책임](../../kadan-super/SKILL.md)을 따른다.

## 감독의 질문 사다리 (2026-09-05 사용자 결정)

1. 감독은 사용자에게 묻기 전에 슈퍼감독에게 먼저 묻는다. 직접 가는 예외는 5)뿐이다.
2. 카드 해석이 실제로 갈릴 때, 정체 블록 1개(3라운드 발견 수 안 줄음)를 지나 필요한 재설계가
   기존 승인 범위를 넘을 때, 실행기 한도·자원으로 진행이 막힐 때, 검수 발견이 기존 승인
   범위를 넘어 보일 때 묻는다. 승인 안의 수정은 구조변경이라는 이름만으로 재질문하지 않는다.
3. 질문은 아래 형식으로 보낸다. 완성된 DONE 마커 문자열은 지문에 쓰지 않는다
   (docs/design.md 잠긴 규칙 6).

   `kadan send 슈퍼감독 "질문 <판> <카드>: 상황 한 문단 / 선택지 A·B(·C) / 내 추천과 이유 / 답 없이 진행 가능한지"`

4. 물은 뒤에는 답에 종속된 행동만 멈추고 영향 없는 승인 작업·읽기 전용 조사는 계속한다. 답은
   슈퍼감독의 우편(`kadan send <판>-감독`)으로 오며 필요한 `kadan read`로
   확인한다. 같은 질문을 두 번 보내지 않는다.
5. 사용자에게 직접 가는 것은 기존 승인 범위 밖의 삭제·초기화·마이그레이션·push·병합·배포,
   범위 변경, 제품 방향·취향, 18라운드 상한, 슈퍼감독이 없거나 답이 없을 때뿐이다
   (watch 죽음/전달실패 알림으로 확인).

라운드 원본은 중앙 카드의 명시적인 티키타카 연결이다. `rallyId/rallyRound/rallyStep`을
사용하고 이름 기반 옛 tree 라운드는 참고만 한다. 관련 조사는 round0이며 자체 시험 반복은 세지 않는다.

## 검수 규칙

**무검수 단독 편성은 없다.** 지휘를 걸었다는 것 자체가 검수받을 일이라는 뜻이다.

무게는 검수 강도가 아니라 합격 기준 개수의 차이다.

| 무게 | 합격 기준 |
|---|---|
| LIGHT (기본) | 1~2개: 정상 경로 + 가장 위험한 엣지 |
| HEAVY | 3개 이상: 정상 + 엣지 + 회귀 |

HEAVY 조건: 새 모듈·레이어·추상화, 인증·보안·세션·권한, 외부 연동, DB 스키마·
마이그레이션, 동시성·트랜잭션·캐시 무효화, 도메인 경계를 넘는 리팩터,
사용자의 "신중하게/꼼꼼히" 신호.

**래칫**: 애매하면 상위 등급이다. 도중에 HEAVY 사실이 드러나면 즉시 승급하고
LIGHT가 건너뛴 검증을 다시 한다. 강등하지 않는다.

- 검수 카드의 계약 문장(불신·실측, 서브에이전트 전파, 증거 재사용 판정, 근거 파일
  장소)은 `card-template.md`가 원본이다. 복사해 쓰고 여기에 다시 적지 않는다.
- 검수자는 작업자와 다른 새 역할로 시작한다. 구현 문맥을 이어받지 않는다.
- 첫 검수는 전체 범위, 이후에는 수정 지점 + 인접 회귀 + 발견 재현을 검수한다.
  재설계급 수정이나 치명 발견 뒤에는 다시 전체 범위다.
- 검수자에게 소스 수정을 요구하지 않는다. 발견은 작업자 수정 카드로 보낸다.
- 라운드당 검수는 정확히 1회다. 합격 뒤에 검수를 추가하지 않는다.
- 실물 증거·focused 검증·증거 재사용(5항목이 같으면 전체 반복 금지, 재실행 예외
  5가지)·근거 파일 장소는 작업 카드와 검수 카드 템플릿에 문장으로 들어 있다.
  감독이 기억할 것은 하나다: **템플릿의 계약 문장을 지우지 않는다.**
  (같은 전체 테스트를 여러 역할이 반복하면 컴퓨터가 느려진다. 사고 요약은
  `../../kadan-super/references/scars.md`.)
- 합격 기준(보통 치명·중요 0건)은 카드 시작 전에 적는다.
- 검수 결과를 받은 뒤 감독이 할 일(덜 판 검수 의심, 수정 카드, 검수 역할 stop)은
  `card-template.md` 마지막 절에 있다.

## 배틀 오프닝

방향이 갈릴 때만 첫 라운드를 경쟁으로 시작한다.

발동 기준:

1. 조사 결과 2~3개 안 중 지휘자가 한 문단으로 승자를 못 고를 때
2. 재설계 뒤에도 방향 확신이 없을 때
3. 잘못된 방향 3라운드 비용이 병렬 2배 비용보다 클 때
4. 사용자가 직접 지시할 때

절차:

- 같은 명세의 카드 2장을 서로 다른 역할·실행기에 보낸다.
- 파일 충돌 위험이 구체적이면 참가자당 worktree 1개를 만든다.
- 둘 다 DONE이면 새 검수자가 두 안을 직접 실측한 점수표를 만든다.
- 우열이 명백하면 지휘자가 채택한다. 취향·UI/UX·제품 방향이면 사용자에게
  대화로 결정 관문을 연다. 카단 라이트 원장에는 관문 상태가 없다.
- 승자의 worktree에서 통상 티키타카를 계속한다. 패자 worktree는 승인 뒤 정리한다.

## 쪼개기와 병렬 판

- 묶음·분리는 [단순화 규칙](operating-contract.md#단순화-규칙)을 따른다. 동일 방식·승인·소유의 반복은 한 작업자·한 실행 카드에서 이어가고, 나눌 때만 실제 이유를 카드에 남긴다.
- 같은 파일, 의존 사슬, 빠듯한 사용량이면 한 작업공간에서 순차 실행한다.
- worktree는 병렬 파일 충돌 사유가 있을 때만 만든다. 병렬·편의 자체는 이유가 아니다.
- 역할 이름은 `<판>-작업자`, `<판>-검수자`처럼 판 접두사를 붙인다.
- 여러 판은 각 직속 감독에게 완료 편지를 보낸다. 감독은 응답을 끝내고 도착한 카드만 처리한다. 다른 판 완료를 기다리는 AI 루프를 만들지 않는다.
