# 작업자 생성

## Why

실행기와 작업공간을 명시해 역할을 세우고, 발령문을 삼키는 신뢰·훅 창을 사람이
확인한 뒤에만 카드를 보낸다.

작업자를 추가하기 전 현재 자원과 작업 규모는 [자원 확인](operating-contract.md#자원-확인) 기준으로 일반감독이 판단한다.

## 자동 전달 업무의 역할 수명

명시 설정한 자동 전달 업무는 블록 시작에 작업자와 독립검수자를 서로 다른 세션으로
준비하고 입력창·실제 실행 명령을 확인한다. 프로그램은 역할이나 모델을 만들거나 바꾸지 않는다.
같은 3라운드 블록에서는 둘을 유지하고, 다음 블록은 감독이 둘 다 새 세션으로 교대한다.
이전 블록의 어느 두 세션도 재사용하지 않는다. 전체 18라운드를 한 세션 수명으로 해석하지 않는다.
상세는 [자동 전달 계약](dispatch-wait.md#구현검수-자동-전달--명시-설정한-업무만)을 따른다.

## 역할 생성

1. `$KADAN_HOME/agent-runners.json`(예시: `skills/kadan-conductor/references/agent-runners.example.json`)에서 실행기를 사람이 고른다. 사용자 기본은
   codex다. 역할별 모델·강도는 `_역할별기본`(기본 프리셋 B)을 읽고, 실행 명령을 이 스킬에 복제하지 않는다.
2. 병렬 파일 충돌 사유가 구체적일 때만 worktree를 만든다.

   ```bash
   git worktree add <절대경로> -b <레포 규칙에 맞는 브랜치>
   ```

3. 아래 로티 우선 규칙으로 창 연결을 선택한 뒤 작업공간에서 역할을 시작한다.

   ```bash
   cd <작업공간>
   kadan start <판>-작업자 --profile worker --cmd "<agent-runners.json의 command>"
   ```

4. Rottie 패널 또는 열린 터미널에서 TUI 프롬프트와 실제 실행 명령을 확인한 뒤
   `kadan send`한다.

## 새 역할의 프로필

담당을 정해 **새 세션을 만들 때** 해당 프로필을 함께 지정한다. 아래 명령은 필요한 역할의 것만 골라 사용한다.
실행 명령은 위 실행기 설정에서 확인한 역할별 값을 넣는다.

| 새 역할 | 생성 명령 |
|---|---|
| 작업자 | `kadan start <판>-작업자 --profile worker --cmd "<작업자 실행 명령>"` |
| 검수자 | `kadan start <판>-검수자 --profile reviewer --cmd "<검수자 실행 명령>"` |
| 일반감독 | `kadan start <판>-감독 --profile conductor --cmd "<감독 실행 명령>"` |
| 슈퍼감독 | `kadan start <슈퍼 역할> --profile super --cmd "<슈퍼 실행 명령>"` |

기존 세션은 현재 역할과 작업을 보존한다. 프로필을 넣으려고 재시작하거나 `start --profile`로 소급 변경하지 않는다.
이름만으로 프로필을 추측하지 않는다. 프로필 없는 기존 세션에 안내가 필요하면 확인된 업무·실행·관계 또는
[정확한 역할 매핑](../../../docs/role-instructions.md#로컬-설정과-템플릿-교체)을 사용한다.
프로필은 [자동 역할 지침](../../../docs/role-instructions.md)의 선택값이며 발령·승인·소유권을 추가하지 않는다.

## worktree와 브랜치 기준

- 사용자 명시 요청 또는 구체적 checkout·파일 충돌이 있을 때만 만든다.
- 같은 판의 구현·수정·검수는 같은 worktree를 공유한다.
- 병렬·편의·분리 선호만으로 만들지 않는다.
- 병렬 작업자의 파일 범위 충돌 때문에 만들었다면 그 사유를 카드에 명시한다.
- 브랜치 이름은 대상 저장소 규칙을 따른다.
- worktree 삭제·병합은 사용자 승인 뒤에만 한다.

## worktree 작업자에게 지침이 닿게 하는 법 (2026-09-11 사용자 결정)

**Why**: worktree는 원본 저장소 폴더 밑에 있지 않은 경우가 많다. 에이전트는 현재 폴더에서 **위로만** 올라가며 지침 파일을 찾으므로, 저장소 루트의 지침이 한 줄도 안 걸릴 수 있다. 실제로 한 제품 저장소의 살아있는 worktree 76개 중 루트에 `AGENTS.md`가 있는 곳은 1개뿐이었다.

**해결은 카드에 적는 것이다.** worktree에 파일이나 링크를 심어 자동으로 읽히게 만들려 하지 마라.

- **감독은 카드의 `읽고 시작할 것` 절에 필요한 문서를 절대경로로 적는다.** 최소한 그 저장소의 공통 지침 1개를 포함한다. 양식은 [카드 템플릿](card-template.md)을 따른다.
- **공통 지침 파일 이름은 저장소마다 다르다.** `CLAUDE.md`만 있는 곳, `AGENTS.md`만 있는 곳, 둘 다 있고 한쪽이 심볼릭 링크인 곳이 섞여 있다. 카드를 쓰기 전에 `ls` 로 **실제로 있는 것을 확인하고** 그 경로를 적는다. 없는 파일을 적으면 작업자가 규칙을 못 읽고 시작한다. (2026-09-12 [kyle] 지시)
- 작업자는 그 경로를 **직접 열어 읽고** 시작한다. 상위 폴더 지침이 자동으로 걸린다고 가정하지 않는다.
- 발령 편지에도 "카드의 읽고 시작할 것 문서를 먼저 읽어라"를 한 줄 넣는다.

**하지 말 것**

- worktree 루트에 `AGENTS.md` 파일이나 링크를 만들지 마라. 외주·공용 저장소에서는 추적되지 않는 파일이 생겨 실수로 커밋될 수 있다.
- 지침 파일을 worktree로 복사하지 마라. 사본은 원본과 갈라진다.
- worktree 안쪽에 만든 연결 폴더(예: `.product-workspace`)를 "지침이 닿는다"는 근거로 쓰지 마라. **그것은 아래 방향이라 에이전트가 자동으로 읽지 않는다.** 사람이 경로를 알려줄 때만 열린다.

**판정 기준**: "파일이 열린다"와 "에이전트가 자동으로 읽는다"는 다르다. 후자를 주장하려면 그 폴더에서 위로 올라가며 지침 파일이 실제로 발견되는지로 확인한다. 확인하지 않았으면 `모름`으로 적는다.

## 시작 창 확인

- Claude/Codex는 첫 실행에 폴더 신뢰·훅·업데이트·로그인 창이 뜰 수 있다.
- TUI가 보였다는 사실과 발령을 받을 준비가 됐다는 사실은 다르다.
- 사람이 창에서 막힘을 통과하고 프롬프트가 다시 나온 것을 본 뒤에만 보낸다.
- 부팅 대기 기본 시한은 3분이다. 넘으면 문자열 대기를 계속하지 말고 창을 직접 본다.

## 기본 창 — 로티 우선 (2026-09-06 사용자 결정)

- 슈퍼감독·일반감독·작업자·검수자 모두 로티 창을 기본으로 사용한다. 포커스 보존을 이유로 처음부터 `--hidden`을 선택하지 않는다. 창 생성과 OS 창 활성화는 별개다. `activate`, `bringToFront`, `open -a` 등으로 앞으로 가져오지 않는다.
- 실행 중인 로티의 실제 실행 파일과 연결 상태를 먼저 확인한다. 연결 가능한 실행 파일의 절대경로를 `KADAN_ROTTIE_BIN`에 지정하고 `KADAN_WINDOW=rottie`로 위 표의 새 역할 생성 명령(`--profile` 포함)을 실행한다. 설치 경로나 과거 빌드 경로를 추측하지 않는다.
- 로티가 없거나 연결 불가를 확인하면 이유를 보고하고 위 새 역할 명령의 `--profile`을 유지한 채 `KADAN_WINDOW=none`과 `--hidden`으로 백그라운드에서 시작한다. 로티 설치·앱 실행·다른 앱 전환을 자동으로 시도하지 않는다. 여러 실행 파일 중 사용할 대상을 구분할 수 없으면 임의 선택하지 말고 백그라운드를 사용한다.
- `KADAN_WINDOW=rottie`인 채로 `--profile`이 있는 역할을 `--hidden`으로 시작하면 CLI가 `KADAN_HIDDEN_FORBIDDEN`으로 거부한다(2026-09-20, 감독이 작업자 8명을 숨김으로 띄워 로티 세션 목록에 안 보인 사고). 백그라운드가 필요하면 위 규칙대로 `KADAN_WINDOW=none`을 함께 지정한다.
- 창 연결 실패 뒤에는 먼저 `kadan status`와 `kadan read`로 세션 생성 여부를 확인한다. 이미 살아 있으면 그대로 사용하고 같은 역할을 중복 생성하거나 재시작하지 않는다. 모델·인증·실행기 오류는 창 연결 실패로 취급하지 않는다.
- 로티가 사용 가능해지면 같은 작업폴더에서 `KADAN_WINDOW=rottie KADAN_ROTTIE_BIN=<확인한 절대경로> kadan attach <역할>`로 기존 세션을 연결한다. 새 에이전트를 만들지 않는다.
- 로티 창 생성 응답만으로 성공 처리하지 않는다. 실제 tmux 클라이언트 연결과 `kadan read` 화면을 확인하고, 창 연결/백그라운드 상태를 구분해 보고한다.

## 세션이 통째로 사라졌을 때 — 기억째 되살리기 (2026-09-12 사용자 확인)

**Why**: 맥 재부팅이나 tmux 서버 종료로 역할이 한 번에 전부 사라진다. 2026-09-12에 27개가
날아갔다. 카드·원장·우편은 파일이라 남지만 **대화 기억은 다시 세운다고 돌아오지 않는다.**
그냥 `kadan start`를 치면 맥락 없는 새 에이전트가 설 뿐이다.

먼저 `kadan status`로 확인한다. `카단 구획(kadan)에 세션 없음`이면 바닥이 통째로 죽은 것이다.
이때 `kadan send`는 전달되지 않는다. `guardedSend`가 세션 생존을 먼저 검사해
`KADAN_SESSION_MISSING`을 던지고 **원장에도 남기지 않는다.** 작업자의 완료 통지도,
watch 알림도 조용히 사라진다.

### 되살리는 법

```bash
node <저장소>/scripts/recover-sessions.mjs --since <YYYY-MM-DD>
```

읽기 전용이며 아무것도 실행하지 않는다. 역할마다 원래 실행 명령·작업폴더와 함께
복구 줄을 출력한다.

```
복구> cd <작업폴더> && kadan start "<역할>" --cmd "codex resume <대화id>"
```

사람이 보고 **필요한 역할만** 골라 친다. 이미 끝난 작업자까지 전부 되살릴 이유는 없다.
맥락이 쌓인 감독과 진행 중이던 작업자만 살린다. 되살린 뒤 `kadan status`로 `PID일치`를 본다.

### 원리

원장 `start` 기록(역할·실행 명령·모델·작업폴더·시작시각)과 codex 대화 파일
(`~/.codex/sessions/<연>/<월>/<일>/rollout-*.jsonl`) 첫 줄 `session_meta`(대화 id·작업폴더·시작시각)를
**작업폴더가 같고 시작시각이 가까운 것**으로 맞춘다. 실측 시차는 -1.3초 ~ -2.8초였다.
원장은 2026-09-07부터 `~/.kadan/kadan.sqlite`의 `events` 표에 있다. 그 이전은 `ledger.jsonl`이다.
둘 다 봐야 한다.

### 한계 — 그대로 인정한다

- 같은 폴더에서 몇 초 간격으로 띄운 역할은 구분되지 않는다. `~/.kadan/out/`의 화면
  기록으로 사람이 대조한다. 추측으로 고르지 않는다.
- 기억이 돌아와도 **하던 일이 이어지는 것은 아니다.** 반쯤 고친 파일이나 끊긴 명령은
  따로 확인한다.
- 대화 파일을 못 찾으면 기억 없이 새로 세운다. 그때는 인계 문서를 읽혀서 시작한다.

### 감독 자신이 되살아나야 할 때

자기 대화 id는 `ps -o command -p $PPID`에 `codex resume <id>` 또는 실행 명령으로 보인다.
한 번 `--cmd "codex resume <id>"`로 세운 역할은 그 명령이 원장에 남으므로,
다음부터는 맞추기 과정 없이 바로 복구된다.

검증 근거: 재부팅 직전 32개 역할 중 27개가 유일하게 맞았고, 정답을 아는 한 감독 세션
사례로 검산했다(2026-09-12, 관리자 작업장 기록).
