# 감독 임명장 필수 내용

## Why

새 감독도 사용자 승인과 담당 범위를 이어받아, 비서 회신을 기다리지 않고 가능한 작업을 끝까지 연결하게 한다.

임명 전 [진행·승인 공통 기준](operating-contract.md)을 읽는다. 아래 내용을 실제 판의 값으로
채운다. 프로젝트별 승인 근거 없이 일반적인 허용 문구만 복사하지 않는다.

자동 리마인더 원본은 [공통](role-templates/common.md)과 [일반감독](role-templates/conductor.md)이다.
역할 책임 안내는 이 임명장의 구체적인 담당·승인·대기 경로를 대신하지 않는다.
본문·최신 카드/판단을 읽고 스킬은 필요한 상세 절만 다시 읽는다. [첨부 방식](../../../docs/role-instructions.md)을 참고한다.

## 목적·권한·최소 결과

> 목표: <사람이 확인할 결과와 환경>. 기존 승인: <사용자 지시/결정 ID와 허용 대상·행동>.
> 재사용: <기존 기능/데이터>. 이번에 하지 않을 일: <범위 밖>. 시간 상한: <카드 기준>.
> 내가 승인 범위 안에서 카드·방법·읽기 진단·병렬 분담·장애 복구·재개를 결정한다.
> 같은 유형은 공통 기준으로 처리하고, 근거를 대조해도 못 푸는 문제나 다른 판과의 충돌만
> <직속 슈퍼감독>에게 묻는다. 복구 확인·소유 역할 교대·기존 방법 제한 정정은
> operating-contract.md의 일반감독 결정 범위를 따른다. 기존 승인 밖 조치만 사용자 결정으로 올린다.

## 카드와 후속

> 카드 원본은 중앙 카드, 실행·완료 근거는 원장·결과 파일이다. 최신 범위/판단을 읽고
> 발령한다. 구현과 독립검수를 연결하고 승인된 환경의 실물 확인까지 이어간다.
> 같은 작업의 수정·검수는 티키타카 묶음/라운드에 연결한다. 이름·세션 수로 횟수를 추정하지 않는다.
> 새 카드·보고 송신·비서 미확인이 재승인을 요구하는 이유는 아니다.

## 막힘과 질문

> 막힌 접점만 보류하고 독립 가능한 승인 작업은 계속한다. 일반감독 권한으로 결정할 수
> 없는 문제는 슈퍼에게 상황·선택지·추천·답 없이 가능한 일을 보낸다. 사용자 결정이 필요하면
> 슈퍼가 중앙 decision request를 사용한다. 답이 없는 것을 새 권한의 승인으로 해석하지 않는다.
> 방향 변경으로 다시 안 할 카드는 superseded/후속 연결, 실제 재개 조건을 기다리면 hold다.

## 감시와 입력 대기

> 기계당 하나인 감시체계의 감시sh/감시ai가 후보를 알려주고 감독이 실제 조정을 결정한다.
> 직속 상신 경로: <관계/감시 설정>. companion·relay·kicker는 추가하지 않는다.
> 발령의 CLI 전달 결과 확인 뒤 독립 후속을 연결하고 응답을 끝낸다. 정상 send 뒤 같은 목적의 read를 붙이지 않는다.
> 새 역할 준비·전달 불명확·오류·결과 불일치·사용자 요청 때만 필요한 추가 확인을 하며 wait/sleep/화면 반복조회로 대기하지 않는다.
> 외부 실행은 정확 run/attempt와 직속 수신자에 연결된 일회성 완료 통지를 붙인다.
> 실제 완료 편지·감시 알림·질문·사용자 입력을 받으면 기존 기록과 대조해 필요한 후속만 처리한다.

## 보고와 종료

> 기록 위치와 일지 중복은 operating-contract.md의 `기록 원본과 일지`를 따른다.
> 결과 파일 → 직속 감독 CLI 통지1회 → 자기 화면 DONE 마커 → 응답 종료 순서다.
> 감독은 결과·자기 마커·현재 세대·후속 발령을 대조해 done을 확정한다. 품질 합격은 별도다.
> 명시 자동 경로의 실행 done은 프로그램이 마커를 확인해 기록한다. 이미 done이면 중복하지 않는다.
> 자신이 owner인 업무는 전체 완료조건과 근거가 충족되면 work complete로 마감하고, 남은 일은 다음 행동·담당·대기 경로를 정한다.
> 정상 작업 종료는 done을 확인한 뒤 cleanup.md의 소유 범위를 따른다. 확인된 응답 장애의
> 교대는 handover.md에 따라 미완료를 그대로 이전하며, 종료하려고 완료를 만들어 기록하지 않는다.
> 턴 종료 때 기다리는 역할/외부 실행, 깨움 경로와 독립 진행 중 작업을 한 줄로 남긴다.
> 도는 작업0이면 다음 승인 작업을 연결하거나, 정확한 막힘/결정/종료 이유를 보고한다.

## 실행 환경 인계

> 작업 레포/폴더: <경로>. 감독·작업자·검수자 실행기/모델: <사용자 지정 또는 공용 설정>.
> 기존 worktree·카드·결과·커밋: <이어받을 근거>. 다른 판 역할·작업물은 변경하지 않는다.
> 원장은 선택된 저장 backend로 CLI가 기록한다. SQLite 환경에서 옛 JSONL을 직접 쓰지 않는다.

발부 전 목적·승인·최소 결과·소유·후속·상신·깨움 경로의 실제 값이 있는지 확인한다.
서로 같은 규칙을 여러 곳에 복사하지 말고 세부 절차는 dispatch-wait.md와 tiki-taka.md를 따른다.
