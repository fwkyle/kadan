# 중앙 카드

## Why

미배정 카드와 승인·질문·답변을 한 곳에서 관리하고, 세션 생존을 작업 진행으로 착각하지 않는다.

- 새 실행 카드는 `kadan card create <레포>/<ID> --repo-path <절대경로> --source <작성한카드>`로 중앙 등록한다. 카드 틀의 계약은 유지한다. 기존 파일 경로가 필요하면 `kadan card link <키>`로 중앙 원본에 연결한다. 이후 카드 내용은 중앙 원본을 고친다.
- 카드 본문만 읽지 말고 `kadan card show <키>`의 최신 승인 범위·상태·질문/답변을 함께 읽는다. 전체 목록은 `kadan card list`, 카드/판/실행 대조는 `kadan tree`다.
- 방법 선택·제한된 복구·소유 역할 교대의 판단자는 [일반감독의 결정 범위](operating-contract.md#일반감독의-결정-범위)를 따른다. 운영상 방법 제한을 바꾸면 기존 카드의 최신 decision/scope에 이유·적용 범위를 정정하고 원이력은 보존한다. 기존 실행을 새 카드로 만들거나 사용자 직접 금지를 덮지 않는다.
- 초안과 TODO 아이디어는 발령하지 않는다. 새 카드라도 기존 목적·환경·대상·행동 승인이 충분하면 재승인 없이 그 근거를 연결한다. 사용자 결정이 확인되면 그 범위만 scope에 적고 `card update <키> --revision N --status ready --scope <범위> --note <승인근거>`로 남긴다. 스킬이나 상위 역할이라는 이유로 승인을 넓히지 않는다.
- 판을 열 때는 최신 ready 카드를 읽어 우선순위·의존성·자원을 판단한다. 현재 진행 중인 판이 없고 승인 범위가 충분하면 일반감독을 통해 판을 연다. 판은 plan으로 기록하고, 발령 전에 `card update <키> --revision N --status assigned --board <판> --role <수신자> --note <판단>`을 기록한 뒤 [발령 절차](dispatch-wait.md)를 따른다. 정상 send 뒤 같은 목적의 read를 반복하지 않는다.
- 같은 ID가 여러 레포에 있으면 send가 거부되므로 새 카드 ID는 충돌하지 않게 정한다. 재검수 등 다른 역할에 넘길 때도 배정을 바꾼다. 이전 역할 실행·결과는 원장에 남는다.
- 일반감독·슈퍼의 질문/판단은 `card note <키> --revision N --kind question|decision --note <내용>`, 사용자 답변은 answer로 남긴다. 웹 저장은 우편 배달이나 자동 재개가 아니다. 다음 정상 입력에서 최신 카드를 읽는다. 이 목록을 보려고 AI를 주기적으로 깨우지 않는다.
- 담당 역할은 작업 시작/외부 결과 대기 등 상태 전이마다 `card progress <키> --revision N --activity running|waiting --note <근거>`로 1회 기록한다. 이는 상태 기록이며 `send`가 아니므로 상위에 별도 편지를 붙이지 않는다. 편지의 필요 여부는 [진행 기록과 상위 통지](operating-contract.md#진행-기록과-상위-통지)를 따른다. 진행 표시 유지용 반복 조회·타이머는 금지한다. 작업 중·결과 대기는 시간 경과만으로 만료되지 않으며 기록 시각을 별도로 표시한다. 이것만으로 재시작하지 않는다.
- 재개 조건이 있는 보류는 hold, 방향 변경으로 다시 하지 않을 작업은 superseded와 replacedBy 후속 카드, 확인된 카드 범위 완료는 done으로 이유·근거를 기록한다. 실제 실행 DONE는 원래의 `kadan done`/완료마커 계약을 지킨다. card done은 제품 전체 완료나 운영 배포 완료가 아니다.
- 명령과 복구 상세는 [카드 중앙 관리](../../../docs/card-center.md)가 기준이다. 중앙 데이터는 `KADAN_HOME/cards`이며 코드 레포·원격으로 자동 게시하지 않는다.

## 사용자 결정 요청 전용 경로

- 내부 질문/실패 보고는 card note로 남기고 직속 감독이 처리한다. 이것은 사용자 답변 대기 표시가 아니다.
- 슈퍼감독이 기존 결정과 조사로 해결할 수 없는 사항만 `KADAN_ROLE=<슈퍼감독> kadan decision request <카드키> --question <쉬운질문> --option <선택1> --option <선택2> --recommend <추천선택> --reason <이유와판단필요성>`로 올린다. 선택지는2~4개, 대표 사례와 영향은 질문/이유에 적는다. 절차실패·압축 작업보고를 질문으로 올리지 않는다.
- 결정 목록은 `kadan decision list --status open`, 상세는 `kadan decision show <ID>`. 사용자는 웹 또는 `decision answer <ID> --revision N --text <답변> [--choice <선택>]`로 답한다. 에이전트가 사용자 답변을 대신 쓰지 않는다.
- 답변은 저장 뒤 요청 슈퍼에게 CLI 통지를 한 번 시도한다. 수신자는 decision show로 원문을 확인하고 관련 카드에 승인/범위와 후속을 반영한다. 질문/답변이 있다는 것만으로 카드 발령·운영 배포 권한을 확대하지 않는다. 답변 원문은 결정 기록 하나이며 카드에는 필요하면 그 ID를 참조한다.
- 같은 답변 재호출은 중복 통지하지 않는다. 전달 실패 또는 불확실은 저장된 delivery에서 확인하고 상태 확인 없이 재전송하지 않는다. 오래된 요청은 요청자 또는 사람이 `decision cancel <ID> --revision N --reason <사유>`로 취소한다. 전체 절차는 [사용자 결정 요청](../../../docs/decisions.md)이 기준이다.

## 판의 감시 근거 조회

- 비서·슈퍼감독·일반감독은 현황 확인 시 `kadan tree`의 `monitoring`을 읽는다. 대시보드와 같은 계산이며 별도 수기 집계나 화면 문구를 원본 설정으로 만들지 않는다.
- `process`는 감시기 생존, `configuration`은 현재 직속 관계 파일과 감시기가 읽은 지문의 일치다. `boards`는 실제 발령된 미완료 작업자·검수자 감시 대상과 상위 수신 경로를 보여준다. 감독은 수신자이며 감시 대상 수에 더하지 않는다. 대상이 없으면 `not-required`, 대상의 누락은 `missingRoles`를 확인한다. 상세 선정 기준은 아래 감시 안내 한 곳을 따른다.
- `cycle.state=unknown`이면 감시 주기 정상은 모름이다. 프로세스 실행 중/설정 일치를 주기 정상·알림 처리 완료로 확대하지 않는다. 미등록 역할은 기존 route 경로가 있을 수 있어 감시 없음으로 단정하지 않는다.
- 원본은 관계 파일·원장·프로세스이며 JSON의 `checkedAt` 시점으로 보고한다. 비서는 기존 전달 절차를 따르고 조회만으로 재시작·관계 수정·발령을 하지 않는다. 읽기용 AI 폴링을 만들지 않는다.
- 구현의 상세 기준은 [감시 기준](../../../docs/watch-overview.md)에 있다. CLI와 대시보드에 필드가 없으면 구버전/미수집으로 보고하며 정상으로 간주하지 않는다.

카드의 최소 결과·진행/보류/결정 경계는 [공통 기준](operating-contract.md)을 따른다. 작업별 수정·검수는 `rallyId/rallyRound/rallyStep`으로 연결하며 관련 조사는 round0이다. 상세는 [왕복 안내](../../../docs/rallies.md).
