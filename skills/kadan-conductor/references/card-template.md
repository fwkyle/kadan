# 카드 템플릿 — 작업 카드와 검수 카드

## Why

작업자·검수자는 스킬을 읽지 않는다. 카드만 읽는다. 규칙이 스킬에만 있으면 감독이 카드에
옮겨 적다가 빠뜨린다. 그래서 계약 문장은 여기 미리 박아 두고, 감독은 복사해서 `<…>` 칸만
채운다. **계약 문장은 지우지 않는다.** 줄이고 싶으면 이 파일을 고친다 (2026-09-02 card-40).

- 카드 파일: `docs/daily/<날짜>/card-<id>.md`. 파일명이 카드 id다.
- 결과 파일: `docs/daily/<날짜>/card-<id>-result.md`.
- 발령 지문에는 카드 경로와 마커 **형식**만 준다. 완성된 마커 문자열은 지문에 넣지 않는다.

카드의 승인·대기 판단은 [진행·승인 공통 기준](operating-contract.md)을 따른다.

## 자동 전달로 등록할 때

원본 작업·검수 카드의 범위·검증·증거 계약은 유지한다. `work auto-configure`에 원본 두 카드를
참조로 지정하며, 자동 생성 실행 카드가 현재 실행ID와 직전 결과 원문 경로를 전달한다.
그 실행 카드의 통지 계약이 아래 수동 완료 편지 절을 대신한다. 결과 파일 완성 →
`work auto-report <업무키> --execution <현재실행키> --outcome <명시판정> --result-file <절대경로>` →
자기 화면의 현재 실행 DONE 순서다. 정상 중간 편지를 감독에게 중복 발송하지 않는다.
구현·수정은 implemented/exception, 검수는 pass/changes/exception을 쓰고 실행 ok/failed와 구별한다.
수정 요구가 승인 범위 밖이면 changes가 아니라 exception으로 보고한다.
기존 결과 근거는 그대로 남기며, 명령 상세는 [자동 전달 계약](dispatch-wait.md#구현검수-자동-전달--명시-설정한-업무만)을 따른다.

## 작업 카드

````markdown
# card-<id> — <제목>

## Why
<누가, 무엇이 불편한지, 무엇을 더 쉽게 하는지 한 문장>

## 읽고 시작할 것
<작업자가 일을 시작하기 전에 직접 열어 읽을 문서를 절대경로로 적는다. 최소 저장소 지침 1개를 포함한다.>
- <예: /절대경로/저장소/AGENTS.md 또는 CLAUDE.md — 저장소 공통 규칙. **둘 중 실제로 있는 것을 확인해 적는다.** 한쪽만 있는 저장소가 많고, 둘 다 있으면 한쪽이 다른 쪽의 심볼릭 링크인 경우가 흔하다. 없는 파일을 적으면 작업자가 규칙을 못 읽고 시작한다.>
- <예: /절대경로/저장소/.claude/skills/<스킬>/SKILL.md — 이 작업에 해당하는 스킬>
- <예: docs/daily/<전날>/<도구>.md — 직전 맥락>

**작업자는 상위 폴더의 지침이 자동으로 걸린다고 가정하지 마라.** worktree는 저장소 루트 밑이 아닌 경우가 많아
에이전트가 위로 올라가며 찾는 지침 파일이 하나도 안 걸릴 수 있다. 그래서 필요한 문서는 감독이 이 절에
경로로 적고, 작업자는 그 경로를 직접 열어 읽는다. 읽지 않고 시작하면 절차 위반이다.

## 시작 기록

카드를 읽고 실제 작업을 시작하기 전에 아래를 **한 번** 실행해 시작을 원장에 남긴다.

```bash
kadan card note <저장소/카드id> --revision <현재revision> --kind progress --note "시작: <자기 역할> / 읽은 문서 <n>건 / 첫 단계 <무엇>"
```

이는 상태 기록이며 `send`가 아니다. 감독에게 별도 편지를 보내지 않는다. 시작 기록 없이 진행한 카드는
절차 위반으로 본다. 상세는 [진행·승인 공통 기준](operating-contract.md)의 `진행은 기록한다`를 따른다.

## 이번에 확인할 결과
- 대상 환경과 대표 사례: <예: Preview에서 태그명 제품을 검색해 상세·이미지 확인>
- 기존에 재사용할 것: <등록/복제/검색 등>
- 이번에 하지 않을 일: <첫 확인에 불필요한 전면 정리/별도 체계 등>
- 승인 근거와 허용 행동: <사용자 지시/결정 ID, 대상·환경·행동>
- 카드 시간 상한과 후속 수신자: <시간>, <직속 감독>

## 범위
- 수정 대상: <소유 파일 목록·허용 데이터 범위>
- 작업공간: <절대경로> (worktree면 브랜치 이름)
- 무게: <LIGHT | HEAVY> — <이유 한 줄>

## 단순화 계약
사용자 요구 밖 조건을 붙이지 말고 실제 참조·권한·데이터 무결성을 보존하며 기존 기능을 최소로 재사용한다.
승인 안의 작은 수정·절차 축소·필수조건 보존 수정은 재질문 없이 계속한다. 승인 밖 조치는 직속 감독에게
기존 질문 경로로 올리고 승인 후 종속 작업을 한다. 동일 방식·승인·소유의 반복은 한 작업자가 이 카드에서
이어가며 항목별 성공/실패/미착수·재개 위치를 결과 파일에 즉시 기록한다. 명시 시간 상한은 자동 연장하지 않는다.
묶음·분리와 검수 범위의 공통 원문은 스킬 저장소의 `skills/kadan-conductor/references/operating-contract.md`다.
이미 정해진 공통 기준은 같은 유형의 다음 항목에도 적용한다. 의미·조건이 다른 예외만 직속 감독에게
질문한다. 직속 일반감독은 승인 안의 방법·읽기 진단·제한된 복구 확인·소유 역할의 장애 교대를 결정한다.
작업자가 스스로 복구 권한을 넓히지는 않는다. `기존 역할 유지` 같은 운영상 방법 제한을 적을 때는
적용 대상·이유·끝나는 조건을 함께 적고, 사용자 금지와 섞지 않는다. 구체적 절차는 위 공통 원문을 따른다.

## 진행 기록

카단에 연결된 이 카드의 진행 기록은 스킬 저장소의 `skills/kadan-conductor/references/operating-contract.md` 중
`기록 원본과 일지`를 따른다. 지정 결과와 원장을 데일리에 복사하지 않는다. 단순 대화·알림 수신만으로
일지나 커밋을 만들지 않으며, 아래 검수 근거·완료 통지·마커는 그대로 남긴다.

**착수하면 곧바로 이 카드에 진행 기록을 1회 남긴다.** 결과를 기다렸다가 한꺼번에 적지 않는다.

```
kadan card note <저장소/카드id> --revision <현재 revision> --kind progress --note "착수: <지금 하는 일 한 줄>"
```

감시체계는 발령 5분 뒤 진행 기록이 없으면 "시작 보고 누락"으로 본다. 실제로는 일하고 있는데
기록만 없어서 울리는 알림이 반복되고, 직속 감독이 매번 화면을 대조해 수동으로 보완해야 한다.
이 한 줄이 그 왕복을 없앤다. 정상 ACK 편지와는 다르며, 편지는 여전히 보내지 않는다.

## 비밀값을 쓰는 법 (2026-09-12 실사고)

카드가 계정·열쇠 파일 경로를 주면 작업자는 **값을 화면에 찍지 않고** 써야 한다.
같은 날 작업자와 검수자가 연달아 암호 3종을 도구 출력에 노출했다. git으로는 새지 않았지만
실행 기록과 압축 기록에 남았고 지우기 어렵다.

카드의 `실행 정보` 절에 아래를 그대로 넣는다.

> 계정 파일의 값을 화면에 찍지 마라. `set -a; . <env파일>; set +a` 로 셸에 불러와 변수로만 넘긴다.
> `cat`·`echo`·`head`·`grep` 으로 그 파일 내용을 출력하지 말고, 명령을 되울리는 `set -x` 도 쓰지 마라.
> 값이 실수로 출력되면 그 사실만 보고한다. 지우거나 바꾸는 일은 사용자 결정이다.

## 금지
- 위 범위 밖 파일 수정 금지. 커밋은 감독이 맡는다. push·배포·DB 쓰기 등은 위 승인 근거와
  허용 행동에 명시된 범위에서만 실행한다. 명시되지 않은 행동은 금지다. `git add -A` 금지.
- 작업 중에는 지금 고치는 파일의 focused 테스트만 돌린다. 전체 테스트·타입 검사·빌드는
  작업이 끝난 뒤 각 1회만.
- 원인을 모르는 실패에 재시도하지 않는다. 실패·미확인·영향을 결과 파일에 즉시 기록하고 해당 항목만
  보류한다. 새 근거로 직속 일반감독이 정한 복구 확인은 최신 카드의 정확 범위·횟수·중단 조건에서만
  수행한다. 미확인을 정상으로 간주하지 않는다. 영향 없는 승인 작업은 계속하며, 분리할 수 없으면 전체
  중지 근거를 적는다. 허용 범위·시간 안의 가능한 작업을 마친 뒤 카드 합격 기준에 미달하면 failed로
  끝낸다. 아래 완료 통지·마커 규칙은 그대로 따른다.
- 삭제는 `.trash/` 이동. 실제 삭제는 하지 않는다.

## 합격 기준
- <정상 경로 1개>
- <가장 위험한 엣지 1개>
- <HEAVY면 회귀 1개>
- 사용자 눈에 보이는 작업이면 실물 증거 1개: <실제 curl 응답 | CLI 실행 화면 | 브라우저 화면 |
  GUI 조작 화면> 중 하나를 결과 파일에 붙인다. 코드 추적과 단위 테스트 통과만으로는 완료가 아니다.

## 결과 파일
`docs/daily/<날짜>/card-<id>-result.md`에 다음 순서로 적는다.
1. 무엇을 바꿨는지 — 파일:줄
2. 실행한 검증과 결과 원문
3. 검증 증거 5항목 (검수자가 전체 테스트를 다시 돌릴지 정할 때 쓴다)
   - 기준 commit SHA 또는 미커밋 변경 지문 (`git rev-parse HEAD`, `git diff --stat`)
   - 테스트에 영향을 주는 설정·환경 (런타임 버전, env, 바닥)
   - 실행 명령과 테스트 선택 범위
   - 성공 개수·실패 개수·종료 코드
   - 결과가 나온 뒤 관련 파일이 바뀌지 않았다는 확인
4. 막힌 것·못 한 것·범위 밖에서 발견한 것

## 완료 통지 수신자
직속 감독: `<직속 감독 역할>`. 결과 파일을 완성한 뒤 자기 역할을 발신자로 하여
`kadan send <직속 감독 역할> "완료 통지: <자기 역할> / <카드id> / <ok 또는 failed> / 결과: <결과 절대경로>"`
를 한 번 실행한다. `--task` 및 완성된 DONE 마커는 편지에 넣지 않는다.
그 뒤 아래 마커를 자기 화면에 출력하고 응답을 끝낸다. 발송 실패는 결과에 남기고 반복 재전송하지 않는다.

## 완료
결과 파일을 다 쓴 뒤 마지막 줄에 `KADAN:DONE <카드id> <ok 또는 failed>` 형식으로 출력한다.
카드 id는 `card-<id>`. 절차를 어겼으면 기능이 됐어도 failed다.
터미널에는 결과 파일 경로를 포함한 한 줄 요약만 남긴다.
````

## 검수 카드

````markdown
# card-<id>-review — card-<id> 검수

## 계약
너는 검수 전용이다. 어떤 파일도 수정하지 마라. 심각도(치명/중요/사소)별 발견 목록과 근거
파일:줄만 보고하라. 작업자의 보고·기존 로그·증거를 불신하고 직접 실행·실측으로 검증하라.
서브에이전트를 쓰면 그 프롬프트에도 이 읽기 전용·수정 금지 계약을 그대로 복사해 전달하라.
판정과 필수 근거를 썼으면 사소한 문장 다듬기로 완료를 늦추지 마라. 결과 파일의 사소한
오탈자는 보고에 남기고 즉시 마커를 출력하라.
착수하면 곧바로 이 검수 카드에 진행 기록을 1회 남겨라:
`kadan card note <저장소/카드id> --revision <현재 revision> --kind progress --note "착수: <검수 범위 한 줄>"`.
이미 같은 카드에 running 기록이 있으면 중복해서 남기지 마라.

## 대상
- 카드: `<카드 경로>` / 결과 파일: `<결과 파일 경로>`
- 변경 파일: <목록>
- 검수 범위: <첫 검수 = 전체 | 재검수 = 수정 지점 + 인접 회귀 + 발견 재현>

## 검증 범위 — 증거 재사용 판정
결과 파일의 검증 증거 5항목(SHA 또는 변경 지문·환경·실행 명령과 범위·성공/실패 수와 종료
코드·파일 불변 확인)이 지금과 **모두 같으면** 전체 테스트를 반복하지 말고 위험 구간의
focused 테스트와 결과 원문 대조만 하라. 하나라도 다르거나, 기존 실행이 0개 선택·timeout·
부분 실행·환경 오류였거나, focused 결과가 기존 결과와 충돌하면 전체를 다시 돌리고 그
이유를 결과 파일에 적어라.

## 합격 기준
- 치명·중요 0건
- <작업 카드의 합격 기준을 그대로 옮긴다>
- 실물 증거가 요구된 작업이면 결과 파일의 증거를 직접 재현한다.

## 근거 파일 장소
근거·로그·스크린샷은 아래 결과 파일에만 쓴다. 검수 대상 작업공간(worktree) 안에는 어떤
파일도 만들거나 고치지 마라. 이미 있는 낯선 파일은 지우지 말고 "범위 밖 산출물"로 보고하라.

## 결과 파일
`docs/daily/<날짜>/card-<id>-review-result.md`: 판정(합격 | 불합격) / 발견 목록(심각도·
파일:줄·재현 방법) / 실행한 것과 결과 원문 / 재사용 판정과 이유 / 걸린 시간
````

## 감독이 카드를 받은 뒤

- 검수 시간만으로 부족/충분을 판단하지 않는다. 결과의 실제 실행 범위와 재사용 근거를 대조하고
  누락이 있으면 해당 누락만 보완한다. 빠르게 끝났다는 이유로 동일 검수를 다시 발령하지 않는다.
- 발견이 있으면 검수자가 고치지 않는다. 발견 전문을 인용한 수정 카드를 작업자에게 보낸다.
- **`stop` 전에 `kadan done <역할> <카드id> <ok|failed>`로 원장에 확정한다.** 화면은 `stop`과
  함께 사라지고, 그 뒤엔 아무도 결과를 증언할 수 없다 (사고 09-01 미아 6건).
- 역할 보존·종료는 `cleanup.md`를 따른다. 검수 종료만으로 다른 카드의 역할을 종료하지 않는다.
