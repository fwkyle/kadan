# 작업·우편 원장 계약

## Why

사용자가 작업의 진행·완료와 역할 사이의 질문·답장을 따로 확인하고, 누가 답해야 하는지 놓치지 않도록 원장을 작업·우편·시스템으로 나누고 기존 우편함을 모든 역할로 넓힌다.

## 원장 구분

전체 구조·수신자 ack·미확인 우편 감시·인계 정책은 [구조 기준](architecture.md)을 따른다. 이 문서는 구현된 저장·조회 계약을 설명한다.

| 영역 | 기록하는 것 | 저장 스트림 |
| --- | --- | --- |
| 작업 | 업무·실행 카드의 상태 이력, 계획·발령·완료 사건 | 기존 `works/.../events.jsonl`, `cards/.../events.jsonl` 및 `tasks/events.jsonl` |
| 우편 | 보낸 편지, 읽음 확인, 질문 취소 | `mail/events.jsonl` |
| 시스템 | 세션 시작·종료, 감시 등 운영 사건 | `system/events.jsonl` |

SQLite에서는 같은 `kadan.sqlite` 안의 스트림을 구분한다. 별도 DB를 세 개 만드는 것이 아니다. JSONL 방식에서는 같은 이름의 파일에 기록한다. 기존 `ledger.jsonl` 이력은 수정·이동·재정렬하지 않는다. 우편 본문은 기존 `mail/<지문>.txt`에 둔다.

`tasks/events.jsonl`은 작업 영역의 발령·완료 사건 원장이다. 기존 업무·카드의 상태 이력을 대체하지 않으며, 업무·실행과 별개인 새로운 작업 개념도 아니다. [업무 카드와 실행](business-work.md)의 완료 기준은 그대로다.

## 기록과 조회 계약

- `send --task`는 우편의 `send`와 작업의 `dispatch`를 같은 `mailId`·`dispatchId`로 연결한다. 일반 편지의 업무·실행 연결(`--work`, `--execution`)은 작업 발령이 아니다.
- `readTaskLedger(home)`는 계획·발령·완료 사건, `readSystemLedger(home)`는 시스템 사건을 반환한다. 과거 겸용 `send`는 작업 조회에서 `dispatch`로 읽으며 과거 원문은 바꾸지 않는다.
- `readMailLedger(home)`는 우편 사건에 더해 책임 계산용 확정 `handover/transferred`와 `completionMailId`가 있는 `done`을 원래 저장 순서로 반환한다. 완료 근거는 짧은 실행 ID와 정식 주소가 섞인 자동 결과 우편도 원본 발령에 대한 유효한 최종 답변인지 검증하는 데 사용한다. `done`은 작업 원장, 확정 인계는 시스템 원장에 각각 한 번만 저장하며 우편 원장에 사본을 저장하지 않는다.
- `readLedger(home)`는 기존 호출자를 위한 통합 호환 조회다. 작업 발령은 기존 `send` 형태로 한 번 노출하며 새 `dispatch`를 중복 노출하지 않는다. 원장별 건수를 더한 값은 호환 조회 건수와 다를 수 있다.
- 과거 기록은 원래 순서, 신규 기록은 전체 저장 순번으로 읽는다. 사건 시각을 기준으로 원장을 다시 정렬하지 않는다. 화면의 최신순은 이 순서의 역순이다.
- 완료 중복 처리는 기존 조회 규칙을 유지하며 원시 사건은 보존한다. 분리 조회는 과거 이력을 이미 새 저장소로 옮겼다는 뜻이 아니다.

## 모든 역할의 우편함과 질문

공통 `Mailbox(home, role)`과 `mailboxLetters(entries, role)`을 사용한다. `mailboxLetters`의 역할을 생략하면 모든 역할의 편지를 보여준다. 역할 선택·조회·질문·답장 명령은 [역할 우편함 안내](secretary-mailbox.md)를 따른다.

질문 상태는 `waiting`·`answered`·`cancelled`이며, 질문이 아닌 편지는 `not-requested`다. 읽음과 중간 답장은 `waiting`을 유지한다. 현재 수신 책임자의 최종 답변 또는 현재 발신 책임자의 취소로 대기를 끝낸다. 사용자 권한에 의한 처리도 공통 우편함의 검증을 따른다. 읽음·답변·실행 DONE·업무 완료의 의미는 [상태 구분](architecture.md#서로-대신할-수-없는-상태)을 따른다.

터미널 전달 뒤 최종 답변·취소가 경합하면 실제 전달 사실은 보존하지만 그 답장이 질문을 끝내지 못할 수 있다. `replyFinalRejected: true`를 남기고 먼저 확정된 질문 상태를 유지한다.

신규 `mailId`가 있는 편지는 읽음 미확인에서 시작한다. 읽음 기록이 없는 옛 전달 중 `mailId`도 없는 것은 읽음 상태를 모름으로 표시한다. `read`와 웹 본문 펼치기는 조회만 하고 자동으로 읽음 처리하지 않는다.

읽음은 수신자의 명시적인 `mail-read` 사건으로 기록한다. 전송 성공·최종 답장·DONE도 자동 읽음으로 취급하지 않는다. 사용자 수동 확인 예외와 알림 정책은 [구조 기준](architecture.md#읽음-확인과-미확인-우편-알림)을 따른다.

## 기존 화면에서 확인하기

화면 사용법은 [역할 우편함 안내](secretary-mailbox.md#화면과-오류)를 따른다. 화면의 조회 계약은 다음과 같다.

- 역할 필터는 현재 수신 책임자(`currentRecipient`)와 발신 책임자(`currentSender`)를 사용한다. 원래 `role`·`by`도 표시하며 현재 필드가 비어 있으면 원래 값을 사용한다.
- 업무·실행 인박스는 명시한 주소나 고유한 답장 연결만 따라가며 본문으로 연결을 추측하지 않는다. 운영 흐름도 같은 우편의 읽음·최종 답변·취소 상태를 사용한다.
- 원문 주소는 과거 `ledger:legacy:<순번>`과 신규 `ledger:new:<전체순번>`을 구분한다. 옛 `ledger:<순번>` 주소는 과거 이력만 가리킨다.
- 조회만으로 편지 발송·읽음 기록·완료 처리를 하지 않는다. 원장이 손상됐거나 읽을 수 없으면 `0건` 대신 `모름`을 표시한다.

## 완료 결과 통지

코어가 실행의 `done`을 기록할 때 원본 발령의 발신자에게 결과 우편을 한 번 저장한다. 수신자는 원본 발신자, 발신자는 완료 역할이며 `replyTo`로 원본 우편을 연결한다. 이 우편은 `transport: mailbox`, `mailKind: report`, `completion: true`, `systemGenerated: task-completion`, `notificationOnly: true`, `replyFinal: true`로 구분한다.

결과 우편에는 발령을 뜻하는 `taskId`를 넣지 않는다. `executionKey`·`workKey`·`replyTo`로 연결하고, 등록되지 않은 과거 실행은 `completionTaskId`와 본문에 대상을 남긴다. 화면에는 **실행 결과 통지**로 표시한다. 원본 발신자를 알 수 없는 경우 추측해서 받는 역할을 만들지 않는다.

자동 결과 우편은 **우편함 저장까지**다. 터미널에 입력하거나 추가 미확인 알림을 보내지 않는다. 읽음이 자동으로 바뀌는 것은 아니며 화면의 **기록용 · 추가 알림 없음**과 미확인 집계는 함께 유지될 수 있다. 기존 직속 감독에게 보내는 완료 편지와 DONE 확인 절차는 [발령과 대기](../skills/kadan-conductor/references/dispatch-wait.md)를 따른다. 결과 우편이 있다는 이유로 검수 합격·업무 최종 완료를 확정하지 않는다.

## 성공 기준

기존 원문·순서 불변, 신규 사건의 작업·우편·시스템 분리, 읽음·중간 답장 뒤 질문 대기 유지, 최종 답장·취소의 종료 구분, 같은 실행 완료 결과 우편 한 번 저장을 확인한다. 격리된 JSONL·SQLite의 렌더링과 HTTP 조회에서 원문 참조가 충돌하지 않고 조회 전후 기록이 같아야 한다. 실제 운영 반영은 별도로 확인한다.

## 운영 반영

코드와 격리 시험이 끝난 것과 실제 운영 반영은 별개다. 운영 DB·설정 전환과 기반 프로세스 재시작은 승인된 전환 구간에서 [SQLite 저장 운영 안내](sqlite-storage.md)에 따라 수행한다. 과거 원장·본문·기존 상태 이력을 보존하며, 새 기록을 만든 뒤 과거 JSONL만으로 되돌리지 않는다. JSONL 비용·비원자성, SQLite 트랜잭션, 구형 작성자 혼용 금지와 남을 수 있는 본문 파일은 [분리 원장의 저장 경계](sqlite-storage.md#분리-원장의-저장-경계)를 따른다.
