# 일시적 429 자동 재개

## Why
일시적 요청 과부하로 멈춘 CLI를 감독 AI가 시간을 재며 기다리지 않고 이어간다.

2026-09-10 사용자 승인으로 `kadan watch`에 적용한다. 실행기 내부 재시도가 끝나 최종 429 오류와 **빈 입력창**이 함께 보일 때 1분, 2분, 3분 간격으로 최대3회 재개 입력을 보낸다. 서버의 `Retry-After`가 더 길면 그 시간을 따른다. watch 순회 간격만큼 전달이 늦을 수 있다. 별도 AI 대기·provider 변경·프로세스 재시작은 없다.

- 활성 단일 실행을 가진 작업자·검수자만 대상. 감독, 완료, 일시정지, 유효 waiting, PID 불일치, 새 사용자 입력은 제외한다.
- CLI가 아직 Working/Reconnecting/Retrying 중이면 예약하지 않는다. 일반 도구 출력 속 HTTP429나 설명문은 대상이 아니다. 인식할 수 없는 화면은 기존 감독 확인 경로에 남긴다.
- 명시 일일한도/RPD/잔액 부족은 자동 재개하지 않는다. 표시되지 않은 한도 종류는 추측하지 않는다.
- 예약 직전·전송 직전에 현재 카드/소유/입력창을 확인한다. 원장 기록 후 기존 PID 확인 전송 경로를 사용한다. 완료 마커가 있으면 보내지 않는다.
- 재개 입력은 최신 승인·영수증을 확인하고 미완료 지점만 이어가라는 지시다. 과거 도구 명령이나 발령 원문을 재전송하지 않는다. 외부 저장의 중복 실행 방지는 작업자가 기존 영수증을 확인하는 계약이며, 카단이 DB 트랜잭션 성공을 대신 판정하지 않는다.
- `rate-limit-retry` 원장에 scheduled/attempt/cancelled/delivery-failed를 보존한다. watch 재시작·새 메시지·새 task로 횟수를 초기화하지 않는다. 동일 역할 세대에서 성공 완료(done ok)가 확인되기 전에는 합계3회가 상한이다. 성공 완료 이후에는 새 예산을 사용할 수 있다.
- 새 오류 근거 없이 남아 있는 동일 오류 화면을 반복 재전송하지 않는다. 전송 실패는 모호한 성공일 수 있어 재전송하지 않고 감독에게 알린다. 3회 소진 뒤 새429도 감독에게 알린다.
- watch 재시작 후 예약은 원장에서 이어받지만 항상 최신 소유·화면을 다시 확인한다. 기존 오류 화면도 위 조건을 만족하면 최초 예약 대상이다.

구현: `src/watch-rate-limit.mjs`, watch 연결: `src/watch-runner.mjs`, 기존 PID 검증 송신: `src/cli.mjs`. 별도 타이머 프로세스·라이브 원장 직접 편집은 사용하지 않는다.

## ocx 사용량 새로고침 (2026-10-18 [kyle] 결정)

Why: 2026-10-18 검수자 셋이 codex 429로 14시간 멈췄다. 진짜 원인은 opencodex 프록시(ocx)가 리셋권 적용 뒤에도 옛 사용량 숫자를 붙들고 요청을 막은 것이었고, `ocx account refresh openai` 한 번으로 풀렸다. 감독은 이를 몰라 곧장 대체 실행기로 내렸다.

- 언제: 감시기가 어떤 세션에서 `한도` 경보를 **처음** 만들 때만. 같은 경보가 이어지는 순회에서는 부르지 않는다. 그 역할의 시작 기록이 openai를 쓰는 codex일 때만 부른다: `harness`가 codex이고 openai라는 긍정 근거가 있을 때만: `cmd`의 `model_provider`가 openai이거나, 모델 이름이 openai 꼴(`gpt-…`·`o1`·`o3`·`o4…`·`codex-…`, 접두어 `/` 없음)일 때. 모르는 이름·모델 없음·시작 기록 없음은 부르지 않고 원장도 쓰지 않으며 경보에 `ocx 새로고침 대상 아님(공급자 확인 못함) — 창 확인`을 붙인다. claude·devin·herdr 세션은 아무것도 붙이지 않는다. 자동 재개(위)가 처음 예약될 때도 부른다(예약된 세션은 한도 경보를 보내지 않으므로 결과는 원장과 감시 출력에 남는다. `Retry-After`로 오래 기다리는 중에도 같다). 재개 횟수·시각·생존 확인은 그대로다. 감시기를 다시 띄운 뒤 화면에 한도 줄이 그대로인 복원 경보는 경보가 첫 순회에 닫히기 전에, 그 경보 뒤 `ocx-refresh` 기록이 없으면 한 번 부른다(경보를 다시 알리지는 않는다).
- 무엇을: `ocx account refresh openai` 하나뿐이다. 실행 파일은 `KADAN_OCX_BIN`으로 바꿀 수 있다(시험이 가짜 명령을 넣는다). 순회 안에서 동기로 부르고 시간 상한은 30초다. 새 프로세스 묶음으로 띄우고, 넘으면 `timeout`으로 기록하며 그 묶음 전체(자식 포함)를 끝낸다. 우리가 띄운 묶음만 끝낸다.
- 상한: **전 역할을 통틀어 30분에 1번**. 원장의 마지막 `ocx-refresh` 줄이 30분 안이면 부르지 않고, 그 마지막 결과를 경보에 다시 붙인다(원장 줄은 새로 쓰지 않는다).
- 원장: `{kind:'ocx-refresh', by:'watch', provider:'openai', at, outcome:'ok'|'failed'|'timeout'|'missing', exitCode, usage:{fiveHour?, weekly?}, trigger:{role, session}}`. ocx의 원래 출력(stdout·stderr)은 원장·경보·알림 기록·감시 출력 어디에도 저장하지 않고 퍼센트 숫자와 종료 코드만 남긴다. 숫자는 출력에서 5시간·주간 낱말과 같은 줄의 퍼센트를 느슨하게 뽑는다(실제 출력 모양은 확인하지 못해 못 뽑으면 '숫자 미확인').
- 경보 본문 끝에 붙는 한 줄(받는 사람·중복 억제·기계 키는 그대로):

| 결과 | 문구 |
|---|---|
| 사용량이 모두 90% 미만 | `사용량 새로 받음: 주간 3% — 가짜 한도였을 가능성, 이 창은 esc 뒤 재개 필요(자동 재개 안 함)` |
| 하나라도 90% 이상 | `새로 받아도 한도(주간 98%) — 대체 실행기 고려` |
| 숫자를 못 뽑음 | `사용량 새로 받음(숫자 미확인) — 창 확인` |
| 실패·시간 초과·없음 | `ocx 새로고침 실패(종료 코드 N)` / `ocx 새로고침 시간 초과` / `ocx 없음` |
| 30분 안에 이미 받음 | `ocx 사용량은 N분 전 새로 받음: 주간 3% — …` |

- 하지 않는 것: 멈춘 창을 esc·재개로 푸는 일은 자동화하지 않는다(감독 몫, 위 문구가 할 일로 적는다). ocx가 없거나 실패해도 경보 전달과 위 자동 재개 예약은 그대로다.

구현: `src/ocx-refresh.mjs`, 경보 본문 `src/watch-alert-body.mjs`, 연결 `src/watch-runner.mjs`, 시험 `tests/watch-ocx-refresh.test.mjs`.
