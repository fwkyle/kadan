# 역할 우편함과 비서 주소

## Why

사용자가 비서뿐 아니라 감독·작업자·검수자의 공식 편지와 답변 대기를 같은 방법으로 확인하고, 전달됨·읽음·답변 완료를 구분하게 한다.

## 역할별 조회

모든 역할은 같은 우편함을 사용한다. 비서는 세션을 만들지 않는 우편 주소라는 특성을 유지한다. 사용자 일반 대화나 전체 터미널 대화를 자동 수집하지 않는다.

```sh
KADAN_ROLE=판-슈퍼감독 kadan send 비서 --mail-kind report '현재 작업 결과와 확인 근거'
kadan inbox list --role 비서
kadan inbox received --role 제품-감독 --all
kadan inbox sent --role 제품-작업자
kadan inbox to-reply --role 제품-감독
kadan inbox waiting --role 제품-작업자
kadan inbox read <우편ID> --role 제품-감독
KADAN_ROLE=제품-감독 kadan inbox ack <우편ID> --role 제품-감독
```

기준 역할은 명시한 `--role`, `KADAN_ROLE`, 호출자의 `by`, 사람 순서로 정한다. 사용자 셸의 기본은 사람이며 비서는 `--role 비서`로 명시한다. 받은 편지 기본 조회는 읽음 미확인이며 `--all`로 읽은 편지도 본다. `read`는 본문만 조회한다. 현재 수신 책임자 또는 사용자가 내용을 확인한 뒤 `ack`를 기록한다. 읽음은 작업 완료나 지시 승인이 아니다.

## 질문과 답장

- `send --expect-reply`는 답변이 필요한 질문이다. `--reply-to <우편ID>`로 원본을 연결한다. 같은 본문 지문이 여러 통에 겹치면 고유한 우편 ID를 사용한다.
- 읽음 확인과 중간 답장은 답변 대기를 유지한다. 현재 수신 책임자의 `--reply-final` 답장 또는 현재 발신 책임자의 `inbox cancel <우편ID> --role <기준역할>`로 끝낸다. 사용자 권한의 확인·취소도 공통 우편함 검증을 따른다.
- `--mail-kind`는 request/decision/report이며 기본 report다. 이 분류나 질문 최종 답장이 별도의 사용자 승인 권한을 만들지 않는다. 정식 사용자 결정은 기존 decision CLI를 사용한다.
- `--work 저장소/업무ID`, `--execution 저장소/실행ID`는 [업무·실행](business-work.md) 연결 주소다. 답장은 원본의 연결을 이어받는다. `send 비서 --task`는 계속 거절한다.

`send <역할> --mailbox`는 역할 세션이 없어도 우편함에만 저장한다. `--task`와 함께 쓸 수 없다. 비서의 기존 `send 비서`는 저장 전용 호환 경로다. 터미널 전달 후 다른 최종 답장·취소가 먼저 확정되면 `replyFinalRejected: true`로 전달 사실만 보존하며, 화면에서 **전달됨 · 답변종결 반영 안됨**을 확인할 수 있다.

## 저장과 깨움

본문은 `mail/<sha256>.txt`, 신규 우편·읽음·질문 취소 사건은 같은 SQLite의 `mail/events.jsonl` 스트림에 저장한다. 비서처럼 우편함에 직접 보관하는 편지는 원장에 본문·미리보기를 복사하지 않는다. 기존 터미널 전달 기록의 미리보기는 호환을 유지한다. 과거 `ledger.jsonl` 이력은 보존하고 읽기용으로 연결한다.

`stored`는 저장됐다는 뜻이다. 비서와 대화하는 창에 직접 입력하거나 자동으로 깨우는 연결은 없으므로 `wake: not-connected`를 명시한다. 다른 역할의 기존 터미널 전달 경로는 그대로다. 자동 실행 완료 결과 통지도 원본 요청자의 우편함에 저장까지만 하며 추가 미확인 알림에서 제외한다. 읽음은 별도 상태다. [원장과 완료 결과 통지 계약](mail-task-ledgers.md)을 따른다.

일반 터미널 메시지는 즉시 전달하고 우편 ID·수신자 ack 안내를 붙인다. `--raw` 원문은 바꾸지 않으며 inbox에서 확인한다. 미확인 우편의 유예·묶음 알림·재시작 중복 방지는 [구조 기준](architecture.md#읽음-확인과-미확인-우편-알림)을 따른다.

## 화면과 오류

현황의 **전체 역할 미확인 우편**과 전체 우편함에서 역할·받은/보낸 편지·내가 답할 질문·답변 대기·질문 상태로 조회한다. 업무·실행 상세에서는 명시적으로 연결된 편지를 본다. 확정 인계 뒤 역할 필터는 현재 책임자를 사용하고 원래 발수신 정보도 보존 표시한다. 후임은 자신의 역할로 받은 편지·답할 질문과 보낸 편지·답변 대기를 조회한다. [인계 책임 기준](architecture.md#인계-뒤의-우편-책임)을 따른다. 웹 본문 조회는 읽음 기록을 만들지 않는다. 우편함 저장은 상대의 처리 완료가 아니다.

**기록용 · 추가 알림 없음**은 읽음 처리를 뜻하지 않는다. 알림 자체·자동 결과 우편도 실제 ack 전에는 미확인 집계에 남을 수 있다.

신규 우편 ID가 있는 편지는 읽음 미확인에서 시작한다. 우편 ID가 없는 과거 전달은 읽음 상태 모름으로 남긴다. 원장 조회 오류는 `0건`이 아니라 `모름`이다. 본문 조회 오류도 읽음 처리하지 않는다. 일반 대화 자동 저장·백그라운드 AI 반복 조회·OS 포커스 이동·비서 프로세스 생성은 하지 않는다.
