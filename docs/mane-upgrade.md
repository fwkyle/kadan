# 카단 업그레이드 제안 — mane 실험에서 검증된 것을 얹는다

## Why

카단은 "사람이 보고 개입하는" 관제를 실제로 돌려왔지만, 규칙은 문서와 감독 판단에 맡겨져 있어서 실제로 강제되지 않는다. mane(~/Dev/mane)은 마네님 프로토콜을 코드로 옮긴 실험으로, 승인 게이트·상태 전이·spec 무효화·자기 승인 금지를 SQLite에 실제로 집행한다. 이 문서는 mane에서 검증된 장치를 카단에 얹는 방법을 정리한다 — 카단의 정체성(대화형 세션·attach·watch·우편)을 유지하면서, 문서 규칙을 코드 규칙으로 바꾼다.

전제 비교는 [mane 분석](research/mane/mane-vs-kadan-analysis.md)과 [AICP 분석](research/aicp/aicp-vs-kadan-analysis.md)을 따른다.

## 지금 카단에 없는 것 (mane이 실제로 집행하는 것)

| 장치 | 카단 | mane |
|---|---|---|
| 상태 전이 규칙 | 없음 — 감독이 판단 | 허용 목록으로 코드가 막음 |
| 착수 승인 게이트 | 문서 규칙 ("파괴적 작업 금지") | L2+는 승인 레코드 없이 start 불가 |
| 승인 무효화 | 없음 — 과거 승인이 계속 유효 | spec_hash 바뀌면 자동 무효 |
| 자기 승인 금지 | 없음 — 작업자가 done 칠 수 있음 | reviewer=assignee면 코드가 거부 |
| 완료 증거 필수 | DONE 마커만 있으면 됨 | evidence 없이는 complete 불가 |
| 의존성 체인 | 없음 — 감독이 순서 판단 | depends_on 선언, 앞 작업 완료 전 ready 불가 |
| 팀 경계 | 없음 | 다른 팀 에이전트에게 배정 불가 |

공통점: 둘 다 append-only 원장, "모호하면 실패 닫힘", DONE 마커 규약을 쓴다. 차이는 규칙을 누가 지키는가 — 카단은 감독, mane은 코드.

## 업그레이드 방향 — 카단의 바닥은 그대로, 게이트만 얹는다

카단의 가치는 살아있는 세션과 사람 개입 경로다. 그걸 유지하면서 mane의 게이트를 얹는다.

### 1. 카드에 상태와 위험 수준을 둔다

지금 카드는 제목·본문·우편 연결 정도다. 여기에 두 필드를 추가한다:

- `status`: DRAFT / READY / ASSIGNED / IN_PROGRESS / PENDING_REVIEW / COMPLETED / FAILED / CANCELLED
- `risk_level`: 0~5 (mane의 L0~L5와 같은 의미 — L2부터 승인 필요)

기존 카드는 status를 'READY'로 간주하고 risk_level 0으로 읽는다(하위 호환). 새 카드부터 명시한다.

### 2. send 직전에 게이트를 끼운다

`kadan send`가 지금 하는 것: 세션 생존 확인(has-session + PID 대조) → 밀어넣기 → 원장에 send 기록.

여기에 한 단계를 추가한다:

```text
send 요청
  → 세션 생존 확인 (기존)
  → 카드 조회: risk_level >= 2 이면 approvals 테이블에서
     유효한 kickoff 승인을 찾는다 (같은 task_id + 같은 spec_hash + status=APPROVED + used_by IS NULL)
  → 없으면 거부하고 원장에 gate.reject 기록
  → 있으면 used_by를 찍고(1회용) 밀어넣기 → 원장에 send 기록
```

승인은 새 명령 `kadan approve <card> --by <사람>`으로 만든다. 승인 요청은 오케스트레이터(또는 감독)가 자동으로 남기고, 사람이 결정한다.

### 3. spec_hash로 승인-대상을 묶는다

카드의 spec(제목·범위·수용기준·위험·팀·역할)을 정규화해서 sha256으로 해시한다. 승인 레코드에 이 해시를 저장하고, send 시점에 현재 카드의 해시와 대조한다. 카드가 수정되면 해시가 바뀌고 이전 승인은 자동으로 무효가 된다 — mane에서 실제로 검증된 패턴이다.

### 4. done에 증거와 검토자를 요구한다

지금은 DONE 마커만으로 완료다. 업그레이드:

- `kadan done <card>`을 부를 때 `--evidence <경로 또는 요약>`을 받는다
- 완료 확정은 수행자가 아니라 검토자(또는 감독)가 한다 — `kadan done <card> --by <검토자>`에서 by가 assignee와 같으면 거부
- DONE 마커는 "작업자가 끝났다고 주장"하는 신호로 남기고, 실제 완료 상태 전이는 검토자 확인으로 간다

이렇게 하면 "에이전트가 완료라고 말함 ≠ 완료"가 코드로 강제된다.

### 5. 의존성을 카드 필드로 둔다

`kadan plan`이나 카드 생성 시 `--dep <다른 카드id>`를 받는다. 의존 카드가 COMPLETED 전에는 해당 카드를 READY로 올리지 않는다. 감독이 순서를 기억할 필요가 없어진다.

### 6. 팀 경계를 둔다 (선택)

에이전트 등록 시 팀을 명시하고, 다른 팀 에이전트에게 배정을 못 하게 한다. 카단이 지금 "역할"만 쓰는데, 팀을 추가하면 스크린샷의 회사 구조(web-experience / content / booking-platform)를 그대로 표현할 수 있다. 다만 이건 규모가 커질 때 필요하니, 처음엔 생략하고 나중에 추가해도 된다.

## 무엇을 얹지 않는가

mane 문서(마네님 프로토콜)에 있지만 카단에 얹지 않는 것:

- **ApprovalUsageLedger의 원자적 예약, ExecutionReceipt, attestation 서명** — 카단은 단일 감독 흐름이라 지금 필요 없다. 병렬 감독이 생기면 그때.
- **점수 기반 조직 선택기 (2C+3R+2D+2E+2Q)** — 카단은 감독이 조직을 판단한다. 자동 선택은 카단의 "사람이 판단" 원칙과 어긋난다.
- **Shared Blackboard / Decision Log** — 카단은 원장과 우편이 그 역할을 한다. 별도 저장소를 만들지 않는다.
- **Claude Code 훅 계약** — 카단은 provider 어댑터를 만들지 않는다(잠긴 규칙). 바닥(tmux) 위에서 돌아가는 한 훅은 필요 없다.

## 단계별 도입 순서

한 번에 다 얹지 않는다. 사고가 반복될 때 최소 장치를 추가하는 카단 원칙을 따른다.

**1단계 (지금 가치가 있는 것)**: 카드에 status + risk_level 필드 추가, send 전 게이트, approve 명령, spec_hash 무효화. 이 네 개면 "승인 없는 고위험 실행"과 "승인 후 범위 변경" 사고를 막는다.

**2단계**: done에 evidence 필수 + 검토자 분리. 완료 판정이 단단해진다.

**3단계**: depends_on. 카드가 많아지고 순서가 복잡해질 때.

**4단계**: 팀 경계. 여러 팀이 생기면.

## 검증 방법

각 단계는 mane에서 이미 검증된 패턴을 따른다:

- 게이트: risk 2+ 카드에 승인 없이 send → 거부되는지
- 무효화: 승인 후 카드 제목 변경 → send 거부되는지
- 1회용: 같은 승인으로 두 번 send → 두 번째는 거부되는지
- 자기 승인: 작업자가 자기 카드를 done → 거부되는지
- 증거: evidence 없이 done → 거부되는지

mane의 tests/core.test.mjs에 해당하는 테스트가 이미 있으니, 카단에 옮길 때 같은 시나리오를 카단 CLI로 돌린다.

## 한 줄 정리

카단의 바닥(살아있는 세션·attach·watch·우편)은 그대로 두고, mane에서 검증된 게이트(승인 필수·spec 무효화·자기 승인 금지·증거 필수·의존성)만 카드와 send/done 경로에 얹는다. 규칙이 문서에서 코드로 옮겨가는 게 핵심이다.
