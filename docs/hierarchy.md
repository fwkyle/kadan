# 카단 역할과 알림 경로

## Why

역할 이름이나 작업폴더가 달라도 누가 누구를 책임지는지 명시하여 완료·이상 알림을 올바른 상위에 전달한다.

## 현재 카단과 역할의 자리

- 실행 코어는 이 저장소다. 이전 카단 구현(2026-08-30 동결)은 설명서 참고 원본일 뿐이다.
- 비서는 공통 지휘 공간, 슈퍼감독과 일반감독은 담당 레포, 작업자·검수자는 해당 기능 worktree를 기본으로 한다. cwd 자체는 권한이나 상하관계를 증명하지 않는다.
- 비서는 사용자 요청과 확인 결과를 전달한다. 일반감독은 카드 발령·결과 검수와 승인 범위 안의 방법 선택·진단·장애 복구·재개를 결정한다. 슈퍼감독은 판 간 충돌·우선순위·일반감독이 풀지 못한 판단을 조정하고, 작업자는 구현, 검수자는 독립 검증을 소유한다. 구체적인 위임과 기존 방법 제한 정정은 [공통 운영 기준](../skills/kadan-conductor/references/operating-contract.md#일반감독의-결정-범위)을 따른다.
- 기존 세션의 cwd를 이 규칙 때문에 강제 재시작하지 않는다. 다음 정상 인계에서 맞춘다.

## 레포별 슈퍼감독

슈퍼감독은 자기 레포의 규칙·문서·진행 상황을 읽고 사용자와 대화한다. 구현·검수 운영은
일반감독에게 맡긴다. 다른 레포 슈퍼에게 맥락 우편을 넘기면 위임한 일은 수신 측이 책임지고
자기 일반감독과 처리한다. 슈퍼는 카드를 먼저 쓰지 않고 수신 일반감독이 설계·카드·발령을 맡는다.
회신을 요청하지 않았으면 발신자는 자동으로 회신을 요구하거나 기다리지 않는다.
명시 요청에만 `--expect-reply`와 최종 `--reply-final` 회신 의무가 생긴다.
위임이 발신자가 맡은 별개 프로젝트 전체를 자동 완료한다는 뜻은 아니다.
각 슈퍼는 사용자 직속의 동료다. 다른 슈퍼의 자식으로 자동 등록되지 않게 담당 레포에서
`kadan start <레포>-슈퍼 --profile super --parent @user`로 만든다.
`--profile super`에 `--parent`가 없으면 만든 쪽이 아니라 `@user`가 상위로 적힌다(2026-10-14). 총괄 아래에 레포 슈퍼감독을 세우려면 `--parent <총괄>`을 준다.
기존 역할의 관계나 세션은 이 규칙 때문에 자동 변경하지 않는다.

### 슈퍼감독은 시작 프로필로 알아본다 (2026-10-14)

"슈퍼감독이 누구인가"는 관계표의 위치가 아니라 **start 사건에 기록한 `roleProfile`** 로 판정한다(`src/super-role.mjs`). 그 역할의 start 중 `roleProfile`을 기록한 가장 최근 것이 `super`이면 슈퍼감독이다. 프로필을 기록한 start가 하나도 없는 옛 역할만 예전 기준(상위가 `@user`)으로 본다. 원장을 못 읽어 프로필을 모르면 모두 예전 기준으로 돌아간다. 그래서 비서가 세운 `kadan-슈퍼감독`(상위 `비서`)도 슈퍼감독이고, 상위가 `@user`여도 `conductor`·`secretary`로 시작한 역할(예: 비서, adopt한 감독)은 슈퍼감독이 아니다. 총괄 → 레포 슈퍼감독 → 일반감독 사슬도 같은 판정으로 동작한다.

**"슈퍼감독인가"와 "최상위인가"는 다르다.** 상위가 `@user`인지를 묻는 곳은 위치를 뜻하므로 그대로다: 경보를 위로 올리는 사슬(`hierarchyRoute`), 감독 점검 범위가 `@user`까지 거슬러 오르는 길, 자원 알림 등 `@user` 수신. 바꾼 곳은 "누가 슈퍼감독인가"를 묻는 곳뿐이다: 대시보드 슈퍼감독별 현황, `status?super=`, 슈퍼 간 우편(`peer-mail`), 대시보드 질문 수신자(`askRecipient`), `start --profile super`의 상위 기본값.

대시보드 범위: **요약 목록**은 각 행·업무를 가장 가까운 슈퍼 조상 한 곳에만 묶어 한 번만 센다. `status?super=X`는 X가 슈퍼감독이면 200이고 X 자신과 X 아래 전부(하위 슈퍼감독의 몫 포함)를 돌려준다. 슈퍼감독이 아니면 400("슈퍼감독(--profile super)으로 시작한 역할이 아님")이다. 그래서 총괄의 `?super=` 값은 요약 목록의 총괄 한 줄보다 넓다.

동료 요청·회신은 [레포 간 우편](peer-super-mail.md)을 따른다. 같은 `KADAN_HOME`과
같은 실행 바닥에서 사용한다. 다른 서버·다른 홈 사이의 우편 중계 기능은 아니다.

## 명시적인 직속 상위

`kadan watch --hierarchy /절대경로/역할관계.json`은 시작 시와 매 감시 주기에 아래 JSON을 읽는다.

```json
{
  "제품-슈퍼감독": "@user",
  "제품-감독": "제품-슈퍼감독",
  "제품-wave2-작업자": "제품-감독",
  "데이터-감독": "제품-슈퍼감독",
  "품질-감독": "제품-슈퍼감독"
}
```

- 값은 직속 상위다. `@user`는 OS 알림과 watch 출력이다. 새 역할은 아래 자동 등록으로 들어가며, 자동 등록이 건너뛴 경우(사람이 직접 시작 등)에는 `kadan hierarchy add`로 더한다. 다음 감시 주기에 변경을 검증하고 `hierarchy-loaded` 원장에 경로·파일 지문·감시 PID를 남긴다. 실행 중 파일 오류는 마지막 정상 관계를 유지하고 사용자에게 오류를 알린다. 이전 버전 감시기는 재시작해야 이 동작이 적용된다.
- 빈/잘못된 이름, 자기 참조, 순환, 상위 미등록, 파일 읽기/JSON 오류는 시작 실패다. 잘못된 관계를 이름 추정으로 덮지 않는다.
- 등록된 역할의 모든 역할 알림(완료후보·정체·죽음·끊김·읽기불가)은 명시된 상위로 간다. 감독유휴(`--idle`, 놀고 있음)는 작업 감시 범위와 감독 점검 범위의 세션에 적용되고, 먼저 그 감독 본인에게, 그 두 배 시간이 지나면 상위에게 간다([멈춤 규칙](watch-overview.md#멈춤-규칙-2026-10-05); `--wake` 자가점검은 2026-10-05에 없앴다). 관계표에서 하위를 가진 감독과 최상위 슈퍼감독도 아래에 활성 실행이 있으면 받는다(2026-10-05, 그 전에는 작업 감시 범위로만 걸러 등록된 감독에게 닿지 않았다). 등록된 감독의 응답은 [감독 관찰AI](watch-overview.md#감독-관찰ai의-응답-점검-2026-09-09)가 맡는다(`--judge-cmd`가 있을 때). 직속 상위가 죽었으면 같은 책임 사슬에서 살아 있는 다음 상위로, 모두 없으면 사용자에게 간다.
- 미등록 역할은 기존 `--route`/판이름/`--super` 규칙을 유지한다. 다만 `--route`·`--super`에 적힌 이름도 **살아 있는 세션일 때만** 받는다(HW-7). 죽었으면 건너뛰고(`route.skipped`에 이유를 남긴다) 같은 판 살아 있는 감독 → super → 끝내 없으면 `@user` 순서로 간다. 역할 이름이 `<판>-신규-작업자`처럼 판 이름이 달리 뽑혀도 route 키가 역할 이름의 접두사(`<키>-`)이면 걸리고, 여럿이면 가장 긴 키가 이긴다. 다른 바닥·다른 홈에 있는 수신자는 이 감시기의 생존 목록에 없어 죽은 것으로 보인다. 자원·원장 읽기 오류처럼 특정 역할이 없는 경보도 기존 공통 수신자를 유지한다. 한 프로젝트를 고치려고 타 판의 전역 수신자를 바꾸지 않는다.
- 감독 유휴는 **본인 차례인 일**의 미완료와 실제 출력 변화를 본다(2026-10-16 [kyle]). 본인 차례 = 열린 업무는 지금 차례(`turnOwner`)인 역할(관계표에 없으면 owner. 차례 칸에는 역할 이름 또는 `@user`를 적는다 — `@user`(current)는 사용자 대기로 할 일에서 빠지고, 밖에서 기다리는 글 값은 관계표 밖이라 owner로 돌아오므로 `kadan work update '<업무>' --revision <지금 revision> --status hold --next-action '…' --note '외부 대기'`로 멈춘다(경보 본문에 현재 revision이 채워져 나온다)), 작업자에게 보낸 발령은 그 직속 감독, 내가 답할 질문이 걸린 일. 하위 감독 차례인 일은 상위의 1단을 만들지 않는다 — 그 하위 감독의 1단 → 2단(상위) 경로로만 올라온다. 이것은 2026-10-05 2-H1(하위 일도 감독 유휴에 포함)을 바꾼 것이다. 하위 작업이 진행하면 조용한 감독을 유휴로 알리지 않는 규칙은 그대로다. 역할별 done을 구분하며 동일 카드ID의 다른 역할 완료로 지우지 않는다.
- 계획만 있는 카드는 같은 판의 직속 감독을 찾는다. 비표준 별도 판 이름의 미발령 계획은 정확한 판 등록/담당 확인이 필요하며 이름만으로 직속 관계를 만들지 않는다.

## 역할 이름 규칙과 같은 이름 재사용 (2026-10-13)

**이름 규칙.** 새 역할 이름은 `<레포명>-<역할>`, 주제가 있으면 `<레포명>-<주제>-<역할>`로 짓는다(예: `kadan-슈퍼감독`, `rottie-RH-감독`, `kadan-역할주소-작업자`). 이름의 첫 `-` 앞이 판 이름이라는 감시 경로 규칙([감시 운영](../skills/kadan-super/references/watch-ops.md))과 같은 뜻이다. 레포명은 시작 폴더가 속한 git 주 저장소 이름이다(worktree면 주 저장소 기준). `kadan start`·`kadan adopt`가 **처음 쓰는 이름**이 이 접두로 시작하지 않으면 표준 오류로 경고를 한 번 내고 그대로 시작한다. git 밖이거나 판단할 수 없을 때, `--profile secretary`일 때, 이미 쓰던 이름일 때는 경고하지 않는다. 거절하지 않고 끄는 설정도 없다. 거절로 바꿀지는 사용자 결정이다. 기존 역할 이름은 이 규칙 때문에 바꾸지 않는다.

**같은 이름 재사용.** 이름을 다시 써도 거절하지 않는다. 대신 우편은 이름이 아니라 **세대**에 속한다. 세대는 원장의 `start` 사건으로 시작한다. 같은 이름의 새 세션이 시작되면(처음 start가 아닌 start) 그 이전에 그 이름 앞으로 온 미확인 우편은 **이전 세대 미확인**이 된다.

- 새 세대의 미확인 수, `kadan inbox` 기본 목록, 5분 묶음 재알림, 대시보드 미확인 수에 들어가지 않는다. 우편은 지우지도 읽음으로 바꾸지도 않는다(원장은 추가만 한다. 계산에서만 거른다).
- `kadan inbox --previous-generations`와 대시보드 우편함의 '읽음 상태: 이전 세대 미확인'에서 따로 보고 `ack`할 수 있다. `--all` 기록 조회에는 그대로 남는다.
- 같은 정체를 잇는 start는 새 세대가 아니다: 같은 대화를 다시 여는 start(`--resume <id>`만 있고 `--fork-session`이 없는 claude, `codex resume <id>`, `agy --conversation <id>`, `devin --resume <id>`), `kadan restart`가 남기는 `restartOf`, 살아 있는 세션을 다시 연 start(같은 pane PID, 사이에 stop 없음), `recovery restore`(`restoredFrom`), 비서 복원(`secretaryResumeSource`). 우편을 그대로 이어받는다. 새 대화를 여는 start(`claude --resume <id> --fork-session`=`adopt`가 쓰는 형태, `codex fork <id>`, 대화 지정이 없는 새 명령, 알아볼 수 없는 명령)는 새 세대다. 방식은 start 사건의 `conversationMode`(new·resume·fork)·`conversationRef`에 남기며, 이 필드가 없는 옛 start는 `cmd` 원문에 같은 파싱을 적용한다(원장은 고치지 않는다). 명령은 셸 인자 경계를 지켜 읽고 옵션 자리의 낱말만 본다(따옴표 안 입력의 `--resume` 낱말은 옵션이 아니다). claude는 `--resume|-r <id>`·`--resume=<id>`·`--continue|-c`와 `--fork-session`을 읽되 값이 꼭 있는 옵션(`--model`·`--append-system-prompt`·`--system-prompt` 등, claude 2.1.296 `--help` 기준)의 값은 건너뛰고(값이 선택인 옵션과 목록 밖 옵션은 값 없는 옵션으로 보므로 그 다음 낱말이 값이면 잘못 읽을 수 있다), codex는 값을 받는 전역 옵션(`-p -m -c -s -C -a` 등, codex 0.155.0 `--help` 기준)을 건너뛴 뒤 첫 하위 명령 `resume|fork <id>`를 읽는다. codex에서 목록에 없는 옵션이 있거나 어느 실행기든 셸 연산이 있으면 판단하지 않고 new로 본다(이때 같은 대화를 resume한 우편이 이전 세대로 숨을 수 있다). 시간 차·자유 문장(`overrideReason` 등)·대화 파일은 보지 않는다. 한계: `--cmd "claude --resume <무관한 id>"`로 죽은 이름을 다시 쓰면 이어감으로 판정된다. 인계(`handover`)의 승계 규칙은 그대로다. 확정된 인계는 받는 이름의 현재 세대 책임으로 옮기므로 인계 뒤에 새 세대가 시작되면 그때부터 이전 세대다.
- 세션이 없는 동안 저장된 우편(`wake: not-connected`)은 직전 세대 몫이다. 다음 start가 복원이면 이어받고, 새 세대면 이전 세대 미확인으로 남는다. 한 이름의 첫 start 이전에 쌓인 우편은 첫 세대 몫이다.
- 이어받기를 원하면 `kadan start <이름> --inherit-mail` 또는 `kadan adopt <이름> --inherit-mail`. start 사건에 `inheritMail`·`inheritedUnread`가 남고 **바로 앞 세대 하나만** 이어받는다(그 앞 세대의 우편은 끊긴 채 남는다).
- 과거에 쓴 이름으로 새 세션을 만들면 표준 오류에 한 번 알린다: 끊은 경우 "이전 세대 미확인 N건은 넘겨받지 않았다", 이어간 경우(resume 또는 `--inherit-mail`) "이전 세대 N건 이어감". 출력은 stdout 한 줄(`시작됨: …`) + 표준 오류 안내이고 JSON은 출력하지 않는다. 관계표의 옛 줄은 아래 "책임자와 관계표도 세대로 가른다"를 따른다.

### 책임자와 관계표도 세대로 가른다 (2026-10-14)

우편과 **같은 세대 경계**(`mail-generation.mjs`: new·fork·adopt start는 경계, resume·같은 PID 재사용·복원·`--inherit-mail`은 이어감)를 업무·카드 책임자와 관계표에도 쓴다. 판정을 새로 만들지 않고 같은 경계를 시각으로도 비교한다(`owner-generation.mjs`).

- **업무·카드 책임자.** 기준 시각은 생성 시각이 아니라 **책임이 그 이름에 마지막으로 붙은 사건**(생성·재배정·확정 인계)이다. 그 시각 뒤에 같은 이름의 새 세대가 시작됐으면 이전 세대 소속이다. 새 세대가 시작된 뒤에 인계·재배정받은 업무는 현재 세대 것이다. 이전 세대 소속의 열린 업무·발령은 **"놀고 있음" 할 일**과 작업 감시 범위(`buildWatchScope`·`buildSupervisorScope`)에서 빠진다. 숨기되 잃지 않는다: 원장·카드는 그대로이고 대시보드 현황의 "이전 세대 업무 N건"(업무·발령 구분)에 보인다. 새 세대가 이어받으려면 업무는 `kadan work update <키> --owner <같은 이름> --revision N --note 이유`(값이 같아도 명시 재지정은 책임 시각을 올린다. 진행 기록·제목 수정은 올리지 않는다), 발령은 다시 `kadan send`로 발령하거나 인계(`kadan handover`)를 쓴다. 인계 시각을 모르는 옛 기록은 "모름"으로 보존해 이전 세대로 숨기지 않는다. 이전 세대 발령을 뺀다고 그 plan을 미발령 할 일로 되살리지 않는다.
- **`--inherit-mail`** 은 바로 앞 세대의 우편과 **책임도 함께** 이어받는다(플래그 이름은 그대로, 의미가 넓어졌다). 그 앞 세대는 끊긴 채 남는다.
- **관계표.** new·fork·adopt start(세대 경계)이고 이름이 관계표에 이미 있으면 **그 역할 자신의 상위 줄만** 이번 start의 상위로 바꾼다(명시 `--parent` > 슈퍼감독 프로필의 `@user`·adopt 기본 `@user` > 만든 쪽). 같은 값이면 아무것도 안 한다. resume·이어감 start는 표를 바꾸지 않는다. 만든 쪽을 모르면(사람이 직접 start) 바꾸지 않고 안내만 한다. 상위가 표에 없거나 바꾸면 순환이 되면 바꾸지 않고 알린다. 잠금·검증·원자적 쓰기는 자동 등록과 같다. 바꿨으면 표준 오류에 "관계표 상위 변경: 역할: P1 → P2"와, 이 이름을 상위로 가리키는 **옛 하위 줄은 건드리지 않고** "옛 하위 N개(살아 있는 것 M개)가 이 이름을 상위로 가리킨다. 끝난 역할은 `kadan hierarchy prune`"을 한 줄씩 알린다.
- 대시보드 `status?super=`의 `previousGeneration`은 그 슈퍼감독 아래 몫만 센다.

## 시작할 때 자동 등록 (2026-09-11 [kyle] 지시)

`kadan start`는 세션을 만든 뒤 **만든 사람을 그 역할의 직속 상위로 관계 파일에 적는다.** 사람이 한 줄을 기억해서 넣지 않아도 알림이 갈 곳이 정해진다. 대상 파일은 원장의 마지막 `hierarchy-loaded`가 가리키는 경로, 즉 현재 감시기가 실제로 읽는 관계 파일이다.

추가만 하고 기존 줄은 고치거나 지우지 않는다. 아래에 해당하면 적지 않고 시작은 그대로 진행한다.

| 건너뛰는 경우 | 이유 |
|---|---|
| `KADAN_ROLE` 없이 사람이 직접 시작 | 상위로 적을 역할이 없다 |
| 실행 명령이 카단 자신의 `watch`·`dashboard`·`wall` | 보고 관계의 역할이 아니다. 넣으면 트리에 부하처럼 보이고 만든 감독의 인계 때 "보고 대상 변경" 편지가 그 프로그램 창에 붙는다(2026-09-23 [kyle]) |
| 감시기가 읽는 관계 파일을 모름 | 감시기 없는 환경은 정상이다 |
| 이미 등록된 역할 | 기존 상위를 덮지 않는다 |
| 만든 사람이 관계 파일에 없음 | 위로 올라가는 길이 끊긴 줄을 만들지 않는다 |
| 파일 읽기·검증·쓰기 실패, 동시 등록 잠금이 2초 이상 지속 | 깨진 표를 남기지 않는다 |

성공하면 `감시 등록: <역할> → <상위>`를 출력한다. 관계 파일을 찾고도 못 적었을 때만 표준 오류로 알린다. 쓰기는 임시 파일과 이름 바꾸기로 한 번에 반영하며, 같은 순간 두 곳이 고치지 않게 `hierarchy-register.lock`을 쓰고 남의 잠금은 지우지 않는다. 작업자를 여러 개 동시에 시작하면 잠금이 짧게 겹칠 수 있으므로 등록은 최대 2초 기다렸다가 다시 얻는다(2026-09-28). 그래도 못 얻으면 시작은 그대로 진행하고 등록만 건너뛴다. 이 기능은 등록만 하며 역할 생성·모델 선택·발령 권한을 넓히지 않는다.

## 빠진 역할을 수동으로 더하기

사람이 `KADAN_ROLE` 없이 직접 시작한 역할처럼 자동 등록이 빠진 줄은 사람이 더한다.

```sh
kadan hierarchy add <역할> <상위|@user>
```

자동 등록과 같은 검증·잠금을 거치며 추가만 한다. 이미 있는 역할의 상위는 덮어쓰지 않고,
표에 없는 상위·공백 있는 이름·`@user`를 역할로 쓰는 것은 거부한다. 결과를 JSON으로 출력한다.

## 끝난 역할 정리

끝난 역할이 관계표에 계속 쌓일 때 수동으로 정리한다. 원장·카드의 이력은 그대로 남는다.
관계표 크기를 줄이는 기능이며 `tree` 전체 조회의 속도 개선을 보장하지 않는다.

```sh
kadan hierarchy prune
kadan hierarchy prune --file /절대경로/관계표-복사본.json
kadan hierarchy prune --apply
```

- 기본은 미리 보기다. 파일을 바꾸거나 잠금·백업을 만들지 않고, 전체·제거·보존 개수와 역할별 보존 이유를 JSON으로 출력한다.
- 기본 대상은 마지막 `hierarchy-loaded`의 파일이다. `--file`은 복사본 검증 등 대상 파일만 바꾼다. 생존 정보와 카드·업무·원장은 현재 바닥과 `KADAN_HOME`에서 읽는다.
- 세션이 살아 있으면 남긴다. PID 불일치·시작 기록 없음도 남긴다. 생존 목록·카드·업무·원장 조회 실패는 정리 실패이며, `0개`로 취급하지 않는다. tmux 서버가 없어 목록을 확인할 수 없는 경우도 적용하지 않는다.
- 카드 상태 또는 현재 실행 상태가 미완료이거나, 완료 기록 없는 발령이 있으면 남긴다. 일시정지·미발령·입력 대기도 종료로 취급하지 않는다. 카드 주소와 확정 인계는 기존 계산을 사용하며, 연결이 불명확한 역할은 남긴다.
- 열린·일시정지 업무의 현재 책임 감독과 다음 담당도 남긴다. 실행이 끝났어도 업무 최종 확인이 남아 있을 수 있다. 감시 대상에서 제외됐다는 사실은 정리 가능 근거가 아니다.
- 마지막 `start` 이후 `stop` 또는 해소되지 않은 `죽음` 경보가 있어야 한다. 그 관측부터 **24시간**이 지나야 후보가 된다. 재시작·경보 해소·후속 전달/완료 기록이 있으면 새 종료 관측을 기다린다. 시작 시각을 종료 시각 대신 쓰지 않는다. 24시간은 보수적인 기본값이며 알림 처리 시간으로 검증된 수치는 아니다.
- 현재 표에 자식이 있는 역할은 이번 회차에 남긴다. 하위부터 빠지고 다음 실행 때 다시 판단하므로, 살아 있거나 책임이 남은 역할의 상위 사슬이 보존된다.

`--apply` 때만 쓴다. 인계의 `handovers/.lock`과 등록의 `hierarchy-register.lock`을 함께 잡고
자료를 다시 읽는다. 같은 파일에 열린 인계가 있으면 거부한다. 기존 인계 취소는 파일 지문이
달라지면 원복을 거부하며, 두 잠금을 함께 잡는 것은 확인과 쓰기 사이의 동시 변경도 막기 위해서다.

쓰기 전 원문을 `$KADAN_HOME/.trash/<파일명>.before-prune-<시각>-<고유값>`에 권한 `600`으로
보존한다(기본 홈 `~/.kadan`). 자료 변경·역할 생존 복귀·파일 변경을 다시 확인하고,
`parseHierarchy`를 통과한 결과를 임시 파일 후 이름 바꾸기로 반영한다. 중간에 실패하면
적용하지 않으며 이미 만든 백업·임시 파일은 보존한다. 파일 밖에서 직접 실행한 세션 생성이나
수동 편집까지 잠그지는 못하므로 적용 중에는 같은 역할 재시작·관계표 수동 편집을 겹치지 않는다.
`--apply`는 사람이 직접 칠 때 쓴다. 감시기가 켜져 있으면 [하루 한 번 자동 정리](#감시기의-하루-한-번-자동-정리-2026-10-12)가 같은 규칙으로 따로 적용한다.

### 감시기의 하루 한 번 자동 정리 (2026-10-12)

`kadan watch`에 `--hierarchy`가 있으면 감시기가 24시간에 한 번 위와 같은 정리를 스스로 적용한다. 정리 규칙(유예 24시간·보존 조건·백업·잠금·버전 검사)은 `--apply`와 같고 바뀐 것이 없다.

- **하루 한 번 판단**: 원장의 마지막 `hierarchy-prune` 기록 시각이 24시간 안이면 건너뛴다. 메모리가 아니라 원장을 보므로 감시기를 다시 띄워도 하루 안에는 다시 돌지 않는다. 현재보다 미래인 기록(시계가 앞으로 틀렸던 흔적)은 근거로 쓰지 않고 바로 정리 대상으로 본다.
- **거절·오류도 하루로 센다**: 잠금(`HIERARCHY_LOCKED`·`HANDOVER_LOCKED`)·열린 인계·판정 중 변경 등으로 거절돼도 감시는 멈추지 않고 경보·우편도 내지 않는다. 거절 이유를 `error`에 적은 같은 `hierarchy-prune` 기록이 24시간 시계를 시작해, 인계가 하루 종일 열려 있어도 주기마다 기록이 쌓이지 않는다.
- **원장 기록**: `kind: "hierarchy-prune"`, `by: "watch"`, `file`, `applied`, `removeCount`, `retainCount`, `backup`(지운 줄이 없으면 `null`), `error`(성공이면 `null`). 지운 줄 목록은 넣지 않는다. 원본은 백업 파일이다. 지울 줄이 0이면 파일을 바꾸지 않고 백업도 없지만 기록은 한 줄 남는다.
- **백업 위치**: `$KADAN_HOME/.trash/<관계표이름>.before-prune-<시각>-<무작위>`
- **끄기**: 감시 프로필 `"hierarchy-prune":"off"` 또는 명령줄 `--hierarchy-prune off`. 기본은 켬이며 다른 값은 시작할 때 거부한다. `--hierarchy`가 없으면 정리도 기록도 하지 않는다.
- 정리로 파일이 바뀌면 같은 주기의 관계표 읽기(`hierarchy-loaded`)가 바뀐 지문을 읽어 반영한다(정리가 읽기보다 앞이다).

## 완료·전달·사용자 확인은 별개

- 작업자 완료 편지는 카드에 적힌 직속 감독에게 `kadan send`로 보낸다. 이 옵션은 감시 경로를 바꾸며 작업 카드의 수신자 문장을 자동 수정하지 않는다.
- AI는 발령 뒤 응답 종료·입력 대기한다. 외부 배포는 일회성 대기 프로그램이 결과를 저장하고 CLI로 통지한다. 반복 AI 조회를 하지 않는다.
- 명시된 최상위 경보는 `--user-notify` 유무와 무관하게 사용자 알림을 시도한다(디스코드 설정이 있으면 디스코드, 없거나 실패하면 OS 알림. [사용자 알림](user-notify.md)). 그 옵션은 기존 공통 RED/죽음 알림의 선택 기능으로 남는다. OS 알림 권한·집중모드로 실제 표시가 안 될 수 있으므로 osascript 성공을 사용자가 읽었다는 증거로 취급하지 않는다.
- 알림 실패는 원장 delivered:false와 watch 출력에 남긴다. 감시가 죽거나 OS 알림 자체가 실패한 뒤 자동 복구/재시도를 보장하지 않는다.
- 대시보드의 기존 판 묶음/진행 막대는 카드 원장과 이름에 의한 요약이다. 새 관계표가 대시보드의 모든 분류와 진행률을 고친다고 주장하지 않는다.

## 판별 감시 확인

대시보드와 `kadan tree`가 공유하는 감시 조회 기준은 [판별 감시 조회 기준](watch-overview.md)을 따른다. 직속 관계 설정 반영, 감시기 생존, 감시 주기 정상 여부, 경보 전송 결과를 서로 구분한다.
