# 카드 중앙 관리

## Why

[kyle]이 흩어진 카드의 승인 범위와 실제 실행을 한 화면에서 확인하고, 슈퍼감독과 판단·질문·답변을 같은 카드에 남기도록 한다.

## 설계와 영향 범위

- 카드 원본: KADAN_HOME/cards/<저장소>/<카드ID>/card.md. 내용과 메타데이터를 중앙에 두고, 기존 파일은 보존 백업 후 원본으로 연결한다. 상대 링크 기준은 기존 sourcePath다.
- 결정 이력: 카드별 events.jsonl에 전체 메타데이터 버전을 추가한다. 기존 실행 원장은 수정하지 않는다. 수정은 버전 확인과 잠금으로 충돌을 거부한다.
- 카드 상태: draft(초안), ready(발령 가능), assigned(배정), hold(보류), done(완료), cancelled(취소), archived(과거 자료·미분류). 파일이 있다는 것만으로 발령 승인이 되지 않는다. ready에는 구체적인 승인 범위가 필요하다.
- 판은 명시적인 board로 묶으며, 실행은 역할별 발령/완료 기록이다. 한 카드의 여러 역할 실행을 카드 여러 장으로 세지 않는다. 세션 생존은 진행 근거가 아니다. 옛 미완료 실행은 완료 미확인으로 남긴다.
- 중앙 등록 카드의 발송은 배정한 역할과 판에만 허용한다. 기존 미등록 카드는 호환 경로를 유지하되 별도 미등록 실행으로 보여준다.
- dashboard의 답변·판단 기록 저장은 편지 발송이나 작업 재개가 아니다. CLI로 조회한 슈퍼감독이 승인된 ready 카드만 판에 배정한다. 이번 작업은 주기적으로 AI를 깨우는 자동 발령기를 추가하지 않는다.
- 코드: card-store(저장/버전), card-center(실행 상태 계산), center-wall(화면/API), 기존 CLI와 wall의 진입점. 기존 우편·원장 상세 화면은 별도 링크로 유지한다.
- 검증: 중복 ID, 재발령, 다른 역할 완료, 손상 자료, 보류/초안 발송 거부, 웹 쓰기 출처·버전 충돌, 실자료와 화면 집계 대조, 데스크톱/모바일/편집 검증.

## 명령

```sh
kadan card create repo/card-search --repo-path /절대경로/레포 --source /절대경로/카드.md
kadan card list
kadan card show repo/card-search
kadan card update repo/card-search --revision 1 --status ready --scope '검색 화면 구현·로컬 검수, push/배포 제외' --note '사용자 결정'
kadan card note repo/card-search --revision 2 --kind question --note '검색 결과 정렬은 무엇을 우선할까요?'
kadan card update repo/card-search --revision 3 --status assigned --board search --role search-작업자 --note '승인 범위 그대로 발령 준비'
kadan send search-작업자 --task card-search '중앙 카드 show와 card.md를 함께 읽고 지정 범위 수행'
kadan card link repo/card-search
```

- 질문/답변과 상세 승인 범위는 `card show`로 읽는다. card.md만 읽으면 최신 결정 이력이 빠진다.
- `card link`는 기존 파일이 중앙 복사본과 같을 때만 원본을 보관하고 기존 경로를 심볼릭 링크로 바꾼다. 기존 파일에 추가 변경이 있으면 연결하지 않는다.
- 수집: `node scripts/centralize-cards.mjs /절대경로/레포`로 먼저 목록을 확인한다. `--apply --link`로 가져오고 연결한다. `*-result`, 기준점/보존/인계 증거 파일은 수집하지 않는다.
- 자동 가져오기는 ready를 만들지 않는다. 기존 원장의 완료/발령 상태만 연결하며, 판과 담당이 불명확하면 초안인 채 실행 미확인 표시를 유지한다. 확인되지 않은 과거 본문은 새 구현 승인이 아니다. 발령 흔적도 미발령/승인대기 표시도 없는 옛 자료는 archived로 분리하며 완료 판정으로 쓰지 않는다.
- 기본 대시보드는 미완료 카드를 표시하고 전체/완료 필터로 과거 카드도 볼 수 있다. 카드·판은 명시 계획과 중앙 배정으로 연결한다. 미등록 실행은 별도 보존한다.
- `kadan tree`는 중앙 상태 JSON을 출력한다. 과거 이름별 표시가 필요하면 `kadan tree --legacy`를 사용한다. 대시보드 `?legacy=1`은 기존 우편/실행 상세 화면이다.
- 상태 손상/생존 조회 실패는 모름이다. 질문 저장은 알림 전송이 아니며, 웹 저장은 사람 명의의 로컬 카드 기록이다. `by`는 인증 신분이 아니라 기존 원장과 같은 선언값이다.
- 중앙 데이터는 이 컴퓨터의 KADAN_HOME에 있다. 코드 Git 저장소나 원격 서비스로 자동 게시하지 않는다. 다른 컴퓨터로 이동할 때 cards 디렉토리와 원장을 함께 보존해야 한다.

## 카드 결과와 검증 자료

새 카드는 결과 보고서와 검증 자료를 대상 코드 저장소 밖, 카드와 같은 폴더에 둔다. 작업공간을 옮기거나 역할을 종료해도 카단에서 근거를 찾기 위해서다.

```text
KADAN_HOME/cards/<저장소>/<실행ID>/
  card.md
  result.md
  evidence/
```

`card show <현재실행키>`의 `resultPath`와 `evidenceDir`가 실제 절대경로다. 생성 시 검증 자료 폴더만 준비하며, 보고서가 있는 것처럼 빈 `result.md`를 만들지 않는다. 구현·검수·수정 실행마다 자기 경로를 쓰고 참조 카드나 직전 실행의 결과를 덮어쓰지 않는다. 제품 코드·테스트·계속 사용할 설계/사용 문서는 대상 저장소에 둔다.

수동 실행은 보고서를 완성한 뒤 최신 revision으로 등록한다.

```sh
kadan card show repo/exec-id
kadan card report repo/exec-id --revision 3 --outcome implemented
```

결과의 경로·SHA256·바이트 수·판정·작성자·시각을 기존 카드 이력에 추가한다. 긴 보고서 본문은 원장에 복사하지 않는다. `implemented`는 구현 종료, `pass`·`changes`는 검수 판정, `exception`은 판단 필요, `ok`·`failed`는 일반 실행 결과다. **결과 등록은 카드 상태·DONE·업무 완료를 바꾸지 않는다.** 기존 완료 통지와 마커 절차를 이어간다.

등록 후 같은 결과를 다시 등록하면 이력을 늘리지 않는다. 등록한 보고서는 보존하며, 수정·재검수는 후속 실행의 결과로 남긴다. 등록 뒤 통지 실패 등 추가 상황은 카드 메모나 `evidence/`에 남긴다. 파일 외부 편집을 막는 기능은 아니며, SHA256은 등록 당시 내용의 지문이다.

자동 실행은 기존 `work auto-report`가 현재 실행의 경로를 기본으로 사용하고, 프로그램이 파일과 완료 근거를 확인할 때 카드 결과도 등록한다. 별도 `card report`를 추가하지 않는다. [자동 전달](automatic-review.md)을 따른다.

이전 카드는 새 경로를 강제하거나 파일을 옮기지 않는다. `resultPath`가 없는 카드는 기존 지정 경로를 유지하며, 결과를 등록하려면 `--result-file /기존/절대경로`를 명시한다. 새 카드의 외부 경로 지정은 거부한다. 결과 원문과 `evidence/`는 DB 밖 파일이므로 **DB와 `cards/`를 함께 백업**한다.

## 진행 보고

여기서 진행 보고는 카드의 상태 기록이며, 상대 AI에게 보내는 편지(`send`)와 다르다. 상태 기록 뒤 상위에 같은 내용을 별도 발송하지 않는다. 편지가 필요한 경우는 [진행 기록과 상위 통지](../skills/kadan-conductor/references/operating-contract.md#진행-기록과-상위-통지)를 따른다.

배정된 역할은 시작·외부 결과 대기 등 상태 전이마다 `KADAN_ROLE=<담당> kadan card progress <키> --revision N --activity running|waiting|unknown --note <현재 근거>`로 1회 기록한다. 현재 담당의 미완료 발령 이후 유효한 기록이고 역할 PID가 일치하면 작업 중/결과 대기 상태를 시간 제한 없이 유지한다. 마지막 기록 시각은 별도로 표시한다. 완료·실패·보류, 재발령·담당변경·세션 소실·PID 불일치/조회실패가 확인되면 상태를 다시 판단한다. 오래된 기록만으로 미확인으로 바꾸거나 AI 타이머·반복 기록을 만들지 않는다.

## 사용자 결정과 내부 기록

일반 card note의 question/answer는 감독 사이의 내부 기록이다. 사용자 답변 대기는 슈퍼감독이 별도로 올린 `decision request`만 집계하며, 대시보드의 전용 답변은 `decision answer`와 같은 처리로 저장·요청자 통지를 수행한다. [사용자 결정 절차](decisions.md)를 따른다. 새 GNB의 우편·실행·원장은 새 화면에서 읽으며 legacy는 참고 경로로만 남는다.

## 사람이 읽는 첫 화면과 서기

첫 화면은 현재 판의 목표, 최근 작업, 남은 카드 묶음, 명시 사용자 결정, 비서에게 확인할 질문을 보여준다. 끝난 판과 판 미지정 옛 실행 기록은 접어 둔다. 막대는 카드 수 기준이며 구현·조율·검수 카드를 함께 포함하므로 제품 완성률로 해석하지 않는다.

`kadan card brief <저장소/카드ID> --revision N --title '쉬운 제목' --workstream '작업 묶음' --stage '구현' --summary '확인한 내용' --next '다음 일' --blocker '막힌 이유' --goal '이번 판의 목표'`

- 별도 서기 세션·AI 모델 호출·폴링은 없다. 코드 서기가 원본 상태를 짧은 문장으로 바꾸고, 지문이 동일하면 서버 메모리의 요약을 재사용한다. 화면 조회는 파일을 수정하지 않는다.
- 쉬운 제목과 묶음은 필수이며, 나머지는 선택이다. 단계는 구현/검수/통합/프리뷰 확인/조율/조사/기타. 자동으로 단계를 추측하지 않는다. 목표는 판 전체를 설명하는 조율 카드에 기록한다.
- 설명은 카드 폴더의 briefs.jsonl에 추가한다. 기존 card.md/events.jsonl 및 실행 원장을 수정하지 않고, 발령·완료·승인 변경을 하지 않는다. 원본 버전이 바뀐 상태에서 설명을 저장하면 거부한다.
- 제목/묶음/단계/목표는 원문 제목과 본문이 같을 때만 재사용한다. 진행 설명/다음 일/막힌 이유는 원본 버전이 달라지면 현재 사실로 표시하지 않는다. 카드 상세에서 원본을 확인할 수 있다.
- 감독 또는 서기는 기존 보고 작성 시 필요한 경우 설명도 갱신한다. 설명을 위해 감독을 주기적으로 깨우지 않는다. 자연어를 자동으로 다시 쓰는 AI 서기는 이번 기능에 포함하지 않는다.
- ‘질문 복사’는 클립보드에만 복사한다. 실제 우편 전송은 하지 않으며, 사용자 결정 요청은 decision CLI 경로만 인정한다.

유효한 시작/결과 대기 보고가 없는 발령 카드는 ‘발령됨 · 마지막 보고 N분 전’으로 표시한다. 진행 보고가 없으면 없음으로 표시하고 카드 수정 시각으로 대체하지 않는다. 재발령 이전 보고는 새 발령에 포함하지 않는다. 순서 대기 기록은 현재 별도로 없으므로 발령된 작업을 다음 큐로 추측하지 않는다. 발령 가능은 순서가 확정되지 않은 후보로 표시한다.

대시보드의 카드 링크는 현재 화면 위의 상세 창으로 열린다. 닫기/Escape로 원래 위치로 돌아오며 상세를 읽는 동안 자동 새로고침을 멈춘다. 카드 저장은 기존 버전 검사 경로를 사용하고 창 안에서 결과를 갱신한다. 카드 탭 및 새 탭 열기 링크는 기존 경로를 유지한다.

그래프 구간·카드 라벨·보고 시각을 해석하는 기준은 [대시보드 상태·색상 안내](dashboard-status-guide.md)를 따른다. 화면의 ‘상태·색상 안내’에서도 짧게 확인할 수 있다.

## 실행 작업과 관리 기록

- `workType=execution`은 실제로 수행하는 구현·검수·설계·판단 작업, `coordination`은 감독의 조율·결과 취합·대기를 담는 관리 카드다. 역할이 감독이어도 독립적인 실행 작업은 execution이다. 담당자 이름으로 자동 분류하지 않는다.
- CLI `card create`/`card update`의 `--work-type execution|coordination`, 카드 상세의 종류 선택으로 지정한다. 생략한 기존 카드는 execution으로 읽는다. 새 조율 카드는 coordination을 명시한다.
- 첫 화면의 지금 하는 일/남은 실행 작업/막대는 execution만 센다. 조율 카드는 판 아래 접힌 관리 기록에 보존한다. 카드 전체 목록과 원장 상태는 유지한다.
- 현재 담당은 카드에 배정된 역할, 관리 감독은 검증된 직속 상위에서 표시한다. 담당이나 상위가 불명확하면 확인 전으로 표시한다.
- 별도 구현 카드와 검수 카드를 같은 기능이라는 이유만으로 합치지 않는다. 집계 단위는 실행 카드이며, 감독에게 결과를 보고한다는 이유로 할 일을 한 장 더 세지 않는다.
- `kadan tree`와 `/api/cards`의 `executionSummary`는 전체 실행 카드 요약이고 기존 `summary`는 관리 카드를 포함한 원본 집계다. 첫 화면은 열린 판의 실행 카드에 한정한다. 관리 카드만 미완료이면 남은 실행 작업0과 관리 기록을 함께 표시한다.

## 상태 이유와 다음 조치

상태 변경 시 `--note`는 필수이며 변경자·시각·변경 전후는 중앙 카드 이력으로 보존한다. 작업 중/결과 대기는 `card progress`의 실제 보고로 구분한다. 일반 메모는 상태 이유를 덮지 않는다.

```sh
kadan card update 저장소/카드 --revision 3 --status hold --note '방향 변경으로 보류' --resolution-owner '판-감독' --next-action '검수 자료를 새 카드에 넘긴 뒤 종료'
kadan card update 저장소/카드 --revision 4 --status-reason '검색 방식 변경' --note '보류 설명 보완'
```

후속 담당·다음 행동은 모든 상태에서 선택적으로 기록한다. 보류에서 미기록이면 감독 확인 필요로 표시한다. 명시적인 사용자 결정은 전용 decision 원본에서 읽는다. 상태/진행 단계 전환 시 이전 후속 조치는 초기화된다. 웹은 입력한 후속 항목을 함께 저장하므로 새 단계에 맞게 바꾼다. 저장 자체는 실행 재개나 우편 발송이 아니다. 기존 원장·우편은 증거이며 상태 설명을 자동 추론하는 입력으로 사용하지 않는다.

## SQLite 저장소

명시적으로 전환한 저장소에서는 카드 변경 이력·현재 상태와 사용자 결정·brief가 kadan.sqlite에 저장된다. card.md·result.md·evidence/와 sourcePath 심볼릭 링크는 유지한다. 전체 이전·복구 시 DB와 파일을 함께 보존한다. [절차와 경계](sqlite-storage.md).

### 근거 폴더 용량

검증 자료 폴더에는 재현 명령·선별한 로그·스크린샷을 둔다. 저장소 복제본·worktree·의존성·빌드 캐시는 제품 작업 공간에 두고 경로·커밋·명령으로 연결한다. 기존 자료는 보존하며 자동 이동·삭제하지 않는다.

### 터미널 출력 로그

새 tmux 세션은 원문 바이트를 빠른 gzip 압축으로 `out/<세션>.log.gz`에 뒤이어 보존한다. 같은 역할의 후속 세션은 gzip 멤버를 추가하며 `gzip -dc <절대경로>.log.gz`로 순서대로 복원한다. 실행 중에는 마지막 멤버가 아직 닫히지 않아 복원 명령이 종료부 부족을 표시할 수 있으므로, 완전한 검증은 해당 세션 종료 뒤 한다. gzip이 없으면 경고와 함께 기존 `.log` 기록을 유지한다. SQLite·로티 바닥의 기록 방식과 화면에서 DONE을 판정하는 경로는 바꾸지 않는다.

기존 `.log`·카드 근거·동결 JSONL은 이동하거나 삭제하지 않는다. 이 변경은 앞으로의 증가량을 줄이며 기존 공간을 회수한 것은 아니다.
