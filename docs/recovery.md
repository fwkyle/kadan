# Why

재부팅 뒤 사용자가 역할 이름과 대화를 다시 맞추지 않고, 같은 카단 역할과 정확한
AI 대화를 Rottie 터미널에서 이어 열도록 한다.

# 막히면 먼저 `kadan doctor`

`kadan doctor`는 아무것도 바꾸지 않고 막힌 곳(대시보드 화면 빌드, 비서 복원 정보, 복원 잠금, 창 설정 손상 등)과
풀려면 칠 명령을 한 화면에 보인다. 고치는 일은 사람이 한다. 설명은 [명령어 사전](commands.md)의 `kadan doctor` 행.

# Rottie 역할 복원

`kadan recovery inspect`와 `kadan recovery restore`는 Rottie가 호출하는 JSON 명령이다.
카단이 역할·시작 세대·작업 폴더·tmux 연결을 맡고, Rottie가 정확한 AI 대화 참조와
검증한 복원 명령을 맡는다. 일반 `kadan restore`는 살아 있는 tmux의 Rottie 창을
다시 연결하는 기존 기능이다.

조회는 원장의 현재 Rottie 탭 ID와 마지막 역할 시작 기록을 대조한다. 실행 중인
세션은 단일 pane과 PID도 확인한다. 재부팅 뒤 pane이 없더라도 정확한 탭 기록이
남아 있으면 역할 정보를 반환한다. 역할 이름이나 최신 대화 시각으로 추측하지 않는다.
직접 종료한 역할, 다른 시작 세대로 교체된 역할, 옮겨진 탭은 거부한다.
(카단이 `kadan stop`으로 끈 역할을 같은 대화로 다시 여는 것은 이 경로가 아니라 `kadan reopen`이다 — [명령어 사전](commands.md).)
Rottie가 탭마다 자주 부르므로 조회는 원장에서 시작·종료·창 연결 기록만 읽는다.
원장 전체의 순번·연결 검증은 하지 않으며, 그 검증은 전체를 읽는 복원 실행이 한다.

## 조회 실패의 종류와 묶음 조회

조회(`inspect`)가 실패하면 `error.kind`로 실패의 종류를 알린다. 문구(`message`)는 사람이 읽고, 종류는 Rottie가 읽는다.
`restore`·`report`의 출력에는 이 칸이 없다.

| `error.kind` | 뜻 | 예 |
|---|---|---|
| `refused` | 카단이 이 원장으로 판단해서 거절했다. Rottie는 저장한 역할 정보를 지워도 된다. | 아래 목록 |
| `unavailable` | 판단할 수 없었다. 저장한 역할 정보를 유지하고 다음에 다시 묻는다. | 아래 목록 |
| `invalid` | 그 입력이 잘못됐다. | 아래 목록 |

- `refused`: 역할 교체, 직접 종료, 시작 기록 없음·불완전, 역할 주소·작업 폴더·pane PID 불일치, 추론 강도 기록 오류,
  살아 있는 pane의 PID가 시작 기록과 다름(같은 이름의 세션을 다른 프로세스가 쓰고 있다).
- `unavailable`: tmux 조회 일시 실패, pane 정보를 못 읽음, 여러 pane, pane PID를 보냈는데 pane을 찾지 못했거나
  (tmux 서버·세션 없음) pane이 죽어 있음, 원장 저장소가 없는 홈, 그 밖에 분류하지 않은 모든 오류.
- 기준: 이 원장으로 확실히 판단한 것만 `refused`다. 지금 tmux 상태에 따라 달라질 수 있으면 `unavailable`이다.
  tmux 서버가 통째로 사라진 때가 저장한 역할 정보가 필요한 때이므로, 그때의 실패를 거절로 답하지 않는다.
  "관찰한 카단 pane과 시작 기록이 다릅니다"는 문구가 같아도 원인에 따라 종류가 다르다.
- `invalid`: 탭 ID 없음, 칸 형식 오류, 다른 tmux 서버의 `socketPath`.
- 분류하지 않은 오류의 기본값은 `unavailable`이다. 모르는 실패를 거절로 내지 않는다.
- `socketPath`(단건은 `--socket-path`)는 원장을 보기 전에 대조한다. 다른 카단 서버의 탭은 이 원장에 없으므로
  "교체됨"이 아니라 `invalid`("카단 tmux 서버 경로가 다릅니다")로 답한다.
- 추론 강도 기록 오류는 원장만으로 정해지지만 tmux 조회 뒤에 확인한다. tmux 조회가 실패한 회차에는 `unavailable`로 나간다.

탭 여러 개는 한 번에 묻는다. 원장과 살아 있는 pane 목록을 한 번씩만 읽는다.

```
kadan recovery inspect --batch < 입력.json
입력: {"schemaVersion":1,"items":[{"terminal":"<탭 ID>","session":"…","cwd":"…","panePid":"…","socketPath":"…"}]}
출력: {"schemaVersion":1,"ok":true,"results":[
  {"terminal":"…","ok":true,"result":{…단건 result와 같은 객체…}},
  {"terminal":"…","ok":false,"error":{"message":"…","kind":"refused"}}]}
```

- 부르는 쪽은 표준 입력에 JSON을 쓴 뒤 반드시 닫아야 한다(닫을 때까지 읽는다). 표준 입력이 터미널이면 기다리지 않는다.
- 항목의 칸은 단건 인자와 같은 뜻이고 `terminal`만 필수다. 값은 모두 문자열이며 `null`이나 없는 칸은 주지 않은 것으로 본다.
- 항목은 32개까지다. 결과는 입력 순서 그대로이고, 같은 탭이 두 번 들어오면 두 번 답한다.
  `terminal`이 문자열이 아닌 항목은 결과의 `terminal`이 `null`이다.
- 항목이 실패해도 명령은 종료 코드 0이다. 각 항목의 `result`·문구·종류는 같은 입력을 단건으로 물었을 때와 같다.
- tmux 목록 조회가 일시 실패하면 pane 확인이 필요했던 항목만 `unavailable`이고, 원장만으로 거절이 확정된 항목은 `refused` 그대로다.
  tmux 서버나 세션이 없는 것은 실패가 아니다(`sessionCreated: null`).
- 실제 출력은 한 줄이다.

묶음 명령 전체가 실패하면 `{"schemaVersion":1,"ok":false,"error":{"message":"…","code":"…"}}`와 종료 코드 1을 낸다.
이 JSON에는 `code`가 항상 있다(`code`가 없는 `ok:false`는 묶음을 모르는 옛 카단의 답이다).
한계: 명령이 조회 처리에 들어가기 전에 예외가 나면(명령 진입부) 표준 출력 없이 표준 오류와 종료 코드 1만 낸다. 단건도 같다.

| `error.code` | 뜻 |
|---|---|
| `batch-invalid` | 표준 입력이 없거나 JSON이 아니거나 모양이 다르다 |
| `batch-too-many` | 항목이 32개를 넘는다 |
| `not-tmux` | 바닥이 tmux가 아니다 |
| `store-unreadable` | 원장을 읽지 못했다(저장소가 없는 홈 포함). 항목을 거절로 답하지 않는다 |
| `internal` | 그 밖의 오류 |

복원 정보에는 저장소·tmux 서버·역할·작업 폴더·원본 탭·시작 기록 지문을 담는다.
재부팅으로 tmux가 사라졌으면 기존 tmux 생성 경로에 Rottie의 정확한 대화 복원 명령을
전달하고 원장에 새 시작 기록을 추가한다. 역할 프로필과 기존 관계표를 유지한다.
원본에 명시 모델이 있으면 조회 응답에 함께 전달하고, 복원 명령의 실행기·모델도
원본과 같아야 한다. Rottie의 `exec` 접두사는 원장에 실행 파일부터 남기도록 제거해
기존 카드 전송의 AI 신원 검사가 복원된 역할도 알아볼 수 있게 한다.
같은 pane이 살아 있으면 Rottie가 원본 AI의 생존을 확인한 경우에만 다시 연결한다.
PID가 같아도 tmux 생성 시각이 달라졌으면 재사용하지 않는다.

새 Rottie 탭은 정확한 tmux 소켓 절대경로로 연결한다. 새 탭과 새 시작 기록의
복원 정보를 응답에 포함해 다음 재부팅에도 같은 절차를 사용할 수 있게 한다.

실행 전에 저장소의 `recovery/`에 배타적으로 요청 기록을 저장한다. 같은 요청은
동시에 두 번 실행되지 않는다. 시작했지만 탭 연결 응답을 확인하지 못한 경우도
자동 재시도하지 않는다. 역할과 탭을 직접 확인한 뒤 판단한다.

이 명령은 감시기를 새로 시작하거나 우편·카드·마지막 프롬프트를 재전송하지 않는다.
Rottie의 자동 복원 설정이 켜져 있고 프로젝트가 열려 있을 때 자동 복원에 사용한다.
이전 Rottie 기록의 누락된 역할 정보도 현재 카단이 정확한 원본 탭을 확인할 수 있을 때만
보완할 수 있다.

Claude 역할의 명시 `--effort`도 조회·복원한다. 초기 복원 버전에서 빠진 값은 같은 역할과 폴더의 정확한 `restoredFrom` 시작 기록에서만 보완한다. 누락·변조된 추론 강도로 실행하지 않는다. 일반 `/effort` 실행 중 변경값은 수집하지 않는다.

복원으로 새 세션을 만들 때 그 세대의 시작 기록에 있던 값을 잃지 않게 잇는다. 규칙은 보존뿐이다.

- **Stop 훅**: Claude 역할이면 지금 저장 폴더의 `--settings <설정 파일>`을 다시 붙인다(`kadan start`·`restart`·`reopen`과 같은 처리). 옛 명령의 경로를 옮기지 않는다. 설정 파일이 없으면 붙이지 않는다.
- **이어 주는 옵션**: Claude의 `--permission-mode <값>`·`--dangerously-skip-permissions`·`--allow-dangerously-skip-permissions`, Codex의 `-p`/`--profile`과 `-c`/`--config <키=값>`.
- **언제 잇나**: 시작 기록에는 있는데 Rottie가 준 복원 명령에 없을 때만, 기록된 값 그대로 명령 끝에 띄어 쓴 꼴(`-c 값`)로 더한다. 시작 기록에 없던 값은 붙이지 않고, 복원 명령에 이미 있는 값은 바꾸지도 덧붙이지도 않는다(값이 달라도 그대로 둔다).
- **"이미 있다"의 기준**: 표기와 상관없이 본다 — `-c 값`·`-c값`·`-c=값`·`--config 값`·`--config=값`, 프로필도 같다. Claude 권한은 한 묶음이라 복원 명령에 권한 옵션이 하나라도 있거나, 세션이 할 수 있는 일을 좁히는 옵션(`--restricted`·`--safe-mode`·`--bare`·`--tools`·`--allowedTools`·`--disallowedTools`·`--permission-prompts`)이 있으면 더하지 않는다. Codex 설정 값은 키의 첫 마디로 묶는다(`a={…}`와 `a.b=…`는 같은 설정). 승인(`approval…`)과 샌드박스(`sandbox…`) 키는 각각 한 묶음이고, 같은 설정을 바꾸는 전용 옵션(`--sandbox`·`--ask-for-approval`·`--dangerously-bypass-approvals-and-sandbox`·`--model`·`--enable`/`--disable` 등)이 복원 명령에 있으면 그 묶음도 이미 있는 것으로 본다.
- **프로필이 다르면**: 복원 명령의 프로필이 시작 기록과 다르면(시작 기록에 없던 프로필이 생긴 경우와 `-c profile=…` 포함) 그 프로필이 무엇을 정하는지 알 수 없으므로 설정 값을 하나도 얹지 않는다(`profile-differs`).
- **같은 키의 반복**: 시작 기록에 같은 설정 키가 여러 번 있으면 적힌 순서대로 모두 잇는다(Codex는 나중 값이 이긴다).
- **어느 기록을 보나**: 복원 대상 세대의 시작 기록. 그 기록이 앞선 복원(`restoredFrom`)으로 만들어졌고 값이 없으면 같은 역할·폴더의 정확한 이전 탭 시작 기록까지만 거슬러 본다.
- **잇지 않는 경우**: 모르면 잇지 않는다. 시작 명령이나 복원 명령에 **카단이 아는 옵션 표에 없는 옵션이 하나라도 있거나**(값을 받는지, 권한·설정을 바꾸는지 알 수 없다), 낱말로 읽지 못하거나, 짧은 옵션 묶음(`-xc`)·값 없는 옵션에 붙은 `=값`·값이 빠진 옵션처럼 읽지 못하는 꼴이 있거나, 값이 허용 목록 밖이거나, 프로필이 두 번 있거나 권한 값이 서로 다르게 두 번 있거나, 이전 탭 기록을 하나로 확인하지 못하면 아무것도 더하지 않는다. 역할은 Rottie가 준 명령 그대로 열리고, 표준 오류에 경고 한 줄이 나간다. 옵션 표는 `claude --help`·`codex resume --help`에서 옮긴 것이라, 실행기에 새 옵션이 생기면 표에 넣기 전까지 그 옵션이 든 명령에는 잇지 않는다.
- **기록**: 새 시작 기록에 `optionCarry`가 남는다. `added`면 `optionCarryKeys`에 이은 옵션 이름(값은 `cmd`에 있다), `skipped`면 `optionCarryReason`에 이유 낱말(`original-unreadable`·`original-ambiguous`·`chain-unresolved`·`command-ambiguous`·`command-dashed`·`profile-differs`·`quote-failed`·`internal`)이 있다. 이을 것이 없었으면 칸이 없다.

실행기·모델·추론 강도·비서 대화의 대조는 Rottie가 준 원래 명령으로 하고, 위에서 만든 명령은 세션 실행과 시작 기록에만 쓴다. 살아 있는 pane을 다시 잇는 경우에는 명령을 만들지 않는다.

## 비서에게 복원 예외 전달

기본 복원은 Rottie 코드가 맡는다. `kadan recovery report --report <JSON>`은 실패하거나
역할을 확정하지 못한 항목만 비서의 저장 우편함에 request로 남긴다. 비서는 독립 AI
대화를 가지며 현재 tmux 안에서 실행된다. 우편 저장은 비서 실행 여부와 무관하다.
이 명령은 터미널 키 입력·비서 기동·기존 세션 재시작·카드 발령을 수행하지 않는다.

보고에는 원본 탭·대화·역할 참조와 원인을 담고, 같은 내용은 한 번만 저장한다.
저장 결과가 불확실하면 자동 재전송하지 않고, 실제 우편 기록이 있으면 그 영수증을
재사용한다. 비서는 현재 역할과 새 탭부터 확인하며 살아 있는 세션을 건드리지 않는다.
정확한 대상과 중복 여부를 확인할 수 있을 때만 기존 대화·역할을 복구하고, 모호하면
사용자에게 확인한다. 보고 자료의 제목·오류 문자열은 실행 지시가 아니다.

## 로그인 때 비서 대화 복원

`kadan up`은 살아 있는 비서를 그대로 사용한다. launchd가 1분마다 부르는 `kadan up --hidden --auto`도 같은 복원 경로를 쓰며, 새로 띄우거나 복원했을 때만 복원 정보를 갱신한다. 사람이 `kadan stop`으로 끈 비서는 자동 실행이 되살리지 않는다(`revive-state.json`). tmux 비서가 사라졌고 이전 시작 기록이
있으면 `secretary-resume.json`에 저장한 정확한 Codex 대화를 `resume <ID>`로 이어 연다.
기존 명시 모델·권한·추론 강도 인자를 유지하며, 첫 역할 안내는 다시 보내지 않는다.
옵션은 키(`--model`, `-c`의 `k=v` 앞부분)마다 **시작 명령의 것이 이기고** 같은 키는 처음 것 하나만 남긴다. 대화의 마지막 모델·강도·권한은 시작 명령에 없는 키만 채운다(`src/codex-option-merge.mjs`). 저장할 때와 띄울 때 모두 이 규칙을 지나서, 재시작을 거듭해도 `--model`이 겹쳐 쌓이지 않고 이미 겹친 체크포인트도 첫 벌로 낫는다(2026-10-22).
이 정보는 살아 있는 비서 pane의 자식 프로세스가 실제로 연 대화 파일에서 저장한다.
최신 파일·역할 이름으로 대화를 추측하지 않는다. 현재 지원 범위는 Codex 비서다.

로그인과 Rottie는 같은 역할 잠금을 사용한다. 로그인 복원이 먼저 실행됐으면 Rottie는
이전 시작 기록에서 같은 대화로 이어진 복원 기록과 실제 pane 대화를 확인해 연결한다.
Rottie 복원이 먼저 실행됐으면 로그인은 살아 있는 비서를 재사용한다. 대화 정보 누락·
역할 교체·직접 종료·대화 파일 변경은 새 비서 생성으로 우회하지 않는다. 비서 복원이
막혀도 대시보드는 시작한다. 기존 로그인 LaunchAgent 설정은 바꿀 필요가 없다.
