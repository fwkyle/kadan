# kadan 설계 원칙과 잠긴 규칙

이 문서는 카단이 왜 이렇게 생겼는지와 무엇을 바꾸지 않는지의 원본이다. 구성요소와 원장의 관계는 [구조 기준](architecture.md), 신규 사건의 저장·연결은 [원장 계약](mail-task-ledgers.md)을 따른다. 기여 절차와 코드 변경 규칙은 `CONTRIBUTING.md`에 있고, 그 이유가 여기 있다.

카드 주소·과거 실행 연결·DONE 호환은 [카드 주소 규칙](task-identity.md)을 따른다.

## Why

사용자가 여러 AI CLI(claude, codex 등)를 역할별로 띄워놓고, 메시지를 주고받고,
멈췄는지 감시하고, 필요하면 직접 창에서 개입하고 싶다. 본 카단(관제층)의 1달 실험에서
배운 결론 — 안전 규칙이 흐름보다 앞서면 흐르지 않는다 — 을 반영해, **먼저 흐르는
심플 1차로**를 이 레포가 담당한다.

카단 라이트 작업을 시작할 때 [진행·승인 공통 기준](skills/kadan-conductor/references/operating-contract.md)을 읽고 단순화 규칙을 적용한다. 규칙 원문은 그 문서 한 곳에서 관리한다.
진행을 기록하거나 상위에 편지를 보낼 때는 같은 원문의 [진행 기록과 상위 통지](skills/kadan-conductor/references/operating-contract.md#진행-기록과-상위-통지)를 따른다.

## 작업 크기에 맞는 경로

[가벼운 실행이 기본](skills/kadan-conductor/references/operating-contract.md#가벼운-실행이-기본-2026-09-10-사용자-정정)을 먼저 적용한다. 작은 직접 작업에는 카드/역할을 만들지 않는다. 위임할 큰 작업만 기존 업무와 자동 전달을 사용하고, 정상 전달 확인과 결과 기록을 중복하지 않는다. 아래 업무·실행 절차는 실제 카단에 연결할 작업의 기준이다.

## 정체성

- 이 저장소는 카단(kadan)의 심플 코어다. 이전 카단 구현(관제층)은 동결 보존하며 이 저장소가 대체하려는 것이 아니다.
- **tmux는 지금의 바닥이지, 영원한 바닥이 아니다.** 나중에 로티 같은 다른 바닥으로
  이동할 수 있다. 중요한 것은 바닥이 아니라 코어다 — 원장·안전장치·명령 인터페이스
  (`start/send/done/wait/read/status/log/attach/stop`)·DONE 마커 규약은 바닥과 분리해
  유지하고, 바닥을 바꿀 때 코어는 그대로 갖고 간다.
- 실행 도구(provider) 어댑터를 만들지 않는다. 어떤 CLI든 바닥의 세션 안에 띄우면
  지원되는 것이다.
- 사람이 실제로 보고 개입하는 것이 목표다. `start`는 창을 열고, `attach`는 언제든 다시 연다.
- headless(`claude -p` 등)를 기본으로 쓰지 않는다. 대화형 TUI 그대로가 기본이다.

### 바닥 자격 기준 — 두 부류 (2026-08-30 관리자 결정)

바닥은 두 부류다. 부류마다 자격이 다르다.

**명세·서버 바닥(tmux)** — 네 개를 모두 충족해야 한다.

- (a) 앱·화면 없이 소켓만으로 7함수+선택 1(만들기·살아있나·PID·밀어넣기·
  읽기·종료·목록 + 변화 대기)이 동작한다.
- (b) Linux 서버(화면 없음)에서 동작한다.
- (c) 아무 터미널에서 attach할 수 있다.
- (d) 라이트 12장 왕복 + 서버 왕복 1회를 통과한다.

tmux는 (a)(b)(c)를 충족했고 (d)는 Mac에서 통과했다(서버 왕복은 서버가 생기면).

**제품판 바닥(rottie)** — GUI 제품이라 (a)(b)(c)는 설계상 해당 없다. 자격은
(d) 12장 왕복 + 아래 전제를 문서에 명시하는 것이다.

- 앱이 떠 있어야 한다(`ROTTIE_APP_NOT_RUNNING`은 typed로 그대로 보고, 자동 기동 없음).
- 빌드마다 소켓·데이터·데몬이 따로다. 실측 대상은
  Rottie dev 빌드 실행 파일(`KADAN_ROTTIE_BIN`)이고, start 원장에 create 응답의
  `runtime.build`를 `rottieBuild`로 적으며, 빌드가 다른 앱을 한 원장에 섞지 않는다.
- Cmd+Q는 종료 팝업대로 터미널을 닫는다. 데몬 PTY 생존은 강제 종료·안전 재시작 경로에서만
  성립한다(card-18 11번).

**등록 현황(2026-08-30 관리자 등록):** tmux(명세·서버), rottie(제품판). rottie 등록
근거는 2026-08-30 12장 왕복 표(Local build `8938ad06`, 관리자 작업장 기록)다. dev 빌드 재검증(card-19)과 일회성 `ROTTIE_INTERNAL` 재현은 남은 과제다.

### 바닥 병존 조건 (4개)

- 바닥 = 파일 하나 + 함수 7개 + 선택 1개. 기계당 하나, `KADAN_FLOOR`로 설치 때
  고정한다.
- 런타임 전환·자동 폴백·capability 등급은 만들지 않는다.
- 두 바닥이 병존하려면 둘 다 같은 12장 왕복을 통과해야 한다.
- 세 번째 바닥은 없다(herdr 포함 — herdr는 attach·상태 감지의 참고 소스일 뿐이다).

## 잠긴 최소 규칙 (이것만은 지킨다)

1. **원장은 append-only다.** `~/.kadan`(또는 `$KADAN_HOME`)의 `storage.json`으로 저장 방식을 선택한다.
   현재 원본은 `kadan.sqlite`의 events이고 기존 JSONL은 동결 보존한다. 사건 수정·삭제·재정렬 금지.
   신규 사건은 같은 SQLite 안의 작업(tasks)·우편(mail)·시스템(system) 스트림으로 나눈다. 작업 영역은 기존 works/cards 상태 이력도 포함한다. 기존 ledger 이력은 불변이며 통합 조회는 호환용이다. [원장 계약](mail-task-ledgers.md)을 따른다.
   직접 JSONL을 쓰지 않고 CLI/저장 모듈을 사용한다. 전환·복구는 `docs/sqlite-storage.md`를 따른다.
2. **밀어넣기 직전에 생존을 확인한다.** `send` 전에 `has-session`과 pane PID 대조를
   매번 수행한다. 세션이 없거나 PID가 다르면 보내지 않고 보고한다(실패 닫힘).
   카드 연결 전송(`--task`, 발령으로 추론된 `--execution`, 자동 전달)은 여기에 더해
   현재 세대를 시작한 명령이 등록 실행기(codex·omo·claude·devin)이고 모델이
   지정됐는지(`--model`/`-m`)를 원장의 start 기록과 현재 pane PID로 확인한다.
   인증 환경만 준비하고 실행기로 exec하는 `kadan-<실행기>` 래퍼(예: `~/.kadan/bin/kadan-claude`)는 그 실행기로 읽는다.
   명령은 인용을 보존해 인자 단위로 읽으며 셸 결합·주석·확장은 거부한다.
   프롬프트 문자열 속 모델 옵션이나 `--` 뒤의 옵션은 모델 지정으로 인정하지 않는다.
   tmux 카드 전송은 버퍼 준비 전과 붙여넣기 직전에 `pane_dead`, 같은 pane PID,
   입력을 받는 전경 프로세스 그룹에 속한 pane 프로세스/자식의 실행 파일 또는
   Node/Bun 스크립트 이름을 대조한다. 뒤에서 실행 중인 AI만으로는 허용하지 않는다.
   입력 줄은 커서가 있는 프롬프트 줄(`›`·`>`·`❯`·devin `❭`) 하나다. 화면 전체의 프롬프트 모양 줄을
   후보로 세지 않는다 — codex 배너(`│ >_`)·과거 프롬프트 때문에 실제 대기 화면을 거부한 사고(2026-09-23).
   그 위쪽 가장 가까운 글 줄도 프롬프트 모양이면 여러 줄 입력과 구별할 수 없어 보류한다.
   입력 상자 윗줄은 0열에서 pane 폭을 채우는 가로줄(표지 허용)이며, 입력 상자(devin·claude)는 바로 아래 닫는 가로줄 밑을 상태줄로 보고, 상자가 없으면(codex) 빈 줄 뒤 상태줄 한 줄만 허용한다.
   프롬프트 뒤 글은 실제 화면에서 확인한 빈 입력 자리표시자만 빈 입력으로 본다(작업 중 자리표시자는 제외).
   커서가 프롬프트 줄 밖이거나 이 모양과 다르면 보류한다. 프롬프트가 없거나 미제출 텍스트가 있거나 빈 입력창을 확인하지
   못하면 전송하지 않는다. 이는 화면에 보이는 빈 입력의 확인이며 AI 인증·모델 응답
   성공을 증명하지 않는다. 복사모드 검사는 기존 공통 전송 경계를 재사용한다.
   이 tmux 프로세스·입력 검증은 Rottie 바닥의 실측을 대신하지 않는다.
   실제 전경 AI 프로세스의 명시 모델도 시작 기록과 대조한다. 불일치·미확인이면 거부한다.
   빈 셸·비AI 명령·모델 미지정·이전 세대 신원만 남은 pane에는 카드를 붙여넣지
   않는다 — 일반 우편·질문·답장은 이 경계를 거치지 않는다(2026-09-21 --profile
   단독 시작 사고).
3. **원인을 모르는 실패에는 재시도하지 않는다(모호하면 실패 닫힘).** 다만 **네트워크·프록시
   오류처럼 원인이 식별된 실패는 다시 돌린다. 같은 지점에서 3회 반복되면 멈추고 보고한다.**
   watch는 프로세스를 자동 재시작하지 않는다. 2026-09-10 사용자 승인 예외로, 최종 429 뒤 활성 작업자의 빈 입력창에 1/2/3분 제한 재개를 최대3회 전달한다. 명시 일일한도·잔액 부족, 보류·완료·새 입력은 제외한다. 상세는 `docs/rate-limit-retry.md`. 다른 실패의 재개는 감독의 판단이다.
   실패 조건에 관련된 새 근거가 생겼을 때의 제한된 복구 확인과 소유 역할 교대는
   [일반감독의 결정 범위](skills/kadan-conductor/references/operating-contract.md#일반감독의-결정-범위)를 따른다.
4. **카단 전용 구획만 쓰고, 자기 것만 종료한다.** 현재 바닥(tmux라면 `-L kadan` 구획)에서
   kyle 개인 세션과 절대 섞지 않는다. 카단이 만든 것만 `stop`으로 종료할 수 있다.
   이 규칙은 바닥이 바뀌어도 유지된다.
5. **세션 주소는 이름 규칙이다.** 세션 이름 = `kadan-<역할>`. 자동 번호 ID(`%3`, `@1`)를
   주소로 쓰지 않는다.
6. **완료 신호는 DONE 마커다.** 작업 지문에 `KADAN:DONE <taskId> ok|failed` 출력을
   요청하고, 감시는 그 줄을 원장에 기록한 출력에서 찾는다. 마커가 없는 정지는
   "quiet"로 보고만 하고 판정하지 않는다. **작업 지문에는 완성된 마커 문자열을 쓰지
   않는다.** 형식(`KADAN:DONE <카드id> <ok|failed>`)과 카드 id만 주고 조립은 에이전트가
   한다. 완성된 마커가 지문에 있으면 입력 에코가 마커로 읽혀 오판의 뿌리가 된다
   (2026-08-30 herdr 실측·card-13 검수).
   판을 열면 `kadan plan <판> <카드id>...`으로 카드 목록을 원장에 먼저 적는다
   (안 적으면 미발령 감시가 빈다).
7. **창은 기계당 하나다.** `KADAN_WINDOW=orca|rottie|none` 중 하나만 쓰고
   폴백 체인을 두지 않는다(2026-08-30 card-15·17).
8. **실제 미완료 작업자·검수자와 활성 책임이 있는 일반감독을 구분해 감시한다** (2026-09-09 관리자 결정).
   작업자는 실제 발령·미완료 실행 기준이며 완료·보류·취소·미발령·유효 입력 대기는 제외한다.
   일반감독은 활성 실행·발령 이력이 있는 열린 업무를 책임지는 동안 1시간마다 응답 상태를 점검한다.
   감시sh→작업 감시AI 세트와 감독 관찰AI를 개념·표시·호출 이유로 구분한다.
   작업 감시AI는 같은 실행·같은 근거를 30분 간격으로 재확인하고 정체·진행 검사의 호출 시각을 합친다.
   감독의 연결·압축 오류가 5분 지속되면 감독 관찰AI에 먼저 넘긴다. 정당한 결과 대기는 정상이다.
   최상위 슈퍼감독은 정기 점검 대상이 아니다. 자원 수치는 대시보드에서 확인하며 watch가 자원 경고·해제 우편으로 AI를 깨우지 않는다.
   감시ai는 완료 후 입력 대기를 죽음으로 보고하지 않는다. 실행완료와 응답장애를 구분한다.
   두 AI는 강도max·동시에1개·호출당5분 상한이며 감독 관찰 대기를 우선한다. 그동안 감시sh 순회는 계속한다. 보고 접수 후 최종 답변을 기다리지 않는다.
   비활성 판은 AI를 호출하거나 깨우지 않는다. 원장 조회 실패를 대상 0명으로 꾸미지 않는다.
   상세 대상 선정과 대시보드 공통 기준은 [감시 안내](docs/watch-overview.md)에 둔다.

## 다시 만들지 않기 (본 카단에서 배운 것)

- 다중 provider 어댑터 추상화 — 금지. AI CLI(claude·codex 등)별 어댑터를 만들지 않는다.
  바닥 교체는 어댑터 계층을 쌓는 게 아니라 "코어는 그대로 두고 바닥 구현만 갈아끼우는"
  방식으로 한다.
- strict JSON 게이트, 발령 전 확인 관문, 권한 매트릭스, 4계급 우편 — 금지.
  사고가 반복될 때 그 사고에 맞는 최소 장치만 그때 추가한다.
- 완전 호환 capability 심사 — 금지. 남을 심사하지 않는다. 바닥은 우리 소유다.

## 명시적인 책임 관계

역할 자리·직속 상위·watch의 `--hierarchy` 설정과 최상위 사용자 알림은 [책임 관계 안내](docs/hierarchy.md)를 따른다. 기존 이름 기반 판 분류와 실제 보고 관계를 혼동하지 않는다.

### TODO와 카드 (2026-09-12 관리자 결정)

- 미래 작업 큐는 이슈(관리자 기계에서는 비공개 기록 레포의 TODO), 실행은 카드다. 언젠가 할 일은 TODO에, 다음에 역할에게 태울 일만 미배정 카드(draft/ready)에, 지금 일의 연장은 새로 만들지 말고 기존 카드에 추가 입력으로 남긴다.
- TODO에 있던 걸 카드로 만들면 TODO 항목에 카드 링크를 남긴다. 카드를 TODO로 내리지 않는다 — 못 하는 건 카드 상태를 보류·취소로 남긴다.
- 미배정 카드는 감시 대상이 아니라 판의 '발령 전' 표시 대상이다. 감시는 발령(assigned)부터다.

### 업무와 실행 (2026-09-08 관리자 결정)

- 새 결과 중심 작업은 `kadan work`로 업무 카드 한 장을 유지한다. 목표·전체 대상·완료 조건·책임 감독을 적고, 구현·검수·수정·배포는 그 안의 실행으로 연결한다. 사진 몇 장이나 시간 구간마다 새 업무 카드를 만들지 않는다.
- `work execute`로 등록한 실행은 고유 ID를 쓴다. 배정·발령·DONE은 기존 실행 카드 규약을 따른다. 업무 ID를 `send --task`에 쓰지 않는다.
- 작업자의 실행 종료와 감독의 업무 최종 완료는 다르다. 중간 구간은 처리 수·남은 대상·재개 위치를 `work update --progress`로 남긴다. 책임 감독이 약속한 결과와 근거를 확인한 뒤 `work complete`한다.
- 기존 SQLite 우편함에 `send --work <업무키> [--execution <실행키>]`로 연결하고 답장은 `--reply-to`로 이어간다. 새 우편함을 만들지 않는다.
- 기존 원본·실행·완료·우편 이력은 보존한다. 과거 기록을 제목으로 추측해 일괄 묶거나 완료 판단을 다시 쓰지 않는다. 상세 명령은 [업무 카드와 실행](docs/business-work.md)을 따른다.

## 용어

- 코어(core): 바닥이 바뀌어도 갖고 가는 것 — 원장, 안전장치(생존 확인·모호하면 판정 금지·
  자기 것만 종료), 명령 인터페이스(start/send/done/wait/read/status/log/attach/stop),
  DONE 마커 규약.
- 바닥(bottom): 에이전트가 사는 곳. 지금은 tmux 구획(`-L kadan`). 로티 같은 다른 바닥으로
  이동할 수 있다.
- 역할(role): 슈퍼감독·일반감독·작업자 등 바닥의 세션 하나로 띄우는 단위.
- 원장(ledger): 무엇을 했는지 뒤에만 추가하는 사건 기록. 현재 실제 저장은 SQLite다.
- 영수증(receipt): `send`가 원장에 남기는 전달 기록(시각·대상·내용 지문).
- DONE 마커: 에이전트가 화면에 출력하는 완료 표시 줄.
- 턴(turn): 티키타카 왕복의 한쪽 작업(구현·수정 또는 독립검수).
- 라운드(round): 왕복 한 번 = 턴 2개. 1라운드 = 구현 턴 + 독립검수 턴.
  검수 FAIL이면 다음 라운드(수정 턴 + 재검수 턴)로 이어진다. 저장 필드에서는
  rallyRound가 라운드 번호, rallyStep이 턴의 단계다. 명칭은 2026-09-22에 정리했고 저장 필드는 유지한다.

### 원장 기록 형식

모든 기록은 뒤에만 추가하는(append-only) JSON 사건이다. 아래는 기존 통합 조회의 대표 사건이며 전체 종류 목록이 아니다. 신규 저장의 `dispatch`·우편 읽음·질문 취소와 세 영역의 관계는 [원장 계약](mail-task-ledgers.md)을 따른다.

- `plan`: `role` 없이 `board`, `taskId`, `by`를 기록한다. 감독이 판을 열 때 카드
  목록을 미리 적는다. 남은 일은 distinct(plan ∪ send) − distinct(done)이다.
- `start`: `role`은 시작 대상이다. pane PID와 창을 연 방법을 포함하고, `by`는
  시작시킨 사람 또는 역할이다. `--cmd`로 띄우면 명령 원문(`cmd`)과 거기서 읽은
  실행기(`harness` — 명령 첫 낱말)·모델(`model` — `--model` 값)을 함께 적는다
  (2026-09-06 관리자 결정). `harness`·`model` 필드는 사후 표시용이며 카단이 그 값만으로
  신원을 신뢰하지는 않는다 — 카드 연결 send는 규칙 2에 따라 같은 start 기록의 `cmd`
  원문과 현재 pane PID로 신원을 다시 확인한다(2026-09-21). 화면이 사라진 뒤에
  "어느 실행기·어느 모델이었나"를 원장만으로 답하기 위한 기록이다(ps는 세션이
  죽으면 같이 사라진다). 이미 살아 있어 재사용한 세션은 실제로 그 명령으로 띄운 게
  아니므로 적지 않는다. 실행기별 어댑터가 아니라 명령 문자열을 그대로 옮긴 것이다.
  역할 프로필을 단 세션을 새로 만들 때는 `--cmd`가 필수다 — 세션·창·start 기록을
  만들기 전에 실패한다(2026-09-21). 살아있는 세대의 재사용에는 명령을 요구하지
  않는다.
- `send`: `role`은 받는 사람이다. 바이트 수와 지문을 포함하고, `by`는 보낸 사람 또는
  역할이다.
- `done`: `role`은 완료한 사람이다. taskId와 결과를 포함한다. `wait`가 마커를
  확인해 기록할 수도 있고, 사람 또는 감독이 확인한 뒤 `kadan done`으로 수동
  확정할 수도 있다. 수동 확정은 확인한 사람 또는 역할을 `by`에 남긴다. 동시
  실행으로 같은 역할·카드의 줄이 여럿 생기면 읽을 때 가장 먼저 쓴 한 줄만 인정한다.
- `stop`: `role`은 종료 대상이다. `by`는 종료시킨 사람 또는 역할이다.
- `alert`: watch가 낸 알림 한 줄. alertKind·level·수신자·전달 여부를 담는다. by는 watch다.

`by`는 watch 내부 전달이면 `watch`, 카단 세션 안에서 실행해 `KADAN_ROLE`이 있으면
그 역할, 둘 다 아니면 `사람`이다. 이 값은 인증된 신분이 아니라 **스스로 밝힌
신분**이다. 기존 원장처럼 `by`가 없는 줄은 `사람`으로 추측하지 않고 `모름`으로
읽는다. append-only 원칙 때문에 옛 줄을 소급 수정하지 않는다.
