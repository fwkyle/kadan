# AICP vs 카단 비교 분석 — 에펨코리아 자동매매 연재에서 배울 점

## Why

에펨코리아 주식 게시판에 올라온 AICP 연재(0화·1화)는 "여러 AI를 역할별로 띄워 24시간 자율 연구시스템을 만든다"는 문제의식이 카단과 거의 같다. 같은 문제를 다른 길로 풀었기 때문에, 어디가 같고 어디가 다른지 정리해 두면 카단의 설계 선택을 다시 점검하는 데 도움이 된다.

- [0화 원문](aicp-ep0-original.md) — https://www.fmkorea.com/10339678186
- [1화 원문](aicp-ep1-original.md) — https://www.fmkorea.com/10339693723

## AICP가 뭔가

작성자(나스닥의도로롱)가 AI 자동매매 연구를 위해 만든 멀티에이전트 시스템. Gemini(연구)·Claude(반박/감사)·Codex(저장소 구현)·GPT(방향/판단) 네 개의 LLM을 쓰고, 그 사이에서 작업 계약·증거 기록·검증·공식 상태 승격을 담당하는 뼈대가 AICP다.

1화까지 드러난 3층 구조:

```text
사용자 / GPT (필요할 때만 큰 판단)
   ↓
Local Supervisor   — 비-LLM 상태머신, launchd로 120초마다 깨어남
   ↓
Project Controller — dependency·capacity·HOLD를 보고 실행 가능 task 선정
   ↓
AICP Core          — worker 실행 + 증거 저장 + deterministic 검증 + 승격
   ↓
Gemini / Claude / Codex (worker)
```

핵심 원칙 네 개: 멀티에이전트≠협업, LLM 출력≠진실(canonical truth 분리), 지능과 오케스트레이션은 다른 문제, AI는 필요할 때만 깨운다(episodic).

## 카단과 같은 문제를 만났다

두 시스템이 독립적으로 같은 벽에 부딪혔다는 점이 제일 재미있다.

| 발견 | AICP | 카단 |
|---|---|---|
| 사람이 메시지 버스가 되는 문제 | 0화 "내가 인간 메시지 버스가 되어 있었다" → AI 간 통신을 구조화된 상태 패킷으로 | `send`/원장이 그 역할을 대신함. 역할 간 전달을 CLI가 흡수 |
| LLM 말을 믿을 수 없는 문제 | "LLM의 말은 프로젝트의 진실이 아니다" → 검증된 것만 canonical state로 승격 | DONE 마커 규약 + 감시가 원장에 기록된 출력에서 마커를 찾아 확정. "AI가 완료라고 말함 ≠ 완료" |
| 상주 LLM 관리자 문제 | ChatGPT Agent를 끄니 연구소가 멈춤 → 비-LLM Supervisor 분리 | 감시를 sh 스크립트+제한된 감시AI로 분리. "감시sh→작업 감시AI" 이중 구조, 감시AI도 강도max·5분 상한 |
| 모르면 멈춰야 한다 | shadow state 발견 시 fail-closed로 차단 | "원인을 모르는 실패에는 재시도하지 않는다(모호하면 실패 닫힘)" |
| 작업과 오케스트레이션 분리 | worker에게 운영권을 주지 않는다 | 역할(슈퍼감독·일반감독·작업자) 분리, 작업자는 할당 범위만 |

## 결정적인 차이 — 어디에 복잡성을 두는가

같은 문제의식인데 복잡성을 두는 위치가 다르다.

**AICP는 무인 자율 운영이 목표다.** "내가 자러 가도 연구가 계속된다"가 핵심 요구라서, 사람이 없을 때도 다음 작업을 고르고 dispatch하는 층(Local Supervisor + Project Controller)을 직접 만들었다. Never-idle 원칙 — 막히면 다른 안전한 작업으로 이동 — 까지 들어간다. 사람은 "Human/Expert Plane"으로 밀려나서 복잡한 판단 때만 호출된다.

**카단은 사람이 보고 개입하는 것이 목표다.** "사람이 실제로 보고 개입하는 것이 목표다", "start는 창을 열고 attach는 언제든 다시 연다"가 정체성이다. 그래서 AICP의 Controller 같은 "다음 작업 자동 선정" 층이 없고, 대신 감독 역할(AI 세션)이 판을 읽고 판단한다. 완전 무인이 아니라 "감시 + 사람 개입" 모델이다.

정리하면:

- AICP: **사람을 빼는 방향**으로 진화. LLM도 episodic으로 줄이고, 상태머신이 평상시를 굴린다.
- 카단: **사람을 남기는 방향**으로 진화. 바닥(tmux) 위에서 사람이 attach·개입할 수 있게 유지하고, 자동화는 감시·전달·기록에 집중한다.

## 카단이 배울 만한 점

1. **deterministic 검증의 승격 구조.** AICP는 "AI 작업 → 실제 변경 확인 → 증거 저장 → 결정론적 테스트 → 통과 → 공식 상태 승격" 파이프라인이 명시적이다. 카단은 DONE 마커가 완료 신호지만, 마커는 "에이전트가 출력한 줄"이라 여전히 자기 보고다. 카단 work의 work complete 전에 "검증된 증거만 승격" 같은 한 단계를 의식적으로 두면 감독의 완료 판단이 더 단단해진다. 실제로 카단도 "책임 감독이 약속한 결과와 근거를 확인한 뒤 work complete"라고 되어 있으니 방향은 같고, AICP는 그 검증을 코드로 강제한다는 차이가 있다.

2. **quota/capacity를 선정 로직에 넣는 것.** AICP Controller는 "Claude quota가 없는데 Claude task를 실행하지 않는다"를 구조적으로 처리한다. 카단은 429 같은 레이트리밋을 사후에 경험 규칙(rate-limit-retry)으로 다룬다. 실행 전에 capacity를 보고 worker를 고르는 발상은 카단의 발령 단계에도 적용 가능하다 — 다만 카단의 "먼저 흐르는 심플" 원칙상 사고가 반복될 때만 최소 장치로 추가하는 게 맞다.

3. **Never-idle과 fail-closed의 공존 방식.** AICP는 "막혀도 안전한 다른 일을 한다"와 "모르면 멈춘다"를 동시에 둔다. 카단은 후자(모호하면 실패 닫힘)는 강하지만, 막힌 작업 대신 다른 dependency-ready 작업으로 이동하는 개념은 감독의 판단에 맡겨져 있다. 작업 큐가 커지면 참고할 만하다.

4. **shadow state 경계.** aicp/state.json vs .aicp/state.json 사고는 "진짜 canonical 파일과 비슷하게 생긴 파일"이 시스템을 멈추게 한 사례다. 카단도 원장이 SQLite로 가면서 "현재 원본은 kadan.sqlite의 events이고 기존 JSONL은 동결 보존"이라 둘러싼 경계가 생겼다. 비슷한 혼동 사고가 날 수 있는 지점이라 경계 표시를 분명히 유지할 이유가 있다.

## 카단이 이미 잘하고 있는 점 (AICP에 없거나 약한 것)

- **사람 개입 경로.** attach로 언제든 들어가는 것, 창을 여는 것. AICP는 사람을 Expert Plane으로 밀어냈는데, 그러면 "지금 뭘 하고 있나"를 사람이 직접 보기 어려워진다. 카단은 이게 1급 기능이다.
- **append-only 원장의 단순함.** AICP의 canonical state + evidence chain은 기능이 많은 만큼 무겁다. 카단의 여섯 종류 사건(plan/start/send/done/stop/alert)은 훨씬 단순하다.
- **"안전 규칙이 흐름보다 앞서면 흐르지 않는다"는 사전 교훈.** AICP는 lock·hash·dependency·HOLD 등을 실제 사고를 겪으며 하나씩 추가했다. 카단도 "사고가 반복될 때 그 사고에 맞는 최소 장치만 그때 추가한다"로 같은 길을 가되, 미리 만들지 않는다는 원칙이 명시돼 있다.

## 한 줄 정리

AICP는 "사람 없이 24시간 도는 연구소"를 목표로 control plane을 코드로 만들어 간 사례이고, 카단은 "사람이 보고 개입하는 관제"를 지키며 감시·기록을 단순하게 유지한 사례다. 목표가 달라서 어느 쪽이 낫다기보다, AICP의 "검증된 것만 승격"과 "capacity-aware dispatch"는 카단이 작업이 커질 때 참고할 수 있는 구체적인 패턴이다.
