# 마네님(ACS-MAGP) vs 카단 비교 분석 — 회사형 멀티에이전트 프로토콜에서 배울 점

## Why

마네님이 작성한 "Adaptive Company-Style Multi-Agent Global Protocol"(ACS-MAGP v1.0.0)은 "여러 AI 에이전트를 회사 조직처럼 운영한다"는 문제의식이 카단과 같다. 다만 카단이 실측에서 배운 "먼저 흐르는 심플"과 달리, 이 문서는 승인 체인·불변 기록·해시 바인딩까지 명세한 무거운 설계다. 어디가 같고 어디가 다른지 정리해 두면, 카단이 나중에 고위험 작업용 승인 장치를 만들 때 무엇을 가져오고 무엇을 버릴지 판단 근거가 된다.

원문 md화 (틱시디언 → 카일브레인 inbox에서 복사, 2026-09-15 작성):

- [프로토콜 원문](멀티에이전트 V1 - 마네님.md) — 3,154줄, 사람이 읽는 문서 형태
- [YAML 압축본](멀티에이전트 V1 - code인가 - 마네님.md) — 같은 명세를 YAML 설정으로 압축한 기계 판독용

## 마네님 프로토콜이 뭔가

에이전트 집단을 `사용자 ↔ 총괄 오케스트레이터 ↔ 팀장 ↔ 팀원` 수직 책임선으로 묶고, 팀 간 직접 협업은 허용하되 범위·우선순위·공유 계약 변경은 권한자 승인을 요구하는 글로벌 운영 프로토콜이다. Claude Code 훅 계약 어댑터까지 포함한다.

구조의 뼈대:

```text
사용자 (L4/L5 최종 승인)
   ↓
총괄 오케스트레이터 — 요청 정규화, 조직 설계, 통합
   ↓
팀장 — Task Contract 분해, 착수/중간/완료 검토
   ↓
팀원 — 계약 범위 안 실행, 증거 보고
   +
Shared Blackboard / Decision Log / append-only 기록들
```

특징적인 장치 네 개:

- **점수 기반 조직 선택**: 복잡도·위험·의존성·전문성·품질을 0~4로 매겨 `2C+3R+2D+2E+2Q` 점수로 O0(혼자 실행)~O3(멀티팀) 조직을 고르고, O4 고보증 오버레이를 얹는다.
- **승인 수준 L0~L5**: 위험 차원 6개(비가역성·외부효과·데이터보안·재무법률평판·파급범위·불확실성)로 승인 수준을 파생. L4부터는 무조건 사용자, L5는 정확한 행동 단위 승인.
- **승인 체인**: ApprovalRequest → AuthorityValidation → ApprovalRecord(불변) → ApprovalUsageLedger(원자적 사용 예약) → ExecutionReceipt. 대상 spec의 해시가 바뀌면 기존 승인은 무효.
- **완료 3중 서명**: 작성자 attest → 독립 검토자 attest → 완료 게이트(G3) attest가 모두 맞아야 COMPLETED.

## 카단과 같은 문제를 만났다

| 발견 | 마네님 프로토콜 | 카단 |
|---|---|---|
| LLM 말을 믿을 수 없음 | "완료는 산출물이 아니라 증거로 판정", 수용 기준·검증·승인까지 확인 | DONE 마커 + 감시가 원장 기록 출력에서 마커를 찾아 확정 |
| 모르면 멈춤 | broken reference 시 PAUSE_AND_ESCALATE, 승인 없는 외부 행동은 fail-closed | "원인을 모르는 실패에는 재시도하지 않는다(모호하면 실패 닫힘)" |
| 역할 분리 | 수행자·검토자·승인자 분리, 자기 승인 금지 | 작업자·검수자·일반감독 분리, 싸이클(구현 라운드+독립검수 라운드) |
| append-only 기록 | 모든 기록 불변, 수정은 별도 사건으로 | 원장 append-only, 사건 수정·삭제·재정렬 금지 |
| 최소 조직 | "목표를 달성할 최소 조직"이 기본값, 단순 작업에 팀 금지 | "가벼운 실행이 기본", 작은 작업에 카드/역할 안 만듦 |

원칙 수준에서는 거의 같은 결론에 도달했다. 독립적으로 "최소 조직", "증거 기반 완료", "fail-closed"를 뽑은 건 이 문제 영역의 수렴 진화로 볼 수 있다.

## 결정적인 차이 — 명세를 지키는 주체가 뭔가

AICP 비교에서 "복잡성을 어디에 두는가"가 갈림길이었다면, 마네님 프로토콜과의 갈림길은 **명세를 누가 집행하는가**다.

**마네님 프로토콜은 spec_hash·content_hash·quorum·원자적 원장 예약을 요구한다.** 이건 LLM이 프롬프트로 "지키는 척"할 수 있는 게 아니다. sha256을 계산하고, revision을 대조하고, compare-and-append로 원장 head를 선점하는 건 코드만 할 수 있다. 즉 이 문서는 사실상 **에이전트 하네스의 요구명세서**다 — 프롬프트가 아니라 런타임이 집행해야 실제로 작동한다. 프롬프트에 통째로 넣으면 에이전트가 YAML 모양 텍스트를 뱉을 뿐, 안전장치의 대부분은 장식이 된다.

**카단은 같은 목표를 훨씬 얇은 장치로 집행한다.** send 직전 has-session+PID 대조, DONE 마커를 원장 출력에서 찾기, 카단이 만든 세션만 종료. 검증 주체가 CLI와 감시sh라서 실제로 작동하고, 장치가 얇아서 흐름을 막지 않는다.

정리하면:

- 마네님: **정확성을 명세 복잡성으로 사는 방향**. 맞게 구현되면 매우 강하지만, 구현 비용이 크고 프롬프트 단계에서는 허상이다.
- 카단: **정확성을 실측 사고에서 필요한 만큼만 사는 방향**. 약한 부분이 남지만 실제로 돌고 흐른다.

## 카단이 배울 만한 점

1. **승인 수준의 파생 규칙.** 카단은 "파괴적 작업 금지", "send 전 생존 확인"처럼 개별 규칙이 사고별로 쌓였다. 마네님의 L0~L5처럼 "행동의 위험 차원 → 필요 승인 수준"을 한 표로 파생하는 발상은, 카단이 나중에 위험 행동(배포·삭제·외부 발송)을 다룰 때 분류 기준으로 참고할 만하다. 전부 다 만들라는 게 아니라 "어떤 행동이 사용자 승인인가"의 경계선을 그을 때 쓸 어휘다.

2. **대상이 바뀌면 승인 무효.** "spec_revision·spec_hash가 바뀌면 기존 승인은 무효"는 카단에도 그대로 적용되는 원칙이다. 카단 카드의 범위가 승인 후 바뀌었을 때 이전 승인을 재사용하는 사고는 아직 안 났지만, 나면 이 원칙이 최소 장치가 된다.

3. **승인 사용 예약의 원자성.** ApprovalUsageLedger의 compare-and-append는 "같은 승인을 두 에이전트가 동시에 쓰는" 사고를 막는다. 카단 우편/승인이 지금은 단일 감독 흐름이라 필요 없지만, 병렬 감독이 생기면 참고할 패턴이다.

4. **역할 합침(role coalescing)의 명시 조건.** "위험 ≤1, L0/L1, 이해상충 없음이면 한 에이전트가 논리 역할 여럿을 겸한다"를 규칙으로 둔 점. 카단의 "가벼운 실행이 기본"을 언제 깨야 하는지의 경계를 명식화한 버전이다.

## 카단이 이미 잘하고 있는 점 (프로토콜에 없거나 약한 것)

- **실제로 돌아간다.** 이 문서는 canonical_template 상태의 명세다. 카단은 12장 왕복 실측을 통과한 바닥과 원장이 있다. 명세의 완결성과 운영 증거는 다른 물건이다.
- **사람 개입 경로.** attach·창 열기가 1급 기능. 마네님 프로토콜에서 사용자는 승인자로만 등장하고, "지금 화면을 직접 본다"는 개념이 없다.
- **사고 대응 경험칙.** "완성된 마커를 지문에 쓰지 않는다(입력 에코 오판)", "copy mode에서는 send가 막힌다" 같은 규칙은 실측에서만 나오는 지식이다. 명세 문서에는 없는 층이다.
- **흐름 우선 원칙.** "안전 규칙이 흐름보다 앞서면 흐르지 않는다"는 이 프로토콜 전체에 대한 반례다. 3,154줄을 지키려는 시도 자체가 흐름을 죽인다.

## 한 줄 정리

마네님 프로토콜은 카단과 같은 원칙(최소 조직·증거 완료·fail-closed)에서 출발해 "회사 수준의 승인 체인"까지 명세한 이상형 설계서고, 카단은 같은 원칙을 실제로 돌아가는 최소 장치로 유지한 실전형이다. 통째로 쓸 물건은 아니지만, "승인 수준 파생"과 "대상 변경 시 승인 무효" 같은 개별 원칙은 카단이 고위험 작업 장치를 만들 때 가져올 가치가 있다.
