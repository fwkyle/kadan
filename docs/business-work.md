# 업무 카드와 실행

## Why

[kyle]이 작은 실행 수백 개를 읽지 않고도, 약속한 결과와 남은 일·현재 차례를 업무 한 장에서 확인하게 한다.

## 이제 무엇을 한 장으로 보나

| 구분 | 담는 내용 | 종료 기준 |
| --- | --- | --- |
| 업무 카드 (`work`) | 사용자에게 약속한 결과, 전체 대상, 완료 조건, 책임 감독 | 책임 감독 또는 사용자가 최종 결과와 확인 근거를 기록 |
| 실행 (`card`) | 그 업무 안에서 맡긴 구현·검수·수정·배포·조사 | 해당 실행의 결과 기록과 기존 DONE 규약 |
| 인박스 / 우편함 | 같은 업무에 연결된 질문·인계·결과 통지와 답장 | 전달·보관·읽음·답변 상태는 각각 따로 기록 |

‘제품 사진 생성해서 검색·상세에 연결’을 업무 카드 하나로 유지한다. 그 안에서 생성과 연결 실행을 병렬로 진행하고, 검수에서 문제가 나오면 수정 실행을 이어 붙인다. 사진 몇 장이나 시간 구간마다 새 **업무 카드**를 만들지 않는다. 구간 보고는 **처리 수 / 남은 대상 / 재개 위치**를 남긴다.

기존 실행은 한 번 완료한 역할·카드 ID의 DONE을 다시 구별하지 못한다. 따라서 다음 실행에는 새 ID를 부여한다. `work execute`는 이를 자동으로 만든다. 반복 횟수를 늘리기 위해 실행을 잘게 나누는 기능이 아니다. 이어서 수행할 수 있는 실행은 진행 보고로 계속 이어간다.

## 화면 사용

- **업무 카드**가 기본 표다. 목적·흐름과 라운드·현재 차례·다음 행동·책임 감독을 보여준다.
- 화면은 업무를 **워크**, 실행을 **카드**라고 부른다(명령 `kadan work` / `kadan card`와 같은 말, 2026-09-28 [kyle] 결정). 이 문서의 업무·실행과 같은 뜻이다. 작업 화면은 **카드** 탭이 기본이고 옆에 **워크** 탭이 있다.
- 탭 옆에는 두 숫자의 관계를 한 줄로 보여준다(카드 N장 중 워크 안 몇 장, 워크 미연결 몇 장). 워크 표에서는 카드 수준 열을 **안쪽 카드 상황**, 워크 수준 열을 **워크 상태**로 부른다. 카드 기준인 **닫을 카드**(실행 끝·카드 열림)는 카드 표 아래에만 둔다.
- **모든 실행**에서는 기존 실행 카드를 본다. **연결 전 실행**은 아직 어떤 업무에도 연결하지 않은 기존 기록이다. 기존 기록을 제목으로 추측해 묶지 않는다.
- 업무를 펼치면 **목표·현재 상황·현재 차례·다음 행동과 인박스**가 먼저 나온다. 고정된 실행 담당은 목록과 상세에서 반복 표시하지 않는다. 표형이 기본이며 문서형으로도 읽을 수 있다.
- 업무 내용·완료 조건, 진척·완료 기록 남기기, 기술 정보는 접어둔다. **기술 정보 → 실행 기록**에서 새 실행을 등록하거나 기존 실행을 단계·라운드과 함께 연결한다. 같은 라운드에 여러 실행이 있어도 된다. 연결 정정은 실행 원본을 바꾸지 않는다.
- 예전 실행 카드 상세도 현재 차례와 연결된 인박스를 먼저 보여준다. 원본·검수·변경 기록은 펼쳐 읽는다. 연결 정보가 없는 편지를 제목이나 내용으로 추측해 붙이지 않는다.
- 목록의 열 순서·너비와 목록·상세 사이 너비는 기존 드래그 조작을 계속 쓴다.
- 진행 중인 실행이 있으면 업무 완료·취소를 기록할 수 없다. 모두 끝나도 업무는 자동 완료되지 않고 감독의 최종 확인을 기다린다. 실패한 실행을 포함한 최종 판단은 감독이 확인 근거에 남긴다.

‘현재 차례’는 기록자를 그대로 가져오지 않는다. 업무에 명시한 차례가 이후 실행 보고보다 최신이면 그 값을 쓴다. 그 외에는 실행마다 기록된 차례·전달·보고를 모아 여러 사람도 표시한다. 다음 행동 주체를 알 수 없는 실행은 **차례 확인 필요**로 표시한다. 자유 형식 우편의 ‘준비수신’ 같은 단어로 차례나 완료를 확정하지 않는다.

현재 라운드는 명시적으로 연결한 실행 중 가장 큰 번호다. 전체 실행 표에서 이전 라운드의 남은 실행도 확인한다. 관제 요약·판 현황·watch는 기존 실행 기준을 유지한다. 업무 최종 완료 수와 섞어 세지 않는다.

## 실행 종료 뒤 다음 행동

업무 목록·상세와 `work list` / `work show`는 같은 `followup` 조회값을 사용한다. 실행 종료, 등록된 품질 판정, 업무 최종 완료를 나눠 표시한다. 검수 합격 뒤에는 감독 최종 확인, 수정 요구 뒤에는 수정 연결, 자동 블록 경계·상한 뒤에는 해당 판단을 표시한다. 후속 실행이 이미 연결됐으면 그 실행을 우선한다. 새 카드 상태나 자동 알림은 만들지 않는다.

사용자 결정 요청은 해당 실행의 대기로 표시한다. 일시정지·기다림 기록이 없으면 연결 확인이 필요하다고 알리고, 같은 업무의 다른 실행은 유지한다. 답변 전달 실패·재개 미확인은 작업 중으로 바꾸지 않는다. 주소나 근거를 읽지 못하면 ‘확인 필요’로 남긴다.

감독은 기존 `work update --next-action ... --turn-owner ... --note ...` 또는 `work complete`로 후속 판단을 남긴다. 새 결과보다 오래된 다음 행동은 현재 판단으로 쓰지 않는다. 조회는 원장·읽음·카드 상태를 수정하거나 역할을 깨우지 않는다.

`work complete`·`work cancel`은 연결된 실행이 모두 끝나야 받는다. 끝난 것은 완료·실패·취소·대체뿐이다. 보류(`archived`)는 시작 전에 미뤄 둔 카드라 끝이 아니다. 화면 요약이 failed여도 같은 카드에 미완료 실행(실패 뒤 다른 담당에게 다시 보낸 것)이 남아 있으면 마감을 거절하고, 오류에 남은 실행 ID·상태와 다음 행동(마치기·취소·명시 인계 또는 완료 확정)을 적는다. 담당을 바꿔 보낸 옛 실행은 자동으로 완료·취소하지 않는다.

### 결과 우편의 차례 반환 (놀고 있음 PR-3)

일을 위임받은 쪽이 결과를 업무 owner에게 우편으로 보내도 저장된 차례(`turnOwner`)가 보낸 쪽에 남아 값과 실제 책임이 어긋났다. 그래서 `--work`(또는 `--execution`·`--reply-to`로 풀린 업무 연결)가 있는 우편에서 **셋이 모두 참일 때만** 차례를 owner로 옮긴다: (a) 보낸 역할이 저장된 차례 보유자, (b) 보낸 역할이 owner가 아님, (c) 받는 역할이 owner. owner는 인계를 반영한 현재 책임자(`effectiveWorkOwner`)로 본다. `--reply-final`도 같은 조건일 때만 옮긴다. 차례 기록의 current/stale는 조건에 넣지 않는다 — stale이면 감시는 이미 owner로 읽으므로 저장값만 맞춰진다. `사람`·사용자 명의, `watch`, 알림 전용·시스템 생성 우편, `--task` 발령, `--raw`, 비서·사용자 같은 저장 전용 수신자, 보관만 된 우편은 옮기지 않는다.

- **순서(2026-10-23 검수 수정): 먼저 판정·쓰기, 쓰기가 됐을 때만 꼬리, 전송 실패면 되돌림.** 보내기 직전에 업무 잠금 안에서 업무·원장을 다시 읽고 effective owner와 세 조건을 다시 확인한 뒤 차례를 쓴다(판정과 쓰기가 한 순간이라, 판정 뒤 인계가 확정돼도 옛 owner에게 쓰지 않는다). 우편은 그 잠금을 놓은 **뒤에** 시작한다. 잠금을 겹쳐 잡지 않고, 잠금 안에서 우편을 부르지 않는다.
- 저장소가 SQLite 하나라 자동 차례 반환은 저장 방식과 상관없이 같다(2026-10-23 수정 2였던 JSONL 건너뛰기는 JSONL 백엔드와 함께 지웠다).
- 쓰기가 실패했거나(잠금 대기·저장 오류·revision 충돌) 조건이 더는 맞지 않으면 **꼬리 없는 보통 우편**을 보낸다. 보낸 쪽 stderr에 한 줄과 수동 `work update` 명령이 남고 재시도하지 않는다. 받는 owner는 거짓 안내를 받지 않는다.
- 쓰기가 성공했는데 전송이 실패하면(`not-sent`·`unknown`, 보관으로 돌린 경우 포함) 차례를 보낸 쪽으로 되돌린다(best-effort). 쓰기 때 남긴 업무 revision 그대로일 때만 쓴다. 그 사이 어떤 변경이든 있었으면(같은 이름으로 다시 지정했거나 A→B→A로 돌아온 경우 포함) 되돌리지 않고 알린다. 되돌리기도 실패하면 stderr에 정확한 되돌리기 명령을 낸다. 전달은 됐고 기록만 실패한 경우(`sent`)는 되돌리지 않는다. 예전 규칙 "전송 실패 시 옮기지 않음"은 "전송 실패 시 되돌림"으로 바뀌었다.
- 원장은 기존 업무 변경 이력(`by`=보낸 역할, note `우편으로 owner에게 차례 반환(되돌리기: …)`)을 쓴다. 우편 ID는 전송 전에 몰라 note에 없고, 보낸 쪽 영수증 `{"turnReturn":{…}}`에 있다. 새 사건 종류는 없다. 이 경로는 `work update`를 거치지 않으므로 채팅 결정은 자동으로 닫히지 않는다(결과 우편은 kyle의 답이 아니다).
- 쓰기가 성공했을 때만 받는 owner가 읽는 본문 꼬리에 **실제 새 revision**이 들어간 되돌리기 명령이 붙는다. 꼬리·영수증·원장 note의 명령은 같은 문자열이다.
- 우편 보내는 쪽이 `--keep-turn`을 주면 조건이 맞아도 옮기지 않고 꼬리도 붙이지 않는다. 지침·템플릿에는 이 옵션 문장을 넣지 않는다.

`timing`에는 업무 시작·마감·경과, 라운드 번호, 실행 주소로 명시 연결된 감시 호출 수를 표시한다. 실행 상세에는 발령→결과 등록과 발령→DONE 경과가 있다. 음수·발령 없는 기록과 관측 시각이 없는 완료 확정 지연은 `null`(미측정)이다. 대기 시간을 포함한 경과를 실제 작업 시간이나 모델 비용으로 부르지 않는다. 주소가 없는 감시 호출은 해당 업무 비용으로 추측해 합산하지 않는다.

화면에서 구현+독립검수 왕복을 1라운드로 부른다. 기존 저장 필드와 CLI 인자 `round` / `rallyRound`는 바꾸지 않는다.

카드 상세의 검수·수정 횟수와 라운드별 비교 표는 [티키타카 표시 기준](review-flow.md)을 따른다. 후속 카드는 `card update --rally-from <앞카드> --rally-round N --rally-step <단계>`로 같은 묶음을 이어받는다. 업무의 실행 연결 번호도 같은 라운드로 적으며, 병렬 실행 일련번호를 라운드로 대신 쓰지 않는다.

## 명령 사용

```sh
kadan work create 저장소/work-product-photos \
  --title '제품 사진 생성해서 검색·상세에 연결' \
  --goal '등록 제품에서 사진을 확인할 수 있다' \
  --scope '등록 제품 전체' \
  --acceptance '생성·제품 연결·누락 검수와 화면 확인' \
  --owner 제품-감독 --board 제품 --repo-path /절대/저장소/경로

kadan work execute 저장소/work-product-photos \
  --revision 1 --phase implementation --round 1 \
  --title '제품 사진 생성' --body-file /절대/실행지시.md \
  --note '전체 업무 안의 생성 실행'
```

`create` 응답(JSON)에는 `ownerOpenWorks`가 더해진다. 책임 감독의 열린 업무 수이고 방금 만든 업무를 포함한다. 사람이 읽는 한 줄(`책임 감독 ○○의 열린 업무 N건 (이 업무 포함)`)은 stderr에만 나가 stdout JSON을 읽는 쪽을 깨지 않는다. 숫자는 원장에 적힌 `owner` 기준이며 인계(`withEffectiveOwner`) 반영 전 값이다. 숫자는 참고만 하고, 새 일반감독 배정은 [슈퍼감독 지침 `판 열기` 2번](../skills/kadan-super/SKILL.md#판-열기-슈퍼감독-고유-규칙)의 기준(진행 중인 큰 업무 유무, 보류·시간 대기 제외)을 따른다.

`execute` 응답의 `executions[].key`가 새 실행 주소다. **한 번에 발령하려면** `--assign <역할>`을 붙인다: 업무의 범위·판으로 배정하고 묶음(rallyId=업무 ID, 제목=업무 제목, 라운드=`--round`, 조사는 0)·plan까지 기록한다. `--dispatch "<지시>"`를 더하면 같은 명령이 기존 `send --task` 검사(생존·PID·배정·범위·실행기)를 그대로 거쳐 보낸다. `--assign`은 `implementation|review|fix|research`에만 쓴다(`release`·`other`는 묶음에 들어가지 않는다). 따로 하려면 기존 `card update`에서 허용 범위·판·역할을 배정하고 `send --task`에는 **실행 카드 주소**를 쓴다([정식 주소와 짧은 ID 호환](task-identity.md)). 업무 ID를 발령하지 않는다. 화면의 ‘실행 초안 등록’도 등록만 하며 메시지를 전송하지 않는다. 실행 카드를 `assigned`로 바꿀 때는 티키타카 묶음 정보(`--rally-id --rally-title --rally-round --rally-step`)가 필수다. 업무 안의 실행은 업무와 같은 단계·라운드로 적고, 업무 밖 작은 작업은 1라운드 구현 턴로 시작한다. 관리·조율 카드는 묶음 없이 발령한다(2026-09-11 [kyle] 승인).

```sh
kadan work update 저장소/work-product-photos --revision 2 \
  --progress '20개 처리 / 224개 남음 / 제품 21부터 재개' \
  --next-action '도착한 사진부터 연결하고 누락 검수' \
  --note '중간 구간 보고. 업무 최종 완료는 아님'

kadan work link 저장소/work-product-photos --revision 3 \
  --execution 저장소/기존실행ID --phase review --round 1 \
  --note '기존 검수 실행을 이 업무에 연결'

kadan work complete 저장소/work-product-photos --revision 4 \
  --result '전체 대상 확인 결과와 검수 문서 경로' --note '약속한 결과 최종 확인'
```

버전(`revision`)은 최신 `work show` 값으로 바꾼다. 오래된 화면의 쓰기는 거절하며 화면의 작성 내용은 유지한다. 일시정지(hold)는 기록일 뿐 실행 중인 역할을 멈추지 않는다. 완료한 업무를 고쳐야 하면 `work reopen`에 이유를 남긴 뒤 새 실행을 연결한다. 이전 완료 판단도 이력에 남는다.

## 기존 SQLite 우편함 재사용

```sh
kadan send 비서 --work 저장소/work-product-photos \
  --execution 저장소/실행ID --mail-kind report '이번 실행 결과와 남은 대상'
kadan send 제품-감독 --work 저장소/work-product-photos --expect-reply '연결 결과 확인 요청'
kadan send 비서 --reply-to '원본우편ID' '받은 내용에 대한 답장'
```

`--work`와 `--execution`은 편지의 연결 주소이며 실행 발령이 아니다. 실제 실행을 발령하는 `--task`가 업무에 연결된 실행이면 업무 주소도 자동으로 남긴다. 답장은 원본의 업무·실행 주소를 질문을 보낸 시점 그대로 이어받는다(질문 뒤에 실행을 `work link`해도 답장에 업무를 새로 붙이지 않는다. 연결된 업무를 실행 주소에서 추론하는 것은 새 우편에만 쓴다). 원본에 업무가 없는데 답장에 `--work`를 붙이면 거절하고 `--work`를 빼라고 알린다. 같은 본문이 여러 번 발송되어 지문이 중복되면 고유한 우편 ID로 연결한다. `--task`와 `--execution`이 서로 다른 카드를 가리키면 전송 전에 실패한다. `--execution`만 썼는데 그 주소가 수신 역할에 발령된 중앙 카드이면 카드 없는 발령을 막기 위해 taskId를 추론해 발령으로 기록한다. 답장(`--reply-to`)과 다른 담당의 실행 연결은 추론하지 않고 우편 연결로만 남는다.

업무 인박스는 같은 DB의 우편원장에서 send·mail-read·mail-cancel을 읽고 과거 이력도 호환 조회한다. 별도 DB나 자동 읽음 처리는 만들지 않았다. 모든 역할의 받은·보낸 편지와 질문의 답변 대기를 확인한다. 읽음·중간 답장은 질문을 끝내지 않고 최종 답장 또는 질문 취소로 끝낸다. 자세한 명령과 상태는 [작업·우편 원장 계약](mail-task-ledgers.md)을 따른다. 본문은 기존 `mail/<지문>.txt`를 읽는다. 과거 편지는 연결한 실행의 고유 ID 또는 명시한 우편 ID로 묶는다. 연결 정보가 없는 일반 대화는 자동 수집하지 않는다. 한 화면에 100통씩 보며 이전 편지도 이동해서 읽는다.

## 저장과 기존 기록

업무 사건은 기존 저장 모듈의 `works/<저장소>/<업무ID>/events.jsonl` 스트림을 쓴다. 현재 운영에서는 **같은 `kadan.sqlite`의 events/heads**에 저장한다. 새 DB 파일이나 의존성을 추가하지 않는다. 같은 작업 영역에서 발령·완료 사건은 `tasks/events.jsonl`에 기록하며 업무·실행 카드의 상태 이력과 함께 유지한다. 실행 done의 자동 결과 우편은 우편함 저장이며 터미널 깨움·검수 합격·업무 최종 완료를 뜻하지 않는다.

새 업무부터 이 방식을 쓴다. 과거 카드·실행·DONE·우편은 삭제하거나 일괄 재해석하지 않는다. 기존 랠리는 당시 실행 묶음으로 남기며, 업무 완료 기록의 대용으로 쓰지 않는다. 기존 기록을 연결하려면 업무를 만들고 실행을 명시적으로 연결한다. 현재 연결을 정정해도 과거 연결 사건과 실행 원문은 보존한다.

### 대시보드 조회 재사용

화면 주소가 달라도 캐시 기간 안에서는 같은 수집 결과를 사용하며, 화면 변경으로 원본 수집 시각의 유효기간을 연장하지 않는다. 업무 흐름 정상 응답도 캐시하지만 원문·오류는 매번 확인한다. 캐시 반환 전에도 요청 방식·출처를 확인한다. 새로 읽기와 화면 저장 시도는 수집·응답 캐시를 모두 비운다.
