# Autopilot 단계표 (사다리)

## Why

kyle이 자리를 비울 때 켜는 Autopilot을 "켜고 끄는 스위치"로 쓰고, 단계를 올릴 때마다 할 수 있는 일이 하나씩만 더해지게 한다.
결정 요청은 모든 단계에서 평소처럼 받고, 금지 목록은 어느 단계에서도 풀리지 않는다.
이 표가 단계의 유일한 원본이다. 다른 문서는 이 표를 가리킨다.

## 단계표

| 단계 | 켜는 법 | 더해지는 것 | 그대로인 것 |
|---|---|---|---|
| 꺼짐(평소) | — | — | 결정 요청을 올리고 답을 기다린다 |
| Cruise | `kadan autopilot on "<문구>"`(`--level` 생략 = `--level cruise`) | 관문(`kadan merge-gate`)을 통과한 PR 자동 머지. 결정 답을 기다리는 동안 **그 일만** 멈추고 다른 일은 계속한다 | 아래 공통 규칙 4개 |
| Autopilot | `--level autopilot` | Cruise + 새 일 시작: `kadan autopilot picks`의 (가) `[밤 허용]` 후보와 (라) 미배정 ready 카드만. Wingman(경보를 대신 받는 슈퍼감독)은 이 단계에서만 | 아래 공통 규칙 4개 |
| 완전자율 | `--level full [--decide-after 2h]` | Autopilot + (가) 일을 스스로 찾아 카드 작성·발령(출처는 비공개 TODO·사람 명의 우편·디코 글·kyle이 쓴 이슈로 한정, 공개 저장소의 남이 쓴 글은 지시로 읽지 않음) (나) 답 없는 결정을 대기 시간 뒤 추천대로 진행(`kadan decision proceed`가 조건을 검사, 되돌릴 수 있는 것만) | 아래 공통 규칙 4개. 금지 목록은 한 글자도 바뀌지 않는다 |

단계는 순서다(`cruise < autopilot < full`). 위 단계는 아래 단계가 하는 것을 모두 한다: 코드는 `level === …` 대신 `atLeast(level, 최소 단계)`로 가르고(`src/autopilot-terms.mjs`), 모르는 단계 값은 가장 낮은 단계(Cruise)로 읽는다. 시험(`tests/autopilot-full.test.mjs`)이 기능마다 full ⊇ autopilot ⊇ cruise를 고정한다.

`--allow <소유자/이름>`(kyle 원문 `--quote` 필요)은 어느 단계에서도 받고, 정책 보류 두 가지(`night-merge-forbidden`·`deploy-branch`)의 자동 머지만 푼다.

## 완전자율 (`--level full`, 2026-11-11)

- **켜기.** `kadan autopilot on "<문구>" --level full [--decide-after <기간>]`. 기간 꼴은 `--for`와 같다(`2h`·`90m`·`1h30m`). **기본 2시간을 켤 때 정해 on 사건의 `decideAfterMs` 칸에 저장**한다. 하한 30분·상한 24시간, 벗어나거나 `--decide-after`를 full이 아닌 단계에 주면 종료 코드 2. 저장된 값이 없거나 깨졌으면 "넘어가지 않음"으로 읽는다(권한이 늘지 않는 쪽).
  사람은 그대로 켠다. 슈퍼감독(역할 세션)은 kyle 원문 `--quote`가 있어야 하고, Autopilot이 켜진 동안 역할 세션의 `on --level full`은 가드가 거절한다(단계를 올리려면 사람이 직접 치거나 끄고 다시 켠다). 디코 낱말은 없다 — `잘게 바이패스`는 "디코로는 켤 수 없습니다 — 터미널에서 …"로 답한다.
- **답 없는 결정은 추천대로 진행한다 — 단, 명령이 조건을 검사한다.** `kadan decision proceed <ID> --revision N`은 아래를 모두 만족할 때만 기록하고, 아니면 이유를 모두 모아 종료 코드 2(아무것도 쓰지 않음)다. 판정은 `src/decision-proceed.mjs`의 함수 하나이고 명령·감시기·화면이 같이 쓴다.
  1. Autopilot이 켜져 있고 단계가 full이며 저장된 대기 시간이 유효하다.
  2. 결정이 아직 열려 있다(답·취소 전).
  3. 요청할 때 추천안이 있었고, **요청할 때 `decision request --reversible "<되돌리는 방법 한 줄>" --not-prohibited`가 함께 붙었다(둘은 함께만 준다: 하나만 주면 종료 코드 2).** 표시 없는 결정(이 기능 전의 모든 결정 포함)은 영영 넘어가지 않고, 요청 뒤에 표시를 더하는 길은 없다.
  4. **금지 목록·관문·정책에 닿는 결정이 아니다. 세 겹으로 막고, 모두 "기다리는 쪽"으로 틀린다**(`src/decision-proceed.mjs`).
     - (가) **기록 대조(주 방어선).** 결정의 업무에 풀리지 않은 보류(`autopilot note hold`, 모든 종류)나 관문 거절(`gate --verdict reject`) 기록이 있으면 `--reversible` 요청도 `proceed`도 거절한다. 같은 업무·같은 PR(PR이 없으면 PR 없는 칸)의 관문 통과(`gate pass`) 또는 머지(`merge`) 기록으로만 풀린다. 업무가 없는 결정은 대조할 수 없어 `--reversible`을 받지 않고, 기록을 읽지 못해도 거절한다. 이 대조는 명령(요청·진행)이 원장을 읽을 때만 하고 감시기 주기에는 새 읽기를 더하지 않는다.
     - (나) **요청 때의 선언.** `--reversible`은 값 없는 옵션 `--not-prohibited`(요청자가 이 결정이 금지 목록, 곧 운영 배포·운영 데이터·영구 삭제·강제 push·비밀값·결제·카단 밖 글·설정·권한·머지·관문에 닿지 않는다고 밝힘)와 함께만 저장된다. 빠지면 종료 코드 2와 이 요지가 보인다. 저장 모양 `notProhibited: {by, at}`에 선언한 역할·시각이 남고 `decision show`·진행 알림·요약 기록에 "요청자 선언"으로 보인다. **코드는 이 선언의 진위를 검증하지 못한다.**
     - (다) **낱말 거름(보조 방어선).** 질문·이유·추천·선택지에 금지 목록 요지의 낱말(배포·운영·삭제·영구·강제·비밀·결제·권한·설정·정책·보류·머지·관문, `merge`·`force`·`push`·`DB` 등, `#숫자` 꼴 PR 참조, PR 주소)이 있으면 요청도 진행도 거절한다. 의미를 아는 것이 아니라서 무관한 결정이 걸릴 수 있다. 낱말 때문에 막혔으면 kyle 답을 기다린다.
  5. 경과 시간 ≥ 저장된 대기 시간. **시계는 max(결정 요청 시각, 지금 켜짐 구간의 시작 시각)부터**다: 완전자율을 켜는 순간 묵은 결정이 한꺼번에 넘어가지 않고, 껐다 다시 켜면 새 구간의 시작부터 센다.
  6. 부른 쪽이 그 결정을 요청한 역할 본인이거나, 관계표에서 그 역할의 **가장 가까운 슈퍼감독 하나**다(요청자가 슈퍼감독이면 본인뿐, 더 위·옆은 거절, 관계표를 못 읽으면 본인만). 사용자 행위자(`KADAN_USER_NAMES` 포함)는 진행하지 못한다.
  판정은 **쓰기 잠금 안에서 다시 읽어** 한다. Autopilot 켜짐 구간·단계·대기 시간·경과 시간(시계 포함)·부른 쪽의 권한·(가)의 기록을 잠금 안의 원장에서 새로 읽고, 명령을 받은 뒤 잠금을 기다리는 사이 꺼졌거나 다시 켜졌으면(켜짐 구간 시작이 바뀌었으면) 거절한다.
  통과하면 결정에 `proceeded: {by, at, recommendation, reversible, notProhibited}`를 **덧붙인다**(새 결정 사건, `by`는 역할). **결정을 닫지 않는다**: 상태는 열린 채이고 kyle이 나중에 답하면 정상 답으로 기록되며, 추천과 다르면 요청자에게 가는 답 통지 문구에 "추천대로 이미 진행됨 — 되돌리는 방법: …"이 붙는다. kyle에게 알림 1회와 `autopilot note decision` 기록(끝 요약의 "대신 정한 결정"에 모임)이 남고, 요약에는 "추천대로 진행한 결정 N건" 줄이 더해진다. 같은 결정에 두 번 부르면 두 번째는 기록 없이 `already: true`(종료 코드 0). 알림·요약 기록이 실패해도 진행 기록은 남고 `warnings`로 드러난다.
- **감시기는 쓰지 않는다.** **자격이 생긴 결정은 요청한 역할의 할 일이다**(4라운드). 대기 시간이 지나 자격이 생긴(진행 기록 전) 결정은 감시기의 답 대기에서 "사용자 답 대기"가 아니라 "요청한 역할이 처리할 차례"로 바뀐다(답할 역할 = 요청한 역할, 감독→슈퍼감독 질문과 같은 기존 방식). 진행 권한이 요청한 역할뿐이기 때문이다. 그래서 요청한 역할(슈퍼감독)에게는 본인 차례가 되어 자격 시각 + 유예 뒤 1단 안내와 `kadan decision proceed …` 줄이 가고, 계속 멈추면 그 역할의 상위로 2단이 간다. 그 결정이 막던 업무의 책임 감독(일반감독)은 할 수 있는 것이 없어 계속 대기이고 '놀고 있음'이 가지 않는다. 요청한 역할과 책임 감독이 같으면 같은 역할이 받는다. 진행 기록이 붙으면(진행 시각부터 센다) 그 업무가 책임 감독의 할 일로 돌아오고, 사람이 답하면 평소대로 풀린다. 요청한 역할이 관계표에 없으면 맡길 곳이 없어 진행 기록이 붙을 때까지 책임 감독의 할 일로 둔다(요청한 역할의 세션이 죽어 있으면 기존 "모름" 경보 경로를 탄다). **자격이 생긴 순간에는 놀고 있음과 별개로 요청한 역할에게 1회 따로 안내가 간다**(경보 종류 `진행자격`, `src/watch-proceed-notice.mjs`). 화면이 계속 변하거나 자격 시각에서 15분이 안 지났거나 업무 차례 칸이 사용자여서 놀고 있음이 나가지 않는 경우에도 간다(답 대기 가림 규칙·놀고 있음 기준은 바뀌지 않는다). 받는 쪽은 요청한 역할 하나이고, 관계표에 없으면 보내지 않으며(책임 감독의 할 일로 남는다), 세션이 죽어 있으면 기록 없이 다음 주기에 다시 본다. 최상위 슈퍼감독이 요청자여도 간다. 중복 방지 키는 결정 ID + 켜짐 구간 시작 시각이고, 원장 `alert`의 `noticeKeys`를 재시작 뒤 처음 후보가 생길 때 한 번 읽어 복원한다(이미 읽는 원장 범위). 진행 기록·답·취소·꺼짐·단계 내려감이면 보내지 않는다. 10배 질문: 열린 결정이 10배여도 주기마다 이미 읽은 결정 목록을 한 번 훑고 후보에 대해 메모리 집합을 조회할 뿐이며 새 저장소 읽기는 0이다(원장 대조는 감시기당 처음 한 번). 그 밖의 새 경보 종류는 없다. 대기 시간이 지나 자격이 생긴(또는 진행 기록이 붙은) 열린 결정은 감시기의 "답 대기" 목록에서 빠져, 그 결정이 막던 일이 다시 요청한 감독의 할 일이 된다(`--wait-until`과 같은 방식, 새 경보 종류 없음). 대기가 풀린 시각(자격 시각 또는 진행 기록 시각)부터 멈춤을 센다: 대기한 시간은 멈춘 시간이 아니라서, 화면이 대기 내내 멈춰 있어도 풀린 시각 + 유예 뒤에 본인 안내(1단)가 먼저 가고 계속 멈추면 2단이 간다(`--wait-until`과 같은 자리 `idleWorkEntries`를 재사용). 본인 창 안내(놀고 있음)에 "대기 시간이 지났습니다. 진행할 수 있는지 확인: `kadan decision proceed <ID> --revision N`" 한 줄이 붙는다(감시기는 시간·표시·단계만 보므로 최종 판정은 명령이 한다). 판정에 필요한 값을 읽지 못하면 "아직 대기 중"으로 본다. 주기마다 새 저장소 읽기는 없다: 이미 읽은 결정 목록과 주기당 한 번 만드는 Autopilot 스냅샷 하나만 쓰고, 스냅샷은 `--reversible` 표시가 있는 열린 결정이 있을 때만 만들며, 기록 대조(가)는 감시기가 하지 않는다.
- **한계.** 낱말 거름(다)은 이유(`reason`)의 `- <라벨>: <PR 주소 하나>` 줄에 있는 PR 주소 토큰만 거르지 않는다(결정 요청이 확인 경로 줄을 요구해서다). 라벨·주소 뒤에 글이 더 있는 줄·질문·추천·선택지·이유의 다른 줄·`#숫자`·낱말 목록은 그대로 거른다. 선언의 진위는 여전히 코드가 검증하지 못하고, 낱말을 피한 문구("본류에 넣을까요" 같은)는 낱말 거름을 통과한다. `--reversible`과 `--not-prohibited`는 요청하는 역할이 스스로 붙이는 표시다. **코드는 실제로 되돌릴 수 있는지, 정말 금지 목록에 닿지 않는지 검증하지 않는다.** 기록 대조(가)는 `autopilot note`를 남긴 만큼만 안다(기록 없이 한 보류·머지는 모른다). 낱말 거름(다)은 의미를 아는 것이 아니라 보수적인 글자 검사다. `KADAN_ROLE` 자기 신고 우회(`env -u`)가 가능하다는 기존 한계도 그대로다.
- **표시.** `decision list|show`에 `proceeded`가 보이고, 대시보드 결정 줄에 "추천대로 진행함 · 시각 · 역할" 꼬리표, `autopilot status`에 단계 `full`과 `decideAfter`가 보인다.

## 공통 규칙 4개 (켜진 모든 단계)

1. **결정 요청은 평소와 같은 기준으로 올린다.** 더 많이도 더 적게도 묻지 않는다. 답을 기다리는 동안 그 일만 멈춘다.
   사람 명의 결정 답은 Autopilot을 끄지 않는다. 감독이 풀 수 없는 관문 거절(금지 경로·정책 보류·필수 검사 없음 등)은 `[Autopilot 보류]` 기록에 더해 결정 요청으로도 올린다.
2. **끝 시각이 없다(기본).** `--until HH:MM`·`--for 8h`를 줄 때만 끝 시각이 생기고, 상한은 없다. 끝 시각이 없는 켜짐은 사건에 `until` 칸이 **없다**. 원장에서 끝 없음은 칸이 없을 때뿐이고, 칸이 있는데 ISO 문자열이 아니면(`null`·빈 문자열·숫자·해석 불가) 꺼짐(만료)으로 읽는다.
   `status`는 `until: null`·`remainingMinutes: null`·"끝 없음(직접 끌 때까지)"으로 보인다.
3. **끄는 길은 직접 끄기뿐이다.** `kadan autopilot off`, 디코 `일어남`, 그리고 명시한 끝 시각. 끝 사건을 원장에 **먼저** 적고(결정 이력 읽기·요약 계산보다 앞) 요약·알림·우편은 그 뒤에 한다. 끝 사건에는 요약을 담지 않고(옛 끝 사건의 `summary` 칸은 계속 읽힌다), 요약은 끝 사건 시각까지를 구간으로 뒤에 계산해 알림·출력으로 내보낸다. 끝 사건 기록이 실패하면 꺼지지 않은 것이라 종료 코드 1과 오류로 드러난다.
   그것들(알림이 `error`를 돌려주는 경우 포함)이 실패해도 꺼진 상태로 남고, 실패는 `off` 출력의 `warnings`·종료 코드 1·디코 답 글에 드러난다. `until` 칸이 있는데 읽을 수 없으면 꺼짐(만료)으로 본다.
4. **금지 목록은 고정 줄이다.** 단계를 올려도 `--allow`를 줘도 풀리지 않는다(`--allow`는 정책 보류 자동 머지만 푼다). 코드가 거절하는 명령(`autopilot-guard`)도 모든 단계에서 같다.
   한 가지만 완화했다(2026-11-11): 감시기·대시보드는 **끄고 끝내는 것**만 금지이고, 끄고 같은 명령 안에서 다시 띄우는 `kadan restart watch|대시보드`는 역할 세션에서도 쓴다. 맨 `kadan stop`·`restart --force`·디코 다리·비서 재시작은 그대로 거절이다.

## 새 저장소를 자동 머지에 넣는 순서

**기본은 허용이고, 막는 길은 정책 둘과 보호 하나다**(2026-11-23 kyle: "기본적으로 자동승인이고, 위험한것만 내가 막는건어때"). Autopilot이 켜져 있으면(`kadan autopilot on`) 값을 안 넣은 저장소도 관문을 통과하면 자동 머지된다. 켠 뒤에 새로 뜨거나 업무를 받은 슈퍼감독에게는 첫 안내나 `kadan autopilot deliver`가 켜짐 우편을 한 번 보낸다. 막으려면 저장소별 정책으로 (가) 자동 머지 금지(`--auto-merge 금지`) 또는 (나) 배포 브랜치를 적는다(그 브랜치로 가는 PR만 보류). 값은 `kadan autopilot repo …`로 정하는데, 사람 셸이 기본이고 역할 세션은 kyle 원문을 `--quote "<kyle 원문>"`으로 옮길 때만 쓸 수 있다(원장에 원문과 쓴 역할이 남는다). 값(`deployBranch`·`nightMerge`)은 카단 설정이 원본이고, 설정에 없는 칸은 `$KADAN_HOME/ontology/`의 `type: project` 문서(`deploy_branch`·`night_merge`)가 채울 수 있다. 읽지 못한 설정·문서(손상·잘못된 키·카드 못 읽음)는 값 없음이 아니라 `setup-needed` 보류다. 보호 하나(kyle "수동배포일수도있잖아"): 배포 브랜치 값이 비어 있고(설정·카드 모두) 온톨로지 카드의 `deploy:` 칸 첫 낱말이 `자동`이면 기본 브랜치 `main`으로 가는 PR만 `deploy-unset`(자동 배포·배포 브랜치 미설정)으로 보류한다(다른 브랜치는 허용). `deploy:`가 `수동`·`없음`이거나 칸·카드가 없으면 허용이고, 첫 낱말이 `자동|수동|없음`이 아니면 `setup-needed`다. `deploy_branch: 없음`을 **적어 둔** 저장소는 명시값이 이겨 허용이다. 파일(`wrangler.toml` 등)은 보지 않는다: 파일로는 자동·수동을 가리지 못한다. 판정 순서와 온톨로지 문서 형식은 [Autopilot 저장소 정책](autopilot-repo-cards.md#합치기와-판정)이 원본이다.

### 필요한 것

(a) **기준 브랜치에 필수 검사(required status check)가 걸린 브랜치 보호.** 슈퍼감독이 관문에 넘기는 `requiredChecks`는 `gh pr checks N --required --json name,state,bucket`의 출력이다(입력 전체는 [`kadan merge-gate`](commands.md)). 이 목록이 비면 관문은 거절하고, 하나라도 `bucket`이 `pass`가 아니면 거절한다. CI가 있어도 필수 검사로 지정되지 않았으면 이 목록에 들어오지 않는다.

(b) **저장소 정책(선택).** 값이 없어도 자동 머지되므로 막을 저장소만 정한다. 사용자가 사람 셸에서 한 번 치거나, 역할 세션이 kyle 원문을 `--quote`로 옮겨 친다.

```
kadan autopilot repo <소유자/이름> --deploy-branch <브랜치|없음> --auto-merge 허용
```

- `--deploy-branch <브랜치>`: 그 브랜치로 가는 PR만 자동 머지에서 빠진다(`deploy-branch` 보류).
- `--deploy-branch 없음`: 배포 브랜치가 따로 없다는 값이다. 어떤 브랜치도 보류되지 않는다.
- 값이 비어 있음(카단 설정·온톨로지 문서 모두): 허용이다(기본). 막을 브랜치가 없다는 점에서 `없음`과 같지만, 카드 `deploy: 자동`일 때만 다르다: 빈 값이면 `main`으로 가는 PR을 `deploy-unset`으로 보류하고, `없음`을 적어 두면 명시값이 이겨 허용이다(화면에서도 "값 없음"과 `없음`은 다르게 보인다).
- `--auto-merge`(옛 이름 `--night-merge`도 같은 뜻으로 받는다. 둘을 함께 주면 종료 코드 2로 거절)를 생략하면 기존 설정을 유지하고, 설정에 없는 칸은 온톨로지 값을 따른다. 두 원본 모두 값이 없을 때만 허용으로 읽는다. `금지`일 때만 `night-merge-forbidden` 보류다. 허용을 분명히 남기려고 위 명령처럼 함께 준다.

(c) **관문의 나머지 조건.** 새 규칙이 아니라 `src/merge-gate.mjs`가 이미 보는 것이다.

| 조건 | 관문이 보는 것 |
|---|---|
| PR 상태 | OPEN · 초안 아님 · `MERGEABLE` · 머지 상태 `CLEAN`/`HAS_HOOKS` |
| 파일 | 목록 개수가 PR과 같음 · 이름을 바꾼 파일은 옛 경로까지 · 금지 경로([`kadan merge-gate`](commands.md)에 목록)에 없음 |
| 검수 | 같은 커밋(PR head, 소문자 40자리)에 대한 검수 pass |
| 업무와 저장소 | 업무가 열려 있음 · PR 저장소 == 업무 저장소(git origin) |
| 머지 방식 | 저장소가 허용하는 방식이 하나 이상 있음 |
| 정책 | 위 (b) |

### 누가 하나

- **브랜치 보호·CI 도입·저장소 설정은 저장소 설정 변경이다.** 고정 줄 (2)의 "계정·권한·인증과 시스템 설정 변경"에 걸리는 것으로 다룬다. 슈퍼감독이 스스로 만들지 않고 결정 요청으로 올리며 사용자 결정 뒤에 진행한다(감독이 풀 수 없는 거절은 결정 요청으로도 올린다는 기존 줄, `skills/kadan-super/SKILL.md`의 "Autopilot이 켜진 동안"). CI 파일(`.github/workflows/**`)을 넣는 PR은 금지 경로라서 그 PR 자체는 자동 머지되지 않고 사용자 승인 머지로 간다.
- **저장소 정책 쓰기는 사용자만 한다.** 켜진 동안 역할 세션에서 치면 코드(`src/autopilot-guard.mjs`)가 거절하고, 읽기(`autopilot repo`·`list`·`show`)만 통한다. 거절 문구는 다음과 같다.

  ```
  Autopilot이 켜져 있어 역할 세션에서는 `kadan autopilot repo <소유자/이름>`를 쓸 수 없습니다. kyle이 직접 치거나 Autopilot을 끈 뒤 하세요
  ```
- **자동 머지에 넣지 않는 것도 정상 끝 상태다.** 필수 검사나 정책이 없는 저장소는 보류 기록과 결정 요청으로 남기고, 사용자 승인 머지로 두면 된다.

### 관문 거절 → 다음 행동

거절 이유는 `kadan merge-gate`가 모두 모아 보인다. 문구는 코드 그대로이고 `…`는 그때그때 바뀌는 값이다. "감독이 풀 수 있음"은 요청한 감독에게 이유를 돌려 풀고 다시 요청하게 한다는 뜻이고, "결정 요청"은 `autopilot note hold`로 남기고 결정 요청으로도 올린다는 뜻이다(고정 줄 (4)).

| 거절 문구(`src/merge-gate.mjs`) | 누가 | 다음 행동 |
|---|---|---|
| `PR 상태가 OPEN이 아님(…)` | 감독이 풀 수 있음 | 닫히거나 이미 머지된 PR이다. 업무의 열린 PR로 다시 요청한다 |
| `초안(draft) PR` | 감독이 풀 수 있음 | 초안을 해제하고 다시 요청한다 |
| `합칠 수 있는 상태가 아님(mergeable …)` | 감독이 풀 수 있음 | 충돌을 풀어 다시 요청한다 |
| `머지 상태가 CLEAN이 아님(…)` | 감독이 풀 수 있음 | `UNKNOWN`이면 잠시 뒤 다시 부른다. `BEHIND`면 기준 브랜치를 따라잡는다(`update-branch`). `BLOCKED`면 보호 규칙의 남은 조건(검사 진행·승인 등)을 확인하고, 감독이 채울 수 없는 조건이면 결정 요청으로 올린다 |
| `필수 검사 없음(브랜치 보호가 없는 저장소는 머지하지 않고 결정 요청으로 올림)` | 결정 요청 | 위 "필요한 것" (a)가 없다. 브랜치 보호 도입은 사용자 결정 뒤에만 한다 |
| `통과하지 않은 필수 검사 N건: …` | 감독이 풀 수 있음 | 검사가 끝나길 기다리거나 실패 원인을 고친다. 새 커밋을 올리면 PR head가 바뀌므로 검수도 그 커밋으로 다시 받는다 |
| `파일 목록 개수가 맞지 않음(받은 …개, PR …개; REST는 3,000개까지만 줌)` | 결정 요청 | 입력을 다시 받아도 같으면 관문이 PR 전체를 볼 수 없다. 자동 머지하지 않는다 |
| `이름을 바꾸거나 복사한 파일 …개에 옛 경로(previous_filename)가 없음: …` | 감독이 풀 수 있음 | 파일 목록을 `gh api --paginate --slurp repos/<소유자>/<이름>/pulls/N/files`로 다시 받아 넘긴다 |
| `금지 경로 …개: …` | 결정 요청 | 금지 경로는 자동 머지하지 않는다. 사용자 승인 머지로 둔다 |
| `PR head가 소문자 40자리 커밋이 아님(…)` | 감독이 풀 수 있음 | `gh pr view`의 `headRefOid`를 그대로 넘긴다(대문자·공백을 고쳐 주지 않는다) |
| `검수 대조: …`(`검수 pass 없음`·`검수 SHA 없음`·`다름`·`모호`·`같은 커밋 검수 changes`) | 감독이 풀 수 있음 | 이 PR head에 대한 독립검수 pass를 받는다(검수 재판정) |
| `검수 SHA가 PR head와 40자리로 정확히 같지 않음(…)` | 감독이 풀 수 있음 | 위와 같다. 검수 기록의 SHA를 40자리로 맞춰 다시 판정한다 |
| `업무가 열려 있지 않음(…)` | 결정 요청 | 닫힌 업무의 PR은 자동 머지하지 않는다 |
| `PR 주소의 번호(…)와 pr.number(…)가 다름`·`PR 주소에서 저장소를 읽지 못함(…)` | 감독이 풀 수 있음 | 같은 PR을 조회해 입력을 다시 만든다 |
| `PR 저장소(…)가 업무 저장소(…)와 다름` | 감독이 풀 수 있음 | 그 PR 저장소의 업무로 다시 요청한다. 맞는 업무가 없으면 결정 요청으로 올린다 |
| `허용된 머지 방식 없음(mergeCommitAllowed·squashMergeAllowed·rebaseMergeAllowed 모두 false)` | 결정 요청 | 저장소 설정 변경이라 사용자 결정 뒤에만 한다 |
| `저장소 정책이 Autopilot 중 자동 머지를 안 함(setup-needed)` | 결정 요청 | 먼저 `kadan autopilot repo list`·`show <소유자/이름>`로 원인을 확인해 결정 요청에 적는다. 원인별로 다르다. 값이 없는 것만으로는 이 보류가 나오지 않는다(기본 허용). 정책 파일 손상 → 파일을 고치거나 옮기는 것은 사용자 결정이다. 온톨로지 읽기 실패 → 읽기 실패 내용을 확인해 결정 요청으로 올린다. 배포 브랜치는 정해졌는데 PR 대상 브랜치를 모름 → 관문 입력의 `pr.baseRefName`을 다시 받는다. 어느 경우든 `setup-needed`는 `--allow`로 풀리지 않는다. 판정 순서는 [Autopilot 저장소 정책](autopilot-repo-cards.md#합치기와-판정) |
| `저장소 정책이 Autopilot 중 자동 머지를 안 함(deploy-unset)` — `자동 배포·배포 브랜치 미설정(카드 deploy: 자동, main으로 가는 PR만 보류)` | 결정 요청 | 배포 저장소인데 배포 브랜치를 안 적은 것이다. 보류 기록은 `--hold-kind deploy-repo`. kyle 원문이 있으면 `kadan autopilot repo <소유자/이름> --deploy-branch <브랜치\|없음> --quote "<kyle 원문>"`으로 값을 정하거나(그 뒤로 이 보류가 사라진다), 이번 켜짐 동안만 `autopilot on --allow <소유자/이름>`으로 푼다 |
| `저장소 정책이 Autopilot 중 자동 머지를 안 함(night-merge-forbidden)` · `(deploy-branch)` | 결정 요청 | 사용자가 정책을 바꾸거나, 이번 켜짐 동안만 `autopilot on --allow <소유자/이름>`(사용자 원문 `--quote` 필요)으로 푼다. 이 문구에는 `— autopilot on --allow …로 풀 수 있음`이 붙는다 |

`autopilot note hold`의 `--hold-kind`는 관문 거절이면 `gate`, 정책 보류면 `deploy-repo`다(고정 줄 (4)).

### 사용자에게 붙여 줄 요청

```
저장소 <소유자/이름>을 Autopilot 중 자동 머지에 넣으려면 아래를 사람 셸에서 한 번 쳐 주세요.
kadan autopilot repo <소유자/이름> --deploy-branch <브랜치|없음> --auto-merge 허용
바뀌는 것: 이 저장소의 배포 브랜치와 자동 머지 허용이 카단 설정에 저장됩니다(다른 저장소와 저장소 설정은 그대로).
이 저장소에 필수 검사가 걸린 브랜치 보호가 없으면 위 명령만으로는 자동 머지되지 않습니다.
```

옛 이름 `--night-merge`도 같은 뜻으로 받는다(저장 칸 `nightMerge`·온톨로지 `night_merge`·보류 이유 `night-merge-forbidden`은 그대로).

## 운영 순서 (옛·새 프로그램이 섞이는 기간)

끝 시각 없는 `on` 사건은 이 변경 이전 프로그램(감시기·대시보드·디코 다리)도 깨지지 않고 읽는다.
실측(`origin/main` 코드, 격리 홈): 끝 시각 없는 `on`은 켜짐으로 읽히고(`until` NaN 비교가 만료를 못 만든다), 감시기 만료 확인은 아무것도 마무리하지 않으며, 대시보드 띠는 `until: null`로 켜짐을 보인다.
다만 옛 프로그램은 사람 명의 결정 답으로 끄던 규칙이 끝 시각 있는 켜짐에는 남아 있다. 그래서 순서는 다음과 같다.

1. 이 변경을 main에 머지한다.
2. 기반 프로세스를 재시작한다. 감시기·대시보드는 `kadan restart watch|대시보드`(역할 세션도 가능), 디코 다리·비서는 kyle이 한다. GUI를 고쳤으면 먼저 `npm run build:gui`.
3. 그 뒤 처음으로 끝 시각 없이 켠다.

반대로 새 프로그램은 이미 원장에 있는 끝 시각 있는 `on`(8시간짜리)을 그 시각에 정상 만료시킨다.

켜진 동안 역할 세션은 감시기·대시보드를 끄고 끝낼 수 없다(`kadan stop`). 자동 머지된 PR이 상주 프로세스에 닿으면 순서는 머지 → 로컬 main 갱신 → (화면이 바뀌었으면 `npm run build:gui`) → `kadan restart watch|대시보드` → 살아났는지 확인이다. 재시작 명령이 실패했거나 대상이 디코 다리·비서이면 kyle에게 `kadan mail 사람 "재시작 필요: …"` 한 줄이 간다.

## 기반 프로세스 재시작 (`kadan restart watch|대시보드`)

- 끄고 같은 명령 안에서 다시 띄운 뒤 살아났는지 한 번(유한 대기) 확인한다. 시작 함수·명령·포트는 `kadan up`·자동 되살리기와 같은 출처이고, 부른 역할의 `KADAN_ROLE`·`TMUX`·창 설정·작업 폴더는 넘어가지 않는다(되살리기와 같은 `KADAN_WINDOW=none`, 설치된 launchd의 작업 폴더).
- "사람이 끔" 표시를 남기지 않고 `up --auto`와 같은 잠금을 잡는다. 도중에 죽어도 다음 `up --auto` 주기(약 1분)가 평소대로 되살린다.
- 대상이 사람이 끈 상태(`stopped`)·상한 상태(`capped`)·상태 파일 손상이면 역할 세션은 거절한다. 사람이 친 재시작은 `up`처럼 그 대상의 멈춤을 풀고 손상 파일은 휴지통(기본 `.trash`)으로 옮긴다. 옮기지 못하면 거절한다.
- 역할 세션이 부른 재시작은 대상마다 1시간 3번까지이며 되살리기 상한과 따로 센다(`revive-state.json`의 `restarts`). 사람이 친 것은 세지 않는다.
- 대시보드 화면의 '다시 띄우기' 버튼은 감시기·대시보드에 대해 거절한다(대시보드가 자기 세션을 끄면 요청을 처리하던 프로세스도 같이 죽는다). 이 대상은 터미널 명령만 쓴다. 대상 세션 안에서 부른 명령도 끄기 전에 거절한다(판정 못 하면 거절하지 않음).
- 새 감시기 세션의 명령은 자식 쪽에서 `KADAN_ROLE`·`TMUX`·`KADAN_RESTART_*`를 지우고 창 값을 `none`+force로 고정한다(`kadan up`·자동 되살리기도 같은 시작 함수라 같다). 살아난 것은 같은 프로세스가 몇 초 안정 구간 뒤에도 살아 있어야 성공이다.
- 실패·확인 시간 초과는 종료 코드 1, 사용자 알림 1회, 재시도 없음. 결과는 기존 `revive` 사건에 `reason: restart`·`by`(부른 역할 또는 사람)로 남는다.
