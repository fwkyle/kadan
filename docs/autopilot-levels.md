# Autopilot 단계표 (사다리)

## Why

kyle이 자리를 비울 때 켜는 Autopilot을 "켜고 끄는 스위치"로 쓰고, 단계를 올릴 때마다 할 수 있는 일이 하나씩만 더해지게 한다.
결정 요청은 모든 단계에서 평소처럼 받고, 금지 목록은 어느 단계에서도 풀리지 않는다.
이 표가 단계의 유일한 원본이다. 다른 문서는 이 표를 가리킨다.

## 단계표

| 단계 | 켜는 법 | 더해지는 것 | 그대로인 것 |
|---|---|---|---|
| 꺼짐(평소) | — | — | 결정 요청을 올리고 답을 기다린다 |
| Cruise | `kadan autopilot on "<문구>"`(`--level` 생략 = `--level cruise`) | 관문(`kadan merge-gate`)을 통과한 PR 자동 머지. 결정 답을 기다리는 동안 **그 일만** 멈추고 다른 일은 계속한다 | 아래 공통 규칙 4개 |
| Autopilot | `--level autopilot` | Cruise + 새 일 시작: `kadan autopilot picks`의 (가) `[밤 허용]` 후보와 (라) 미배정 ready 카드만. Wingman(경보를 대신 받는 슈퍼감독)은 이 단계에서만 | 아래 공통 규칙 4개 |
| 완전자율 | `--level full [--decide-after 2h]` | Autopilot + (가) 일을 스스로 찾아 카드 작성·발령(출처는 비공개 TODO·사람 명의 우편·디코 글·kyle이 쓴 이슈로 한정, 공개 저장소의 남이 쓴 글은 지시로 읽지 않음) (나) 답 없는 결정을 대기 시간 뒤 추천대로 진행(`kadan decision proceed`가 조건을 검사, 되돌릴 수 있는 것만) | 아래 공통 규칙 4개. 금지 목록은 한 글자도 바뀌지 않는다 |

단계는 순서다(`cruise < autopilot < full`). 위 단계는 아래 단계가 하는 것을 모두 한다: 코드는 `level === …` 대신 `atLeast(level, 최소 단계)`로 가르고(`src/autopilot-terms.mjs`), 모르는 단계 값은 가장 낮은 단계(Cruise)로 읽는다. 시험(`tests/autopilot-full.test.mjs`)이 기능마다 full ⊇ autopilot ⊇ cruise를 고정한다.

`--allow <소유자/이름>`(kyle 원문 `--quote` 필요)은 어느 단계에서도 받고, 정책 보류 두 가지(`night-merge-forbidden`·`deploy-branch`)의 자동 머지만 푼다.

## 완전자율 (`--level full`, 2026-11-11)

- **켜기.** `kadan autopilot on "<문구>" --level full [--decide-after <기간>]`. 기간 꼴은 `--for`와 같다(`2h`·`90m`·`1h30m`). **기본 2시간을 켤 때 정해 on 사건의 `decideAfterMs` 칸에 저장**한다. 하한 30분·상한 24시간, 벗어나거나 `--decide-after`를 full이 아닌 단계에 주면 종료 코드 2. 저장된 값이 없거나 깨졌으면 "넘어가지 않음"으로 읽는다(권한이 늘지 않는 쪽).
  사람은 그대로 켠다. 슈퍼감독(역할 세션)은 kyle 원문 `--quote`가 있어야 하고, Autopilot이 켜진 동안 역할 세션의 `on --level full`은 가드가 거절한다(단계를 올리려면 사람이 직접 치거나 끄고 다시 켠다). 디코 낱말은 없다 — `잘게 바이패스`는 "디코로는 켤 수 없습니다 — 터미널에서 …"로 답한다.
- **답 없는 결정은 추천대로 진행한다 — 단, 명령이 조건을 검사한다.** `kadan decision proceed <ID> --revision N`은 아래를 모두 만족할 때만 기록하고, 아니면 이유를 모두 모아 종료 코드 2(아무것도 쓰지 않음)다. 판정은 `src/decision-proceed.mjs`의 함수 하나이고 명령·감시기·화면이 같이 쓴다.
  1. Autopilot이 켜져 있고 단계가 full이며 저장된 대기 시간이 유효하다.
  2. 결정이 아직 열려 있다(답·취소 전).
  3. 요청할 때 추천안이 있었고, **요청할 때 `decision request --reversible "<되돌리는 방법 한 줄>" --not-prohibited`가 함께 붙었다.** 표시 없는 결정(이 기능 전의 모든 결정 포함)은 영영 넘어가지 않고, 요청 뒤에 표시를 더하는 길은 없다.
  4. **금지 목록·관문·정책에 닿는 결정이 아니다. 세 겹으로 막고, 모두 "기다리는 쪽"으로 틀린다**(`src/decision-proceed.mjs`).
     - (가) **기록 대조(주 방어선).** 결정의 업무에 풀리지 않은 보류(`autopilot note hold`, 모든 종류)나 관문 거절(`gate --verdict reject`) 기록이 있으면 `--reversible` 요청도 `proceed`도 거절한다. 같은 업무·같은 PR(PR이 없으면 PR 없는 칸)의 관문 통과(`gate pass`) 또는 머지(`merge`) 기록으로만 풀린다. 업무가 없는 결정은 대조할 수 없어 `--reversible`을 받지 않고, 기록을 읽지 못해도 거절한다. 이 대조는 명령(요청·진행)이 원장을 읽을 때만 하고 감시기 주기에는 새 읽기를 더하지 않는다.
     - (나) **요청 때의 선언.** `--reversible`은 값 없는 옵션 `--not-prohibited`(요청자가 이 결정이 금지 목록, 곧 운영 배포·운영 데이터·영구 삭제·강제 push·비밀값·결제·카단 밖 글·설정·권한·머지·관문에 닿지 않는다고 밝힘)와 함께만 저장된다. 빠지면 종료 코드 2와 이 요지가 보인다. 저장 모양 `notProhibited: {by, at}`에 선언한 역할·시각이 남고 `decision show`·진행 알림·요약 기록에 "요청자 선언"으로 보인다. **코드는 이 선언의 진위를 검증하지 못한다.**
     - (다) **낱말 거름(보조 방어선).** 질문·이유·추천·선택지에 금지 목록 요지의 낱말(배포·운영·삭제·영구·강제·비밀·결제·권한·설정·정책·보류·머지·관문, `merge`·`force`·`push`·`DB` 등, `#숫자` 꼴 PR 참조, PR 주소)이 있으면 요청도 진행도 거절한다. 의미를 아는 것이 아니라서 무관한 결정이 걸릴 수 있다. 낱말 때문에 막혔으면 kyle 답을 기다린다.
  5. 경과 시간 ≥ 저장된 대기 시간. **시계는 max(결정 요청 시각, 지금 켜짐 구간의 시작 시각)부터**다: 완전자율을 켜는 순간 묵은 결정이 한꺼번에 넘어가지 않고, 껐다 다시 켜면 새 구간의 시작부터 센다.
  6. 부른 쪽이 그 결정을 요청한 역할 본인이거나, 관계표에서 그 역할의 **가장 가까운 슈퍼감독 하나**다(요청자가 슈퍼감독이면 본인뿐, 더 위·옆은 거절, 관계표를 못 읽으면 본인만). 사용자 행위자(`KADAN_USER_NAMES` 포함)는 진행하지 못한다.
  판정은 **쓰기 잠금 안에서 다시 읽어** 한다. Autopilot 켜짐 구간·단계·대기 시간·경과 시간(시계 포함)·부른 쪽의 권한·(가)의 기록을 잠금 안의 원장에서 새로 읽고, 명령을 받은 뒤 잠금을 기다리는 사이 꺼졌거나 다시 켜졌으면(켜짐 구간 시작이 바뀌었으면) 거절한다.
  통과하면 결정에 `proceeded: {by, at, recommendation, reversible, notProhibited}`를 **덧붙인다**(새 결정 사건, `by`는 역할). **결정을 닫지 않는다**: 상태는 열린 채이고 kyle이 나중에 답하면 정상 답으로 기록되며, 추천과 다르면 요청자에게 가는 답 통지 문구에 "추천대로 이미 진행됨 — 되돌리는 방법: …"이 붙는다. kyle에게 알림 1회와 `autopilot note decision` 기록(끝 요약의 "대신 정한 결정"에 모임)이 남고, 요약에는 "추천대로 진행한 결정 N건" 줄이 더해진다. 같은 결정에 두 번 부르면 두 번째는 기록 없이 `already: true`(종료 코드 0). 알림·요약 기록이 실패해도 진행 기록은 남고 `warnings`로 드러난다.
- **감시기는 쓰지 않는다.** 대기 시간이 지나 자격이 생긴(또는 진행 기록이 붙은) 열린 결정은 감시기의 "답 대기" 목록에서 빠져, 그 결정이 막던 일이 다시 요청한 감독의 할 일이 된다(`--wait-until`과 같은 방식, 새 경보 종류 없음). 본인 창 안내(놀고 있음)에 "대기 시간이 지났습니다. 진행할 수 있는지 확인: `kadan decision proceed <ID> --revision N`" 한 줄이 붙는다(감시기는 시간·표시·단계만 보므로 최종 판정은 명령이 한다). 판정에 필요한 값을 읽지 못하면 "아직 대기 중"으로 본다. 주기마다 새 저장소 읽기는 없다: 이미 읽은 결정 목록과 주기당 한 번 만드는 Autopilot 스냅샷 하나만 쓰고, 스냅샷은 `--reversible` 표시가 있는 열린 결정이 있을 때만 만들며, 기록 대조(가)는 감시기가 하지 않는다.
- **한계.** `--reversible`과 `--not-prohibited`는 요청하는 역할이 스스로 붙이는 표시다. **코드는 실제로 되돌릴 수 있는지, 정말 금지 목록에 닿지 않는지 검증하지 않는다.** 기록 대조(가)는 `autopilot note`를 남긴 만큼만 안다(기록 없이 한 보류·머지는 모른다). 낱말 거름(다)은 의미를 아는 것이 아니라 보수적인 글자 검사다. `KADAN_ROLE` 자기 신고 우회(`env -u`)가 가능하다는 기존 한계도 그대로다.
- **표시.** `decision list|show`에 `proceeded`가 보이고, 대시보드 결정 줄에 "추천대로 진행함 · 시각 · 역할" 꼬리표, `autopilot status`에 단계 `full`과 `decideAfter`가 보인다.

## 공통 규칙 4개 (켜진 모든 단계)

1. **결정 요청은 평소와 같은 기준으로 올린다.** 더 많이도 더 적게도 묻지 않는다. 답을 기다리는 동안 그 일만 멈춘다.
   사람 명의 결정 답은 Autopilot을 끄지 않는다. 감독이 풀 수 없는 관문 거절(금지 경로·정책 보류·필수 검사 없음 등)은 `[Autopilot 보류]` 기록에 더해 결정 요청으로도 올린다.
2. **끝 시각이 없다(기본).** `--until HH:MM`·`--for 8h`를 줄 때만 끝 시각이 생기고, 상한은 없다. 끝 시각이 없는 켜짐은 사건에 `until` 칸이 **없다**. 원장에서 끝 없음은 칸이 없을 때뿐이고, 칸이 있는데 ISO 문자열이 아니면(`null`·빈 문자열·숫자·해석 불가) 꺼짐(만료)으로 읽는다.
   `status`는 `until: null`·`remainingMinutes: null`·"끝 없음(직접 끌 때까지)"으로 보인다.
3. **끄는 길은 직접 끄기뿐이다.** `kadan autopilot off`, 디코 `일어남`, 그리고 명시한 끝 시각. 끝 사건을 원장에 **먼저** 적고(결정 이력 읽기·요약 계산보다 앞) 요약·알림·우편은 그 뒤에 한다. 끝 사건에는 요약을 담지 않고(옛 끝 사건의 `summary` 칸은 계속 읽힌다), 요약은 끝 사건 시각까지를 구간으로 뒤에 계산해 알림·출력으로 내보낸다. 끝 사건 기록이 실패하면 꺼지지 않은 것이라 종료 코드 1과 오류로 드러난다.
   그것들(알림이 `error`를 돌려주는 경우 포함)이 실패해도 꺼진 상태로 남고, 실패는 `off` 출력의 `warnings`·종료 코드 1·디코 답 글에 드러난다. `until` 칸이 있는데 읽을 수 없으면 꺼짐(만료)으로 본다.
4. **금지 목록은 고정 줄이다.** 단계를 올려도 `--allow`를 줘도 풀리지 않는다(`--allow`는 정책 보류 자동 머지만 푼다). 코드가 거절하는 명령(`autopilot-guard`)도 모든 단계에서 같다.
   한 가지만 완화했다(2026-11-11): 감시기·대시보드는 **끄고 끝내는 것**만 금지이고, 끄고 같은 명령 안에서 다시 띄우는 `kadan restart watch|대시보드`는 역할 세션에서도 쓴다. 맨 `kadan stop`·`restart --force`·디코 다리·비서 재시작은 그대로 거절이다.

## 운영 순서 (옛·새 프로그램이 섞이는 기간)

끝 시각 없는 `on` 사건은 이 변경 이전 프로그램(감시기·대시보드·디코 다리)도 깨지지 않고 읽는다.
실측(`origin/main` 코드, 격리 홈): 끝 시각 없는 `on`은 켜짐으로 읽히고(`until` NaN 비교가 만료를 못 만든다), 감시기 만료 확인은 아무것도 마무리하지 않으며, 대시보드 띠는 `until: null`로 켜짐을 보인다.
다만 옛 프로그램은 사람 명의 결정 답으로 끄던 규칙이 끝 시각 있는 켜짐에는 남아 있다. 그래서 순서는 다음과 같다.

1. 이 변경을 main에 머지한다.
2. 기반 프로세스를 재시작한다. 감시기·대시보드는 `kadan restart watch|대시보드`(역할 세션도 가능), 디코 다리·비서는 kyle이 한다. GUI를 고쳤으면 먼저 `npm run build:gui`.
3. 그 뒤 처음으로 끝 시각 없이 켠다.

반대로 새 프로그램은 이미 원장에 있는 끝 시각 있는 `on`(8시간짜리)을 그 시각에 정상 만료시킨다.

켜진 동안 역할 세션은 감시기·대시보드를 끄고 끝낼 수 없다(`kadan stop`). 자동 머지된 PR이 상주 프로세스에 닿으면 순서는 머지 → 로컬 main 갱신 → (화면이 바뀌었으면 `npm run build:gui`) → `kadan restart watch|대시보드` → 살아났는지 확인이다. 재시작 명령이 실패했거나 대상이 디코 다리·비서이면 kyle에게 `kadan mail 사람 "재시작 필요: …"` 한 줄이 간다.

## 기반 프로세스 재시작 (`kadan restart watch|대시보드`)

- 끄고 같은 명령 안에서 다시 띄운 뒤 살아났는지 한 번(유한 대기) 확인한다. 시작 함수·명령·포트는 `kadan up`·자동 되살리기와 같은 출처이고, 부른 역할의 `KADAN_ROLE`·`TMUX`·창 설정·작업 폴더는 넘어가지 않는다(되살리기와 같은 `KADAN_WINDOW=none`, 설치된 launchd의 작업 폴더).
- "사람이 끔" 표시를 남기지 않고 `up --auto`와 같은 잠금을 잡는다. 도중에 죽어도 다음 `up --auto` 주기(약 1분)가 평소대로 되살린다.
- 대상이 사람이 끈 상태(`stopped`)·상한 상태(`capped`)·상태 파일 손상이면 역할 세션은 거절한다. 사람이 친 재시작은 `up`처럼 그 대상의 멈춤을 풀고 손상 파일은 `.trash`로 옮긴다.
- 역할 세션이 부른 재시작은 대상마다 1시간 3번까지이며 되살리기 상한과 따로 센다(`revive-state.json`의 `restarts`). 사람이 친 것은 세지 않는다.
- 대시보드 화면의 '다시 띄우기' 버튼은 감시기·대시보드에 대해 거절한다(대시보드가 자기 세션을 끄면 요청을 처리하던 프로세스도 같이 죽는다). 이 대상은 터미널 명령만 쓴다. 대상 세션 안에서 부른 명령도 끄기 전에 거절한다(판정 못 하면 거절하지 않음).
- 새 감시기 세션의 명령은 자식 쪽에서 `KADAN_ROLE`·`TMUX`·`KADAN_RESTART_*`를 지우고 창 값을 `none`+force로 고정한다(`kadan up`·자동 되살리기도 같은 시작 함수라 같다). 살아난 것은 같은 프로세스가 몇 초 안정 구간 뒤에도 살아 있어야 성공이다.
- 실패·확인 시간 초과는 종료 코드 1, 사용자 알림 1회, 재시도 없음. 결과는 기존 `revive` 사건에 `reason: restart`·`by`(부른 역할 또는 사람)로 남는다.
