# 카단 라이트 용어

## Why

[kyle]과 에이전트가 감시 프로그램, AI 판단, 보고받는 감독을 같은 말로 혼동하지 않게 한다.

| 용어 | 뜻 | 구현/예시 |
| --- | --- | --- |
| 감시체계 | 작업 감시 세트와 감독 관찰을 포함하는 전체 구조 | 감시sh→작업 감시AI / 감독 관찰AI → 직속 상위 조치 |
| 감시sh | 현재 미완료 카드의 담당·상위 책임을 기준으로 화면·보고를 읽고 감시ai 호출과 호출 장애 감지를 수행하는 프로그램. 확실한 세션/PID·접속·보고 누락은 직접 알림. 완료 후 대기 역할은 제외하며 자원 수치는 대시보드에서 확인 | `kadan watch`. 실제 구현이 Node.js여도 이 이름을 사용 |
| 실행 스크립트 | 프로그램이나 AI 명령을 실행하는 연결 파일 | `scripts/watch-judge.sh` |
| 작업 감시AI | 감시sh가 고른 미완료 작업자·검수자의 막힘과 진전을 판단하고 보고하는 AI | 최초 무변화5분, 같은 실행·근거 재확인30분, 진행 검사와 호출 시각 공유 |
| 감독 관찰AI | 활성 책임이 있는 일반감독의 응답 상태를 관찰하는 AI | 기본1시간, 연결·압축 오류 지속5분이면 먼저 확인. 정당한 결과 대기는 정상 |
| 감시ai | 두 AI를 함께 가리키는 말. 실제 대상·보고에서는 위 두 이름을 구분 | DeepSeek v4.1 Flash max 기본 (2026-09-10 [kyle] 결정 — 신모델 출시로 승급). KADAN_JUDGE_MODEL로 반드시 지정(스크립트 기본값 없음, 2026-09-12). 실행기는 동시1개 공유 |
| 상신 | 판단할 담당자에게 알림을 올리는 것 | 작업자 → 일반감독 → 슈퍼감독 → 사용자 |
| 시작 보고 누락 | 발령 후 일정 시간이 지났지만 해당 담당의 시작·결과대기 또는 완료 증거가 없는 상태 | 직속 감독이 실제 착수 여부 확인 |
| 화면 무변화 | 화면 내용의 지문이 연속으로 같음 | 정체의 후보이며 그 자체가 중단 확정은 아님 |

감시ai는 상태를 판단하고 보고한다. 진행중/입력대기/실행완료는 기록만 남기며 응답장애/정체/조정/근거 부족은 이유를 붙여 알린다. 죽음은 감시sh의 실제 세션 부재와 과거 판정에만 남긴다. 직접 발령·재시작·완료 확정을 하지 않는다. 감독이 후속 조치를 결정한다.

## 예전 카단에서 가져온 기준

출처: 이전 카단 구현 용어집의 ‘외부 관찰과 관리 자원 용어’. ‘감시기’와 ‘화면 판정기’의 책임 분리를 계승하며, 아래 정의는 카단 라이트의 실제 코드에 맞췄다. 예전 문서 전체를 복제하지 않는다.

| 용어 | 카단 라이트에서의 뜻 |
| --- | --- |
| 원장 | 사건을 뒤에 추가하는 기록. 과거 줄을 다시 쓰지 않는다 |
| 조회 결과(snapshot) | 한 시점의 카드·역할·감시 근거를 읽은 결과. 설정 원본 자체는 아님 |
| 역할 작업 폴더(worktree) | 역할이 작업하는 Git 폴더. 카드 보관소나 세션 신분과 구분 |
| 비서 | 사용자에게 상태를 설명하고 승인된 요청을 사용자가 지정한 감독(지정이 없으면 슈퍼감독)에게 전달하는 역할 |
| 슈퍼감독 | 여러 감독의 우선순위·부하·충돌을 조율하는 상위 역할 |
| 일반감독 | 맡은 작업의 카드 발령·결과 검수·후속 처리를 책임지는 역할 |
| 카단 데이터 폴더 | KADAN_HOME. 기본 ~/.kadan. 예전 카단의 mailbox/work 보관소 경로와 다름 |

예전 ‘화면 판정기’의 결과는 진행/정체/모름이었다. 새 AI 보고 결과는 진행중/입력대기/실행완료/응답장애/정체/모름/조정이며, 일반 대화 답변의 낱말을 해석하지 않고 보고 명령 인자로 받는다. 모델 호출 실패 시 자동 GLM→DeepSeek 전환, 감시기 자기 침묵 탐지, write gateway·서명 관문·resource list는 이번에 가져오지 않는다. 특히 감시기 자체 생존 보강은 TODO 검토 항목이며 구현 완료가 아니다.

현재 용어는 **감시sh → 작업 감시AI**와 **감독 관찰AI**로 구분한다. 예전 감시기=감시sh, 작업자 화면 판정기·AI 판정기=작업 감시AI에 대응한다. `.sh` 파일이라는 구현 형식과 역할 이름 감시sh를 혼동하지 않는다. 상세 표는 [감시 문서](watch-overview.md), 그림은 [HTML 안내](watch-overview.html)를 본다.

| 카드 종류 | 뜻 |
| --- | --- |
| 실행 작업(execution) | 현재 담당자가 수행하는 구현·검수·설계·판단 단위. 첫 화면의 남은 일과 막대에 포함 |
| 관리·조율(coordination) | 감독의 배분·결과 취합·대기 기록. 실행 카드와 별도로 보존하며 실행 집계에서 제외 |

카드 종류는 담당자의 역할과 별개다. 감독이 맡은 독립적인 설계·판단도 실행 작업일 수 있다.

### 상태 이유 · 후속 담당 · 다음 행동

- 상태 이유: 해당 카드의 저장 상태나 진행 보고 단계가 된 이유. 전환 기록의 note 또는 명시적으로 보완한 statusReason.
- 후속 담당(resolutionOwner): 다음 조치를 맡아야 할 역할. 현재 실행 담당과 다를 수 있다.
- 다음 행동(nextAction): 재개·종료 등 다음 단계로 가기 위한 구체적인 조치·조건. 사용자 결정 여부는 별도 decision 기록을 따른다.

### SQLite 저장 전환

- 저장 backend: storage.json으로 선택한 JSONL 또는 SQLite 기록 방식. 동시에 두 원본에 쓰지 않는다.
- 스트림(stream): 같은 카드 또는 같은 기록 종류의 사건을 순서대로 묶는 저장 단위.
- events / heads: 과거 사건과 마지막 상태. 동일 트랜잭션에서 함께 확정한다.
- 저장 pause: 새로운 쓰기와 외부 실행을 거절하는 표식. 진행 중 명령이나 옛 프로세스가 종료되었다는 증거는 아니다.

### 비서 공식 우편

- 비서 수신처: tmux 세션 없이 공식 보고를 저장하는 우편 주소. 세션/정체 감시 대상이 아니다.
- stored: 우편 저장됨. 현재 대화창 깨움이나 업무 처리 완료가 아니다.
- 비서 확인함: inbox ack로 내용을 확인했다고 남긴 기록. 사용자 결정 승인이나 카드 완료와 별개다.

### 진행 조정 확인

화면이 변하는 실행 작업도 30분 관찰 후 감시ai가 이전·현재 화면과 목표를 비교하는 검사. 반복 실패·범위 확장은 직속 감독에게 조정을 요청한다. 카드 상태나 사용자 결정을 대신하지 않는다. 판정 불가는 별도 확인 필요이며 정상으로 취급하지 않는다.

### 티키타카 묶음

한 목적의 구현·수정·독립검수를 연결한 작업 단위(rally). 저장소·판·rallyId로 식별한다. 라운드는 구현과 독립검수 왕복 번호이며 조사·자체 시험 반복은 라운드에 세지 않는다. 미연결 카드는 번호를 추정하지 않는다.

### 대체됨

방향 변경으로 기존 카드를 종료하고 다른 카드로 이어가는 상태(superseded). 보류처럼 재개를 기다리지 않으며 완료 실적으로 세지 않는다. replacedBy에 후속 카드 주소를 남긴다.

### 감시AI 호출과 보고

- 호출ID: 감시sh가 만든 한 번의 판단 요청. 관찰 대상·실행 세대·기한과 연결된다.
- 감시AI 호출 상한: 실행기 시작·판단·보고를 합쳐5분. 그동안 감시sh 순회는 계속하며 두 AI를 합쳐 동시에1개만 실행한다. 대기 중 감독 관찰이 우선이며 다음 점검 간격은 실제 시작 시각부터 센다.
- 보고 완료 신호: 보고와 필요한 전달의 원장 접수가 끝났음을 실행기에 알리는 보조 파일. 원장 대조 후 해당 AI 호출만 종료하며 작업 완료나 승인을 뜻하지 않는다.
- `watch-report`: 감시ai가 판정과 이유를 기록하는 명령. 정상은 무알림, 문제는 기존 직속 상위로 한 번 보낸다. 이미 전송 여부가 불확실한 보고를 자동 재전송하지 않는다.
- 보고 누락: AI 실행이 끝났지만 보고 명령 실행 기록이 없는 상태. `모름`이라는 AI 판단과 별개인 감시 호출 장애다.
- AI 경보 해제: 정상 판정이나 책임 종료를 기록으로 남긴 것. 해제 우편을 보내거나 작업 완료로 확정하지 않는다.

### 감독 응답 점검 (2026-09-09)

- 감독 응답 점검: 감독 관찰AI가 활성 실행 또는 실제 발령 이력이 있는 열린 업무의 책임 일반감독을 1시간마다 확인한다. 연결·압축 오류가 5분 이어지면 먼저 판단한다. 최상위 슈퍼감독·비활성 업무는 제외한다.
- 실행완료: 해당 실행을 마치고 정상 입력 대기로 돌아온 AI 관찰 결과. 업무 최종 완료·원장 done·프로세스 종료와 다르다.
- 응답장애: 연결·문맥 압축 오류 등으로 응답 처리가 막힌 의심. 원인이나 복구 성공을 뜻하지 않는다.

### 실행 모델 설정 (2026-09-23)

- 실행 모델 설정(runner settings): 역할(작업자·검수자·일반감독·슈퍼감독)별 실행기·모델·강도의 기계용 기준. `$KADAN_HOME/runner-settings.json` 한 곳에 둔다. 상세는 [실행 모델 설정](runner-settings.md).
- 활성 프리셋(active preset): 역할 값 묶음 가운데 발령이 지금 읽는 하나. 대시보드 '실행 모델'이나 `kadan runners preset`으로 바꾸고, 원장에 `action: preset`으로 남는다.
- 설정 명령 대체(override): `start --profile`에서 설정과 다른 `--cmd`를 이유와 함께 쓴 발령. start 기록에 `launchSource: override`로 남는다.
