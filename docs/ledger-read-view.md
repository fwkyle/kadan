# 원장 조회 상태와 기록·우편 조회

## Why

지난 기록이 늘어도 기록·우편 한 쪽을 읽는 데 모든 사건을 메모리에 보관하지 않도록 한다.
원본은 `kadan.sqlite`의 `events`이며, 조회 상태는 언제든 원본에서 다시 만들 수 있다.

## 저장과 검증

조회 DB는 `KADAN_HOME/.cache/ledger-view-v1.sqlite`다. 사건 원본을 수정하거나 옮기지 않는다.
영역별 목록 위치·검색 색인·총수, 검증에 필요한 우편·실행·인계 연결과 적용 위치를 저장한다.
화면에 보여 줄 원문은 선택된 사건의 `(stream, seq)`로 원본에서 읽는다.
큰 감시 관계표를 제외하는 기존 조회 규칙도 유지한다.

- 조회 상태와 네 원장 스트림의 순번·끝 지문·누적 지문은 같은 조회 DB 트랜잭션으로 확정한다.
  원본 DB는 읽기만 한다. 두 DB의 쓰기가 동시에 확정된다고 가정하지 않는다.
- 새 사건은 최대 256행을 기준으로 나누되, 같은 순번의 지시/발령과 완료/바로 뒤 결과 우편은
  한 묶음에서 기존 검증기로 확인한다. 오류나 강제 종료는 상태와 적용 위치를 함께 되돌린다.
- 프로세스의 첫 조회는 원본의 적용 구간 전체 지문과 조회 행 수를 대조한다.
  정상 반복에서는 파일 식별값·끝 순번·끝 지문을 확인하고 새 사건만 처리한다.
  옛 원장 스트림 변경, 파일 교체, 끝 순번 감소, 지문·메타 불일치는 새 조회 세대로 재생한다.
- 최초 완료, 발령/우편 연결, 완료 우편, 인계 검증을 그대로 쓴다.
  재생 중 전송·AI 호출·프로세스 재시작은 일어나지 않는다.
- 원본의 암묵적 `rowid`는 적용 위치로 저장하지 않는다. 화면 커서는 조회 세대와 명시적 위치를 쓴다.
  최초 재생과 프로세스 시작 대조는 전체 이력에 비례한다. 재생 중의 객체는 묶음 단위로 해제한다.

SQLite가 읽을 수 없는 물리적 조회 DB 손상이나 다른 종류의 파일은 오류로 표시한다.
이 경우 조회 프로세스를 종료하고 해당 **조회 DB와 그 `-wal`·`-shm`만** 보존 폴더로 옮긴 뒤
다시 조회하면 원본에서 재생한다. `kadan.sqlite`나 원본 WAL을 이 절차로 옮기면 안 된다.
읽을 수 있는 메타·행 수 불일치는 자동으로 재생한다. 일반 반복 조회에서 과거 모든 행의 손상을
매번 다시 검사하는 것은 아니며, 전체 대조는 프로세스 시작·재생 시 수행한다.

## 화면과 API

`GET /api/dashboard/ledger`는 카드·업무·tmux·자원 수집을 거치지 않고 이 조회 상태를 쓴다.
종류·사고·카드 주소·역할·서울 날짜·반복 감시 필터와 기존 표시 내용을 유지한다.
DB에서 필요한 원문만 확보하고 읽기를 닫은 뒤 표시 문구를 만든다.

응답의 `nextCursor`·`previousCursor`를 `logCursor`로 보내면 다음·이전 50건을 읽는다.
화면은 이 커서를 사용하며, 첫 쪽으로 돌아오거나 검색 조건을 바꾸면 최신 범위에서 시작한다.
첫 조회 이후 새로 추가된 사건 때문에 다음 쪽의 기록이 중복되거나 빠지지 않도록 조회 끝을 고정한다.
조회 세대 또는 조건이 달라진 커서는 첫 쪽으로 돌아간다(`cursorReset: true`).
잘못된 커서는 400이며, 저장소를 읽지 못하면 빈 목록 대신 오류다.
인증·출처 제한과 조건부 응답(ETag/304), 강제 갱신을 적용한다.

옛 `logPage` 숫자 링크는 그대로 열린다. 이 호환 경로는 본문 대신 위치 정수만 앞에서 찾아간다.
새 이전/다음 이동은 이 순회와 깊은 `OFFSET`을 사용하지 않는다.
일반 첫 쪽의 총수는 저장된 집계를 사용한다. 특정 조건의 총수와 오래된 커서 뒤 추가분의 총수에는
SQL 집계가 남으므로 모든 검색을 항상 일정한 비용이라고 보장하지 않는다.

## 우편 현재 상태

`GET /api/dashboard/mail`·`mail-body`도 같은 조회 DB를 사용한다. 우편 상태와 적용 위치는
별도 표에 저장하되 원장 조회 상태와 같은 트랜잭션으로 확정한다. 기존 원본·최초 답장/취소,
수신/발신 인계, 참조가 모호한 답장, 완료 우편, 읽음 근거와 이전 세대 규칙을 유지한다.
사용자 이름 설정(`KADAN_USER_NAMES`)이나 조회 세대가 바뀌면 해당 우편 상태를 다시 만든다.
역할 세대는 마지막 경계·가장 늦은 경계 시각·개수로 저장한다. 오래된 미확인 우편을 자르지 않는다.

`nextCursor`·`previousCursor`를 `mailCursor`로 보내면 다음·이전 50통을 읽는다. 새 우편은
쪽 이동 중 기준 범위에 끼어들지 않는다. 기존 우편의 읽음·답장·인계·세대 상태가 달라지거나
조건이 바뀌면 첫 쪽으로 돌아가 최신 상태를 표시한다. 숫자 `mailPage` 링크도 지원한다.
역할·답장·미확인·카드·감시 우편 조건은 SQL로 적용하고, 카드 링크에는 본문 없는 기존 요약을 쓴다.
카드 요약은 현재 열린 카드의 판정 이력을 여전히 보관한다. 이를 전체 카드 상태 전환으로 보지 않는다.

내용 검색은 기존 대소문자 구분 없는 미리보기·본문 검색을 유지한다. 후보를 256통씩 확보하고
DB snapshot을 닫은 뒤 본문 파일을 읽는다. 선택한 쪽 외에 전체 우편 객체를 보관하지 않지만,
검색 총수에는 후보 전체와 본문 파일 순회가 남는다. 검색 도중 기존 우편 상태가 바뀌면 오류를 표시한다.
선택된 편지의 미리보기·단건 본문도 DB를 닫은 뒤 읽는다. 조회가 읽음 처리나 전송을 실행하지 않는다.

상단 요약의 답변 대기 개수와 감시기의 미확인 알림 후보도 이 상태표를 쓴다.
다른 화면의 우편 계산과 카드/업무 읽기를 모두 바꾸거나 전체 이력을 메모리에서 제거한 것은 아니다.
원본을 대신하는 업무 상태표로 취급하지 않는다.

## 감시의 답변 대기와 최근 우편

감시의 질문 대기·동료 책임·감독 관찰 문맥은 저장된 답변 대기 목록과 직전 정상 수집의 감시 역할별
최근12통을 사용한다. 미답변 우편은 오래됐다는 이유로 자르지 않는다.
최근 우편은 발신/수신 주소 색인에서 각각 최대12통을 읽고 저장 순서로 합친다.
동료 감독의 답변 책임을 계산할 때 역할 프로필은 그 호출 안에서 처음 필요할 때 한 번만
읽어 공유한다. 다음 호출은 입력을 다시 읽으며, 잘못된 입력의 오류를 빈 책임으로 바꾸지 않는다.
첫 수집·새 역할은 해당 수집의 기존 우편 해석을 쓴다. 읽기 실패는 준비 대상을 비우지 않는다.
과거 관계표가10배여도 정상 선조회는 현재 감시 역할 수에 비례하며, 첫 역할의 계산 비용은 남는다.

원문 우편과 카드 주소를 해석한 우편은 판정이 다를 수 있다. 감시는 기존처럼 짧은 주소를
정식 카드 주소로 해석하고, 별칭의 최초 완료만 인정하며, 연결 오류인 사건을 제외한다.
이를 위한 사건 위치·완료 중복 키·우편 상태를 별도 `watch` 영역에 함께 저장한다.
카드의 key/id 집합이 바뀌면 과거 주소의 뜻도 바뀔 수 있으므로 이 영역 전체를 다시 만든다.
제목·상태만 바뀌는 수정은 주소 재생을 일으키지 않는다.

원문과 해석 후 우편, 카드 주소는 같은 원본 읽기 시점에서 준비한다. 조회 DB의 적용 위치도
같은 트랜잭션에서 확정한 뒤 닫는다. 이미 내준 수집의 대기·최근 목록은 이후 쓰기로 바뀌지 않는다.
그 뒤 다른 카드 목록을 받은 경우와 미리 읽지 않은 역할의 최근 문맥은 기존 배열 계산을 쓴다.
카드 읽기 오류는 기존 카드 오류 경계에서 보고하며 우편을 빈 목록으로 대체하지 않는다.

정상 우편 계산은 새 사건·현재 대기·관계표 역할 수에 비례한다. 최초 재생·주소 집합 변경은
과거 전체에 비례하며 조회 DB 디스크도 이력에 따라 늘어난다. 감시가 다른 판정에 사용하는
전체 원장 배열과 카드 주소 해석 배열은 아직 남아 있다. 전송 직전의 새 읽기와 PID 확인은 유지한다.

감시의 통합 사건 배열은 같은 SQL 검증 상태의 새 위치를 256개씩 읽어 이어 붙인다.
별도 RAM 검증기와 원문·스트림·정렬 배열을 다시 보관하지 않는다. 원본이나 조회 세대가
바뀌면 재생하며, 적용 개수 불일치는 오류로 처리한다. 이전에 내준 배열은 바꾸지 않는다.
단일 전체 사건 배열과 주소 해석 배열의 메모리는 여전히 이력에 비례하고, 새 사건을 붙일 때
기존 배열의 참조를 복사하는 비용도 남는다. 현재 책임만 보관하는 최종 구조는 아니다.

## 감시의 현재 실행 책임

작업자·감독 범위는 같은 `watch` 조회 영역에서 실행별 마지막 발령/완료 위치와 확정 인계를
이어 적용한다. 인계로 양쪽 이력이 합쳐지면 원래 저장 위치가 늦은 사건을 남긴다.
완료된 실행도 열린 업무의 책임 근거가 될 수 있어 과거 발령 존재는 별도로 보관한다.
카드 담당은 카드의 현재 시각 이후에 적용할 인계만 색인에서 순서대로 따라간다.

수집에서는 현재 배정 카드와 열린 업무가 필요한 사실·세대 경계만 가져온다. 적용 위치와
사실은 조회 DB의 같은 트랜잭션에서 확정하며 이미 내준 수집은 바꾸지 않는다.
수집한 카드가 다르거나 준비하지 않은 업무/역할을 요청하면 그 수집의 기존 배열 계산을 쓴다.
별도로 주입된 원장 읽기 함수에도 기존 계산을 유지한다.

정상 적용은 새 사건과 해당 인계의 실행 수에 비례한다. 최초 재생·카드 주소 집합 변경은
과거 전체에 비례한다. 전체 원장·주소 해석 배열과 다른 경보/보고 소비자의 순회는 아직 남는다.

## 감시 화면의 세대·발령

화면 관측에 필요한 최신 시작, 실제 프로세스 세대, 세대에 남은 발령은 같은 `watch` 영역에서
새 사건만 적용한다. 같은 PID/역할/바닥의 start 재사용은 세대 시각을 유지하며 stop 뒤에도
인계할 발령은 보존한다. 명시한 restart는 그 발령을 잇고 다른 새 세대는 비운다.

이 발령표의 인계는 살아 있는 후임의 Map을 덮어쓰는 기존 규칙을 유지한다. 위 현재 실행
책임표의 원래 사건 위치 비교와는 다르다. 완료 발령도 확정 결과·기준 마커와 함께 남겨
다른 결과의 새 완료후보를 찾는다. 훅·화면·PID와 전송 직전 확인은 기존처럼 새로 읽는다.

상태·적용 위치는 같은 트랜잭션에서 확정한다. 카드 주소 집합이 달라지면 재생하며
이미 내준 수집을 바꾸지 않는다. 다른 카드 목록·별도 배열·잘못된 옛 인계 목록에는
기존 배열 계산을 유지한다. 현재 세대 발령과 알려진 세션 수만큼 상태를 보관하며,
전체 원장 배열과 다른 경보 소비자의 순회는 아직 남는다.

## 참고

WAL은 각각의 DB 안에서 트랜잭션을 보장하며 여러 DB에 걸친 동시 확정을 보장하지 않는다.
조회용 상태와 cursor를 한 DB에 두는 이유다. [SQLite WAL](https://www.sqlite.org/wal.html)

작은 문자·복합 기본키 색인에는 중복 저장을 줄일 수 있는 `WITHOUT ROWID`를 사용한다.
원본 스키마는 바꾸지 않는다. [SQLite WITHOUT ROWID](https://www.sqlite.org/withoutrowid.html)
