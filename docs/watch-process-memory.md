# 감시 프로세스의 중복 방지 기억

## Why

감시기를 오래 켜도 이미 보낸 알림·시도한 설명의 키가 계속 JS 힙을 차지하지 않도록,
중복 방지 의미를 유지하면서 큰 모음의 보관 위치만 바꾼다.

감시기에서 우편 알림의 예약·시도·보류·기록 압축, 설명 AI의 처리·시도,
재시작 때 한도 확인을 마친 경보의 키는 프로세스 전용 모음에 둔다.
합계 1,000개 또는 직렬화된 키/값 256KiB를 넘으면 Node 내장 SQLite의 임시 DB로 옮긴다.
옮긴 뒤 JS에는 키 전체를 유지하지 않으며 SQLite 페이지 캐시는 512KiB로 지정한다.
이 수치는 총 프로세스 RSS나 모든 SQLite 내부 메모리의 상한이 아니다.

오래된 키도 지우지 않는다. 실제 전송은 성공했는데 결과 기록에 실패한 경우에도
현재 프로세스가 같은 알림을 다시 보내지 않아야 한다. 시간 만료나 최근 항목만 남기는 방식은 쓰지 않는다.
삽입 순서와 문자열 구분을 보존하고, 저장 오류 뒤에는 빈 기억으로 진행하지 않는다.

임시 DB는 원본 원장·영구 조회 DB와 별개다. 연결이 닫히면 SQLite가 정리하며,
새 프로세스는 기존과 같이 원장으로 기억을 복원한다. 원장에 쓰지 못한 프로세스 내부 기억을
다음 프로세스까지 새로 보존하지 않는다. 원본 DB의 저장·동기화 설정은 바꾸지 않는다.

감시 주기 기록의 `collections`에는 기존 항목 수와 제한된 표본 크기에 더해
`storage`(`memory` 또는 `temporary`)와 JS에 남은 `retainedEntries`가 표시된다.
표본 크기는 직렬화 크기이며 V8 힙 측정값이 아니다.

10배 이력에서는 같은 키 조회 수의 JS 보관량을 제한한다. 처음 원장을 복원하는 시간과 임시 DB 공간은
키 수에 비례한다. 감시기가 다른 이유로 전체 원장·이력을 보관하거나 순회하는 비용은 별도 개선 대상이다.

참고: [SQLite 임시 DB](https://www.sqlite.org/inmemorydb.html#temporary_databases),
[SQLite 임시 파일](https://www.sqlite.org/tempfiles.html).
