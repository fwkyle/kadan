# Why

레포별 슈퍼감독이 동료에게 문제를 맡기고, 요청하지 않은 회신·재확인 의무를 강제하지 않도록 한다.

# 레포 간 슈퍼감독 우편

각 슈퍼는 담당 레포의 규칙·문서·진행 상황을 읽는 사용자 대화 상대다. 구현·검수 운영은
자기 일반감독에게 맥락 우편으로 맡긴다. 슈퍼가 전달용 카드를 먼저 쓰지 않으며,
일반감독이 설계·카드 작성·작업자 발령을 맡는다. 동료 슈퍼에게 맥락 우편을 넘기면
위임한 일은 수신 측이 책임지고 자기 일반감독과 처리한다. 회신을 요청하지 않았으면
발신자는 자동으로 회신을 요구하거나 기다리지 않는다. 위임이 발신자가 맡은 별개 프로젝트
전체를 자동 완료한다는 뜻은 아니다.

## 배치

같은 `KADAN_HOME`과 같은 실행 바닥에서 각 레포 슈퍼를 사용자 직속으로 등록한다.
담당 레포에서 `kadan start <레포>-슈퍼 --profile super --parent @user`로 시작한다.
이름이나 cwd로 관계를 추측하지 않는다. 기존 세션·관계표·서버는 자동 변경하지 않는다.
다른 홈·다른 기계 사이의 우편 중계는 지원하지 않는다.

## 기본 위임

관련 업무 주소, 문제·확인한 사실·재현 근거, 원하는 결과, 승인 범위와 금지선을
`mail <동료> '<맥락>'`으로 전한다. 받은 슈퍼는 자기 일반감독에게 같은 맥락을 넘기고,
수신 일반감독이 설계·카드 작성·작업자 발령을 맡는다. 슈퍼는 전달용 카드를 먼저 쓰지 않는다.
우편 저장·읽음은 착수·해결의 증거가 아니지만, 기본 위임에 회신·발신 측 재확인 의무는 없다.

## 회신을 명시 요청한 경우

회신이 필요한 요청에만 `--expect-reply`를 붙이며, 이 경우에만 최종 `--reply-final` 회신 의무가 생긴다.

1. 요청자는 관련 업무 주소, 재현 방법·근거, 필요한 결과, 승인 범위와 금지선을 편지에 적는다.
   `mail <동료> --expect-reply --work <원래업무> '<본문>'`의 반환 `mailId`를 보존한다.
2. 수신자는 `inbox read <mailId>`로 읽고 `inbox ack <mailId>`로 읽음만 기록한다.
   단순 문의는 답장한다. 실제 구현·검수가 필요하면 자기 일반감독에게 맡기고, 그 업무에
   `work mail <상대업무> --mail <mailId> --revision <최신버전> --note '<연결 이유>'`를 기록한다.
3. 최종 결과는 `mail <요청자> --reply-to <mailId> --reply-final '<결과·검증·남은 한계>'`로 답한다.
   중간 답장이나 읽음 확인은 답변 대기를 끝내지 않는다. 답장은 원래 업무 주소를 유지한다.
4. 요청자의 원래 업무에 결과 확인·재개가 필요하면 그 범위에서 처리한다.
   최종 답장은 요청자의 원래 업무를 자동 완료하거나 새 배포를 승인하지 않는다.

요청을 보낸 역할의 `KADAN_ROLE`이 정확해야 한다. 사용자가 취소하거나 범위를 바꾸면 기존
요청의 `inbox cancel <mailId>`와 업무 상태를 정리한다. 역할 책임과 세션을 옮기는 `handover`는
동료 간 문제 요청에 사용하지 않는다.

## 보관과 안전한 알림

관계표의 사용자 직속 역할(또는 관계표 밖의 명시된 super 프로필)끼리 보내는 일반 우편은
보내는 순간 일반 `mail`과 같은 입력 보호(최근 30초 사람 입력, 받는 쪽이 슈퍼감독이면 2분)를
거쳐 바로 넣는다(2026-10-13). 통과하면 바로 들어가며 일반 우편처럼 5분 뒤에도 읽음이 없을 때만
감시기가 재알림한다. 걸리거나, 시작 기록·세션이 없으면 넣지 않고 보관한다. 보관한 우편의
`stored`, `wake: watch-required`는 저장 영수증이다. 별도 사전 검사는 없고 바닥의 붙여넣기 직전 검사가
그대로 판정하므로 검사와 붙여넣기 사이 경합도 보관으로 돌아간다.
`--raw`로 보호를 우회할 수 없다. `mail --execution`은 배정된 카드를 연결해도 발령하지 않는다.
실행 발령은 `dispatch --task`를 쓴다.

감시기는 동료 우편의 추가 5분 유예를 생략하고, 같은 수신자의 우편을 묶어서 한 번 알린다.
입력 중이면 보류하고, 확실히 미전송된 입력 보호 오류만 다음 순회에 다시 검사한다.
서버 응답 유실·프로세스 교체·발송 예약 후 중단은 자동 재전송하지 않는다. 보관 우편의 알림이
같은 창에 3번 연속 밀리면 사용자에게 `알림밀림`이 가고 5번 연속이면 입력 보호 없이 넣는다([입력 보호 상한](watch-overview.md#입력-보호-상한-2026-10-13)). 감시기가 꺼졌거나
수신 세션이 없으면 저장만 되므로 inbox에서 확인해야 한다.

tmux는 최근 사람 입력(`client_activity` 기본 30초, `--profile super`로 시작한 슈퍼감독 창은 2분, 붙기만 한 창은 입력 아님)만 검사한다. 입력창 글 모양은 보지 않는다(2026-10-17).
herdr는 사람 입력 시각 API가 없으므로 대기 상태·동일 화면을 기본 30초(슈퍼감독 창은 2분) 이상 관측하고 전송 직전에 재검사한다.
작업 중·승인 대기·스크롤 중은 보류한다. 화면 검사와 전송 사이의 짧은 경합은 서버에서
원자적으로 잠그지 못한다([herdr 경계](experiments/herdr-roundtrip.md#자동-알림-보호-보완--2026-10-13)).

## 읽고 멈춘 요청 감시

미해결 `--expect-reply` 요청은 실행 발령 전에도 수신 슈퍼의 임시 책임으로 계산한다.
수신자가 읽음만 기록해도 감시 대상에서 빠지지 않는다. 기존 감독 유휴 단계와 응답 점검을
사용하며, 새 업무나 실행 카드를 자동 생성하지 않는다.

요청 우편을 연결한 수신 업무의 하위 작업이 진행 중이면 정상 대기로 본다. 그 업무에
등록한 답변 대기도 존중한다. 수신 업무가 끝나도 최종 회신이 없으면 요청 책임은 남는다.
원래 업무 종료·보류, 연결 업무 보류, 최종 답변·요청 취소는 감시 제외 사유다.
