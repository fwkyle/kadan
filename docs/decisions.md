# 사용자 결정 요청

## Why

사용자는 슈퍼감독이 검토 후 명시적으로 올린 결정만 답하고, 내부 질문·실패 보고는 감독이 처리한다.

- `decision request <카드키> [--work <업무주소>|없음] --question ... --option ... --option ... --recommend ... --reason ...`: 슈퍼감독 명의만 요청. 질문/2~4개 선택지/추천/판단 필요 이유를 필수로 받는다. 요청은 고유 ID로 별도 기록한다. `--work`는 결정이 막는 열린 업무를 적는다(선택, 2026-10-07). 카드가 그 업무의 실행이면 없어도 연결되고, 아니면 이것이 있어야 감시·업무 후속 표시가 그 업무를 사용자 결정 대기로 본다. **카드가 업무의 실행이 아니고 같은 판에 열린 업무가 있으면 `--work`를 빠뜨린 요청은 저장하지 않고 후보 업무를 알려 주며 거부한다**(2026-10-08 [kyle] — 지침만으로는 누락이 반복됐다). 막는 업무가 없으면 `--work 없음`.
- `decision request --chat --work <업무주소> --question ... [--option ... --recommend ... --reason ...]`: kyle에게 **이미 채팅으로 물은 질문**을 가볍게 등록한다 → [채팅 질문 등록](#채팅-질문-등록---chat-2026-10-23).
- `decision list [--status open]`, `decision show <ID>`, `decision answer <ID> --revision N --text ...` 또는 `--choice ...`, `decision cancel <ID> --revision N --reason ...`.
- answer는 사람 명의만 허용하며, CLI와 웹이 같은 함수로 저장한다. 답변 후 요청자에게 CLI 편지를 한 번 시도한다. 저장 성공과 통지 성공은 별도이며 불확실한 통지를 자동 재시도하지 않는다. 같은 답변 재전송은 저장/편지 중복 없이 기존 결과를 반환한다.
- 기존 question/answer 카드 이력은 내부 기록으로 보존하고 사용자 결정으로 자동 승격하지 않는다. 카드 상태/승인 범위를 답변만으로 자동 바꾸지 않는다. 슈퍼감독이 답변과 기존 승인 범위를 읽어 필요한 후속을 수행한다.
- 데이터는 KADAN_HOME/decisions/events.jsonl에 추가만 한다. 손상은 모름/쓰기 거부, 동시에 바뀐 버전은 충돌로 거부한다. 역할명은 기존 KADAN_ROLE 선언이며 인증 계정 체계가 아니다.
- 새 화면에 사용자 결정함·우편·실행·원장을 함께 제공한다. 우편 by=발신자/role=수신자, 원장 기록은 실행/배포 성공 증거와 구분한다. 일반 상단 메뉴에서 legacy로 이동하지 않는다. ?legacy=1은 명시적인 과거 표시 참고 화면으로만 유지한다.

## 질문 쓰는 법과 화면 표시 (2026-09-23)

[kyle]이 한눈에 읽고 바로 눌러 확인하도록 질문을 짧게 나눈다.

- 첫 줄은 물음표로 끝나는 질문 한 문장이다. 화면은 첫 줄의 첫 물음표까지를 제목으로, 나머지를 줄바꿈 그대로 본문으로 보인다.
- 확인할 링크·근거·한계·영향은 다음 줄부터 `- 노션: <주소>`처럼 한 줄에 하나씩 쓴다. 본문과 이유의 `http(s)` 주소는 새 창 링크로 표시된다.
- 셸에서는 `--question "$(printf '질문?\n- PR: <주소>')"`처럼 실제 줄바꿈을 넣는다.
- **확인 경로 필수 (2026-09-24 [kyle] 결정):** 모든 결정 요청 본문에는 [kyle]이 답하기 전에 직접 열어 볼 수 있는 링크나 절대경로를 하나 이상 넣는다. 결정 대상마다 해당하는 것을 모두 적는다. PR·이슈 주소, 화면으로 확인할 것은 Preview·Staging 실제 접속 주소, 노션 페이지, 근거 결과 파일의 절대경로 등이다. "Preview-1에 올라가 있음"처럼 이름만 쓰지 않는다. 접속 주소는 배포 기록이나 배포된 메타 파일에서 확인한 값만 적고 추측해서 쓰지 않는다. 주소를 확인하지 못했으면 요청을 올리기 전에 먼저 확인한다. 주소가 바뀌면 요청을 취소하고, 사유를 적어 새 주소로 다시 올린다. 열어 볼 대상이 정말 없는 순수 방침 질문만 예외로 둔다. 이때는 본문에 `- 확인 경로 없음: <이유>` 줄을 적는다.
- **변경 전후 필수 (2026-09-27 [kyle] 결정):** 동작·화면·권한·데이터가 바뀌는 결정(합류·배포·방향 선택)은 본문에 `- As-is: <지금>`과 `- To-be: <바뀐 뒤>` 두 줄을 넣는다. 새 기능처럼 보여도 기존 동작을 좁히거나 없애는 변경이면 반드시 그렇게 적는다(예: As-is 요청중 문서는 직원 누구나 취소 버튼이 보인다 / To-be Master·업로드 권한 직원만 보이고 나머지는 숨김·서버 거부). 확인 경로도 To-be의 차이가 보이는 곳을 가리킨다. 바뀌는 동작이 없는 순수 방침 질문은 생략한다. 근거: #185·#321 결정 문구를 새 버튼처럼 써서 "원래 취소 버튼 있지 않았나?"를 다시 물어야 했다.
- **명령 차단 (2026-09-24):** `kadan decision request`는 질문과 이유를 합친 글에 `http(s)` 주소, 절대경로(`/home/.../result.md`처럼 `/`로 시작해 경로 구분이 있는 것), `확인 경로 없음: <이유>` 줄 중 하나도 없으면 확인 경로 없는 요청으로 보고 저장하지 않고 거부한다. 검사는 새 요청에만 하며, 이미 저장된 요청의 조회·답변·취소는 막지 않는다.

## 화면 구성과 진행 막대

왼쪽 GNB 틀과 판별 가로 막대는 유지한다. 대시보드/카드/내 결정 필요/판 현황/세션/우편함/실행/원장은 모두 새 화면 내부에서 이동한다. 카드 본문·내부 기록 디자인은 유지한다. 판 막대는 중앙 카드 고유키를 한 번만 세어 완료/진행보고/결과대기/발령전/보류/확인필요/실패/취소보관으로 분리한다. 미등록 실행을 카드 수에 섞지 않는다. 오래된 참여 역할은 펼쳐 보며 담당자가 많아 막대가 밀리지 않게 한다.

답변은 해당 요청 ID만 해결한다. 다른 질문이나 기존 내부 question은 함께 닫히지 않는다. 사용자 답변을 대신 만들어 과거 질문을 자동 변환하지 않는다. 답변 후에는 그 결정의 처리 기록과 알림 결과를 보여준다.

## 사용자 알림 (2026-10-14)

`decision request`가 저장된 뒤 사용자에게 알린다. 디스코드가 설정돼 있으면 디스코드(사용자 멘션), 아니면 맥 시스템 알림이다. 첫 줄은 `[레포] 결정 요청: 질문 요약`, 아래에 선택지·추천·이유·`결정 <ID 8자>`·카드·업무, 맨 끝에 맥 링크(`http://127.0.0.1:8790/#decision-<전체 ID>`)다. 업무가 있으면 그 업무 글, 없으면 레포 `결정` 글로 간다. `answer`·`cancel`은 새 메시지 대신 **원래 요청 메시지를 고쳐** 맨 위에 `✅ 해결됨 — 취소: <사유>`/`답변: <선택>`을 쓴다(멘션 없음). 원래 메시지를 못 찾을 때만 질문 앞부분·사유가 든 새 메시지를 보낸다. 알림 실패는 결정 저장과 요청자 통지를 막지 않는다. 설정·재시도·중복 규칙은 [사용자 알림](user-notify.md)을 따른다.

디코에서 **새 글**로 올라가는 것은 결정 요청(이 문서)과 kyle 조치가 필요한 장애뿐이다. 답변·취소는 새 글이 아니라 요청 글을 `✅ 해결됨`으로 고쳐 쓴다. 전체 표는 [사용자 알림](user-notify.md#새-글-정책과-전수-표-2026-10-18).

## 폰에서 답하기 (2026-10-18)

원격 설정(`remote-access.json`)에 `host`가 있으면 알림 링크가 `https://<host>/#decision-<id>`가 된다(`decisionLink`, 설정 파일만 읽는다. 없으면 로컬 주소 그대로). 원격에서 그 링크를 열면 결정 화면의 답하기가 열린다. 답변은 같은 `DecisionStore.answer`를 거치므로 사람 명의(`by`)와 revision 확인이 같다. 원격 답변에만 선택 필드 `answer.remote`(Access 이메일·sub·iat·exp·IP)가 붙고 `answer.source`는 그대로다. 규칙·위협 모델은 [대시보드 원격 보기](dashboard-remote.md#폰에서-결정-답하기-2단계).

## 채팅 질문 등록 (`--chat`, 2026-10-23)

Why: 슈퍼감독이 kyle에게 채팅으로 물어 놓고 결정을 등록하지 않으면 감시기가 그 업무를 '놀고 있음'으로 깨운다. 카드 키·확인 경로·선택지 2~4개를 요구하는 일반 요청은 채팅 질문 하나에는 무거워 등록이 건너뛰어졌다(7일 실측에서 놀고 있음 12묶음 중 슈퍼감독이 8묶음).

- 등록: `kadan decision request --chat --work <업무주소> --question "<질문>"`. 카드키는 쓰지 않는다. 저장 모양은 `chat:true`, `card:null`, `work` 필수다(옛 행은 그대로 읽힌다. `chat`이 아닌 `card:null` 행은 손상으로 거절한다).
- 자동으로 채우는 것: `--option`을 안 주면 선택지 `추천대로 진행`·`보류`(추천은 첫째), `--reason`을 안 주면 고정 문구, 확인 경로가 없으면 `- 확인 경로 없음: 채팅 질문` 줄. 직접 준 선택지는 일반 규칙을 따른다. 같은 업무·요청자·질문은 같은 결정으로 본다.
- 알림은 없다: 등록·답·닫힘 모두 디코·OS 알림을 보내지 않고 결정 저장소에만 남긴다(kyle은 이미 채팅으로 받았다).
- 감시: 열린 채팅 결정이 있는 업무는 일반 결정과 같이 '놀고 있음'에서 빠진다(`src/watch-runner.mjs`의 답 대기 목록이 `chat:true`이고 `work`가 있는 행을 받는다). 닫히면 다시 대상이다.
- 자동 닫힘: 같은 업무의 `work execute`(`후속 발령으로 자동 닫힘`), `work update --turn-owner`(`차례 변경으로 자동 닫힘`, 차례 값이 실제로 달라진 경우에만. 비움 포함), `work complete`(`업무 완료로 자동 닫힘`)가 **성공한 뒤** 별도 저장으로 열린 채팅 결정만 취소한다. 닫은 쪽은 `cancelledBy: 자동`, 닫은 명령은 `cancelledVia`에 남는다. 닫기가 실패해도 업무 명령은 성공하고 stderr에 한 줄만 낸다. 일반 카드 결정과 다른 업무의 결정은 건드리지 않는다.
- **만료는 없다.** 시간이 지났다고 승인이나 닫힘으로 처리하지 않는다. 안 닫힌 채팅 질문은 대시보드 '내 결정'에 `채팅` 꼬리표와 경과 시간으로 남는다.
- kyle이 채팅으로 답했을 때: 요청자가 등록 출력의 `chatCloseCommand`(`kadan decision cancel <ID> --revision N --reason "kyle 채팅 답: <원문>"`)로 닫는다. 사람이 대시보드·디코로 `answer`하면 알림은 요청자에게 직접 간다. 나이트 모드를 끄는 것은 사람 명의의 **답**뿐이다.
- 나이트 요약: 채팅 결정은 `채팅 등록 N건`으로 따로 세고 자동 닫힘·요청자 닫힘은 취소로 세지 않는다.

## 밤 위임 (나이트 모드, 2026-10-23)

`kadan night on`은 kyle이 자러 가며 한 말을 원장에 `night` 사건 하나로 남기고, 열린 업무를 가진 슈퍼감독들에게 같은 우편을 보낸다. **새 권한이 아니다.** 승인·머지·결정 답은 지금처럼 슈퍼감독이 문구를 읽고 기존 승인 범위 안에서 한다. 결정 답은 여전히 사람 명의만 기록한다.

- 켠 사람: 사람 명의는 바로, 슈퍼감독은 kyle 채팅 원문(`--quote`)이 있어야 하고 `viaChat: true`로 남는다(자기신고라는 한계는 결정 답과 같다). 일반감독 이하는 켜지 못한다.
- 끝: `off`, 끝 시각(기본 8시간, 상한 12시간), kyle의 새 입력(켜진 뒤 생긴 사람 명의 결정 답) 중 먼저 온 것. 끝 시각 만료는 감시기 한 주기가 `expired`를 한 번만 기록한다.
- 요약(끝날 때 한 번): 결정 답·취소, 머지 관련 결정(PR 주소가 든 결정) 답·취소 — **실제 머지는 GitHub에서 확인**, 재시작, 우편, 보류로 남긴 것(`kadan mail 사람 "[나이트 보류] <한 줄>"`). 첫 줄에 대리 위임 원문을 보인다.
- 디코 한 마디(2026-11-04 PR E): #비서 본문의 `잘게`·`잘게 자동`·`잘게 N시간`·`잘게 HH:MM까지`·`일어남`만 다리 코드(AI 없음)가 사람 명의로 `night on/off`를 부른다. `--quote`·`--allow`는 쓰지 않고, 늦은 글(10분)·중복 글 id는 켜지 않으며, 바이패스는 거절한다. 레포 포럼 스레드·답장 글은 처리하지 않는다. 문구·답 글은 [디코 나이트런 한 마디](discord-chat.md#나이트런-한-마디-잘게일어남).
- 단계(2026-11-02): `--level`이 없으면 지금과 같다(따로 이름 붙이지 않는다). `--level 자동`은 사건에 `level`·`onlyRunning`을 남기고 `status`에 보이며, 지침에 (4)~(9)를 더한다: 묻기 전에 스스로 찾기, 되돌릴 수 있고 근거 있으면 추천안으로 진행하고 `[나이트 결정]` 한 줄, 금지 목록, 카단 명령 거절 안내, 머지는 아침 보류. `--only-running`은 새 일감을 시작하지 않는 줄을 더한다. `--level 바이패스`는 아직 구현하지 않아 거절한다. **이번 범위에서 자동 단계도 머지는 아침 보류**다(자동 머지 관문은 뒤 PR).

- 나이트런 당번 경로(`src/night-duty.mjs`, 2026-11-09 PR F): 자동 단계에서 당번 슈퍼감독을 켤 때 정하면(`--duty <이름>`, 없으면 `kadan night duty`로 낮에 저장한 기본 당번, `--duty 없음`이면 없음. 자동 고르기 없음) 사용자로 갈 `놀고 있음` 2단·`정체` 경보만 당번에게 간다. 수신자 한 칸을 전송 직전 한 곳에서 바꾸고 새 우편 경로는 없다. 당번이 할 일은 멈춘 슈퍼감독을 우편으로 깨우는 데까지이며 15분 뒤에도 그대로면 `[나이트 보류]`를 남긴다(지침 문구). 감시기의 역할 재시작은 하지 않는다: **잠긴 규칙 3·8은 그대로다**(감시기는 AI 역할을 자동 재시작하지 않고, 최상위 슈퍼감독은 정기 점검 대상이 아니다). RED 정체의 사용자 겹알림은 그대로 둔다. 기본 1밤 실측은 선행 조건이 아니다(kyle: "기본은 걍 내가 일반으로 돌리면서 pr머지 승인 알아서해와 차이가 없음, 자동부터가 진짜 나이트런").
- 켜진 동안 코드 거절(`src/night-guard.mjs`): 역할 세션(`KADAN_ROLE` 있음)의 `restart --force`, 기반 프로세스 `stop 비서|대시보드|디코|watch`(작업자·검수자 세션 `stop`은 통과), `window`·`runners`의 **읽기 전용 하위 명령 밖 전부**(허용 목록: `window` 하위 명령 없음·`show`, `runners` 하위 명령 없음·`show`·`report`·`compare show`·`--out` 없는 `export`), `night on --level 바이패스`, `night repo <저장소> …`(저장소 정책 쓰기, `repo`·`list`·`show`만 통과). 거절 검사는 `--help`를 붙여도 먼저 하고, `window`·`stop`·`restart`의 `--help`는 사용법만 보이고 아무것도 실행하지 않는다. 사람이 직접 치거나 꺼져 있으면 그대로다. 사람 명의 결정 답은 역할 세션에서 이미 거절된다. **한계**: `KADAN_ROLE`은 스스로 밝히는 값이라 `env -u KADAN_ROLE kadan …`로 우회된다. 셸·`gh`로 직접 하는 행위는 카단이 막지 못한다. 이 거절은 실수 방지이지 보안 경계가 아니며, 금지 목록 문구와 아침 사후 드러냄(뒤 PR)으로 보완한다.
- 켜진 동안에도 결정 요청 알림의 kyle 멘션은 그대로다. 소음은 문구 고정 줄(위임 범위 안의 일은 결정 요청을 올리지 말고 처리)로 줄인다.
- 역할 AI 명령은 `TMUX`·`TMUX_PANE` 없이 실행하고 "카단 pane 안" 표시는 `KADAN_PANE_SOCKET`으로 바꾼다(`wrapNoTmux`, 2026-11-04, 슈퍼감독 a91f3398 1번): 역할 아래 자식이 소켓 없이 부른 tmux가 `$TMUX`로 카단 서버에 붙어 `kill-server`로 전원이 꺼졌다. 옛 TMUX 판정은 전환 기간만 함께 받는다. 감싸기는 항상 `unset TMUX TMUX_PANE; <원문>` 하나로 하고, 명령이 없으면 `unset TMUX TMUX_PANE; exec "${SHELL:-/bin/sh}" -l`로 로그인 셸을 실행한다. 앞머리 낱말·exec·env·내장 명령을 다시 해석하지 않아 원래 셸의 뜻을 보존한다. pane 현재 명령이 셸로 보일 수 있지만 PID일치·실행기 칸은 원장 기준이라 영향이 없다(2026-11-04 PR #348 재검수 확인).


## 서버 전체 손실의 감독 복원 (2026-11-09)

Why: 사람이 자리를 비운 동안 tmux 서버 전체가 사라져도 직전 감독이 같은 대화로 돌아와 일을 이어가게 한다.
승인 원문: “서버가 통째로 내려가면 자동 복원 -> 승인. 이런 사고났을 때 대비해서”.

- `up --auto`는 revive 잠금 안에서 `list-sessions -F '#{session_name}'`를 한 번 호출한다(5초 상한).
  결과와 무관하게 기존 기반 4개 되살리기를 먼저 실행한다. 서버 없음 응답(없어진 소켓 포함)만 손실이다.
  권한 오류·시간 초과 등은 stderr 한 줄만 남기고 감독 복원·스냅숏 저장을 건너뛴다.
  서버가 있으면 감독 하나가 없어도 복원하지 않는다. 감시기의 개별 역할 자동 재시작은 여전히 없다.
- 서버가 있는 매 주기에 `$KADAN_HOME/server-sessions.json`의 `{observedAt, sessions}`를 새로 쓴다.
  관찰 시각은 기반 실행 전 조회 시각이며, 카단 세션 이름만 보존한다. 권한 0600·임시 파일+rename을 쓴다.
  복원 후보는 이 목록에 있는 슈퍼·일반감독이다. start의 `roleProfile`이 우선이고,
  없을 때만 관계표의 자식 유무·사용자 직속 관계를 본다. 이름으로 역할 종류를 추측하지 않는다.
  시작 기록이 없는 세션은 건너뜀 목록에 올린다. 작업자·검수자·비서, 관찰 이후 stop,
  revive-state의 수동 정지 역할은 제외한다. 죽음 경보는 생존 근거로 쓰지 않는다.
- 부팅 시각이 마지막 스냅숏의 `observedAt`보다 늦으면 재부팅이다. 로그인이 늦어도 자동 복원하지 않고
  후보별 수동 명령을 알린다. macOS는 `sysctl kern.boottime`, 다른 운영체제는 현재 시각에서 시스템 가동 시간을 뺀다.
  부팅 시각 불명·관찰 기록 없음·10분 초과·손상이면 복원하지 않고 수동 확인을 알린다.
  머지 직후 첫 주기에 서버가 없고 스냅숏도 없으면 알림만 한다. 서버가 있으면 첫 스냅숏을 저장한다.
- 복원 준비·실행의 예외는 기반 결과에 영향을 주지 않는다. `revive(reason=server-restore-error)`에 사유를 남기고
  같은 오류 키는 한 시간에 한 번만 알린다. OS 알림에도 적용하도록 `server-restore-errors.json`에 예약한다.
  세션 스냅숏 쓰기 실패도 이 경로로 알린다. 정상 주기에는 `server-restore-state.json`을 읽지 않는다.
  실패·재부팅·낡은 관찰로 시작하지 못해도 직전 감독 세션 이름을 알림과 사건에 보존한다.
  원장 실패로 역할 종류를 모르면 관찰된 세션 이름과 종류 확인 불가를 적고, 관찰 자체가 없으면 목록 불명을 명시한다.
- Claude는 명시 `--resume <ID>`가 우선이다. 없으면 해당 cwd의 프로젝트 대화 폴더에서 최근 7일 이내이면서
  마지막 start 이후 수정된 파일의 정확한 `수신 역할: <역할>;` 표시를 찾는다.
  일치 0개·2개 이상은 건너뛴다. 대화 파일은 청크로 읽으며 결과에는 경로·mtime만 남긴다.
  Codex는 기존 명령이 명시 `codex resume <ID>`일 때만 복원하고 대화 파일을 찾지 않는다.
- 첫 위치 프롬프트는 제거한다. 값 개수가 확인된 옵션만 보존하며, 알 수 없는 옵션·가변 인자·fork·continue·
  셸 결합·존재하지 않는 cwd는 건너뛴다. 지원하지 않는 명령은 사람이 대화 ID와 폴더를 확인한다.
- 실제 시작은 기존 `start --cmd ... --reason server-restore --no-prompt` 경로다.
  기계 창 설정을 명시하고 launchd의 `KADAN_WINDOW_FORCE`는 제거한다.
  로티 연결 사전 확인이 실패하면 숨김으로 시작하고 결과에 `kadan attach <역할>`을 적는다.
  설정 파일 자체가 손상된 경우에는 창 종류를 추정하지 않는다. 시작 실패는 자동 재시도하지 않는다.
- 복원 시도는 60분에 한 번까지다. 시작 전에 `server-restore-state.json`에 예약하여 중간 종료에도 상한을 보존한다.
  같은 스냅숏으로 확인한 손실을 다시 처리·통지하지 않는다. 서버 재생성을 관찰한 뒤 다음 손실을 받는다.
  `$KADAN_HOME/server-restore.off`가 있으면 감독 복원을 끈다. 기반 4개 되살리기는 계속된다.
  이 파일을 `.trash/`로 옮기면 다시 켜진다. 사람이 친 `up`도 감독 복원 상한을 초기화하지 않는다.
- 손실 결과는 `revive` 사건 하나(`reason: server-loss`, `restoreId`, 후보별 결과, `by: autostart`)다.
  새 start에는 `reason: server-restore`, 같은 `serverRestoreId`, 원본 시작 지문 `serverRestoreOf`가 붙는다.
  원장은 뒤에만 추가한다. 자식 CLI 종료 0뿐 아니라 새 start 연결 기록도 확인한다.
  시작할 감독이 있으면 먼저 “서버 통째 종료 감지 — 감독 N명 복원 시작” 한 통을 보내고, 끝나면 결과 한 통을 보낸다.
  기반의 울림 알림(상태 손상·막힘·상한)은 즉시 따로 보낸다. 조용한 기반 알림은 결과 요약에 함께 싣고,
  기반 revive 사건의 `notice`는 실제 요약 전달 결과, `noticeSummary`는 요약의 `restoreId`를 가리킨다.
  후보 없음·복원 끄기·같은 스냅숏 등으로 요약이 없거나 요약 호출이 실패하면 기반 알림을 원래대로 보낸다.
  복원한 역할마다 직전 명령의 실제 완료 여부를 확인하라는 일반 우편을 한 번 보낸다.
  우편 전달 실패는 복원 성공과 별개로 기록하며 재전송하지 않는다.
- **운영 반영:** main 합류 후 로컬 코드를 갱신하면 다음 1분 주기의 `up --auto`부터 적용된다. 재시작이 필요 없다.
  정상 주기의 추가 비용은 서버 조회 한 번과 최신 세션 스냅숏 한 개 쓰기다. 원장 이력이 10배여도 정상 주기는 같고,
  손실 때의 원장·대화 검색량만 증가한다. 각 역할 시작 전에는 변경된 시작·관찰 이후 종료 기록도 재확인한다.
