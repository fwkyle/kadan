# 사용자 알림 (디스코드 → 맥 시스템 알림)

## Why

사용자가 맥 앞에 없으면 결정 요청과 감시 경보를 놓친다. 그래서 사용자(`@user`)에게 가는 알림을 디스코드 채널로 보내고, 디스코드가 안 될 때만 지금처럼 맥 시스템 알림(`osascript`)을 띄운다. 1단계는 보내기만 한다. 브리핑·대화형(디스코드에서 답하기)은 범위 밖이다.

## 어디서 나가나

사용자에게 가는 알림은 모두 `src/user-notify.mjs`의 `notifyUser` 한 곳을 지난다.

| 알림 | 부르는 곳 | 중복 막기 키 | 멘션 |
|---|---|---|---|
| 감시 경보의 `@user` 전달 | `watch-runner.mjs` | `alert:<경보 id>:<단계>` (10분 창) | 없음 |
| RED·죽음 경보의 사용자 겹알림 | `watch-runner.mjs` | `alert:<경보 id>:<단계>:겹알림` (10분 창) | 없음 |
| `watch`의 `@user` 메시지 | `commands/watch.mjs` | 없음 | 없음 |
| 인계 사용자 통지 | `commands/handover.mjs` | 없음 | 없음 |
| 사용자 우편함에 온 편지 | `commands/send.mjs` | `mail:<우편 id>` | 없음 |
| **결정 요청** | `decisions.mjs` `request` | `decision:<id>:request` | **있음** |
| 결정 답변됨 | `decisions.mjs` `answer` | `decision:<id>:answer` | 없음 |
| 결정 취소됨 | `decisions.mjs` `cancel` | `decision:<id>:cancel` | 없음 |

결정 알림은 결정이 저장된 **뒤에** 보낸다. 알림이 실패해도 결정 저장·기존 역할 통지(`kadan send`)는 그대로다. 답변 알림은 요청한 역할에게 가는 기존 통지를 대신하지 않고 **디스코드에 한 번 더** 보내는 "닫힘" 표시다. 취소도 같은 방식으로 짧게 알린다(작업자 결정).

## 설정

```
kadan notify show
kadan notify set discord --env-file <비밀 파일 절대경로>
kadan notify unset
```

- `$KADAN_HOME/notify-setting.json`에 **비밀 파일의 경로만** 저장한다. 웹훅 주소·사용자 ID는 설정에 복사하지 않는다. `show`도 값은 보여 주지 않고 "있음/없음"만 말한다.
- 읽는 순서: 환경변수 `KADAN_NOTIFY_ENV_FILE` > 기계 설정 > 없음(= 시스템 알림만).
- 비밀 파일은 **보낼 때마다** 읽고 `KEY=VALUE` 줄만 해석한다(따옴표 한 겹·`export`·`#` 주석). 셸로 실행하거나 `source`하지 않는다. 필요한 값은 `DISCORD_WEBHOOK_URL`(https, 시험용 로컬 주소만 http 허용), `DISCORD_USER_ID`(숫자).
- 파일 없음·값 빠짐·형식 오류는 "설정 오류"로 시스템 알림으로 내려가고, 사유(주소·ID 없이)가 `notify-log.jsonl`에 남는다.
- `KADAN_NOTIFY=off`는 디스코드를 보내지 않고, 결정 알림은 시스템 알림도 띄우지 않는다. 시험은 이 값을 켠 채 돈다(`tests/helpers/isolated-home.mjs`).
- 참고: `kadan notify set discord --env-file <경로>`의 `--env-file`은 카단 플래그이고 Node 옵션이 아니다. Node가 가로채는 것은 `node --env-file <파일> src/cli.mjs …`처럼 옵션을 스크립트 **앞**에 둘 때뿐이다(독립 검수가 실행 파일·`node src/cli.mjs` 두 방식 모두 확인). 설정에는 경로만 저장되고 파일의 변수는 환경에 올라가지 않는다. 비밀 파일이 심볼릭 링크여도 그대로 읽는다.

### 레포별 포럼 채널

비밀 파일은 하나다(`kadan notify set discord --env-file <경로>` 한 번). 레포별 경로 설정(`--repo`)은 없다.

| 키 | 뜻 |
|---|---|
| `DISCORD_WEBHOOK_URL` | 기본 #브리핑 텍스트 채널 |
| `DISCORD_USER_ID` | 결정 요청 멘션 대상 |
| `DISCORD_WEBHOOK_URL_<레포>` | 레포 포럼 채널. 레포 이름을 대문자로 바꾸고 영숫자가 아닌 글자는 `_`로 (`kadan` → `_KADAN`, `my-app` → `_MY_APP`) |
| `DISCORD_WEBHOOK_URL_SECRETARY` | #비서. 1단계에서는 쓰지 않는다 |

어디로 가나: 알림에 **업무 키**가 있고 그 업무 저장소의 레포 키가 있으면 레포 포럼의 업무 글로 간다. 업무 키는 결정의 `work`, 우편의 `--work`(없으면 `--execution`이 속한 업무)에서 얻는다. 감시 경보는 경보의 실행 키가 한 업무에 속하면 그 업무 글로 간다(아래 "경보를 업무 글로"). 역할 단위 경보(실행 키 없음)와 업무를 못 찾은 경보, 인계·`watch` 메시지는 업무를 알 수 없어 기본 #브리핑으로 간다. 레포 키가 없는 레포, 업무 키가 없는 알림도 기본이다.

포럼 웹훅은 `thread_name`(새 글)이나 `thread_id`(기존 글)가 없으면 거절한다. 처음에는 `thread_name`(업무 키 + 업무 제목, 100자 안)과 `?wait=true`로 새 글을 만들고, 응답의 `channel_id`(= 글 id)를 `$KADAN_HOME/notify-threads.json`에 남긴다(값 모양은 아래)(주소·토큰·사용자 ID는 저장하지 않는다). 다음 알림부터 같은 업무는 `thread_id`로 이어 붙인다. 기록한 글이 지워져 `thread_id` 전송이 429가 아닌 4xx로 거절되면 새 글을 한 번 만들고 기록을 바꾼다(같은 요청 재시도가 아니라 다른 요청이라 허용). 상태 읽기 → (새 글 만들기) → 상태 갱신은 **한 잠금 안에서** 한다. 기존 글이 4xx여서 새 글을 만들 때도 잠금 안이고, 들어가서 상태를 읽어 이미 다른 호출이 만든 글이 있으면 그 글을 쓴다. 상태 저장은 임시 파일 → rename(0600)이며 그 순간 최신 파일을 다시 읽어 자기 업무 줄만 바꾼다(다른 업무 기록 보존). **잠금을 종료 시각 안에 못 얻으면 잠금 없이 읽거나 보내거나 쓰지 않는다.** 업무 글로 가야 할 내용을 기본 #브리핑에 섞지 않으려고 시스템 알림으로 내려간다(잘못된 채널로 새지 않는 쪽). 레포 키 형식이 틀리면 기본 웹훅으로 내려가지 않고 시스템 알림으로 간다. 요청이 나가는 곳은 `postDiscordWebhook` 한 함수이고(메시지 수정 PATCH도 여기, 아래 "업무 글의 상태 메시지"), 상태 파일의 값 모양은 아래에서 설명한다.

### 업무 글의 상태 메시지 (2단계)

업무 글마다 **상태 메시지 하나**를 두고, 바뀔 때마다 새로 올리지 않고 **그 메시지를 고쳐 쓴다**(웹훅 메시지 수정, `PATCH /webhooks/<id>/<토큰>/messages/<메시지 id>?thread_id=<글>`). 휴대폰에서 업무 글 하나만 열면 지금 어디까지 왔는지 보인다.

- 내용(`src/work-status-message.mjs`): `WorkStore`·카드·원장에서만 만든다(AI 호출 없음). "열린 실행"은 업무 완료 확인과 같은 기준(`endedExecution`)이라 원장 결과가 실패인 실행은 열린 실행이 아니라 "실패로 끝난 실행: N건"으로 보인다. 저장된 시작·대기 보고만 있는 실행은 `시작함(보고 기준)`·`결과 대기(보고 기준)`로 적는다(실시간 생존은 조회하지 않는다). 고정 틀, 2,000자 안, `allowed_mentions: {parse:[]}`. 요약 한 줄 자리는 코드에만 있고 지금은 비어 있다.

```
**업무 상태** · kadan/work-x
제목: 알림 만들기
상태: 열림 · revision 5
열린 실행 2건:
- 구현 1라운드 · kadan-작업자 · 작업중
- 검수 1라운드 · kadan-검수자 · 작업대기
현재 차례: kadan-작업자
다음 행동: 구현 결과를 검수에 넘긴다
책임 감독: kadan-감독
갱신: 2026-10-14 06:55 UTC
```

- 상태 파일: `notify-threads.json`은 `업무 키 → {threadId, statusMessageId}`다. 1단계의 옛 형식(`업무 키 → 글 id` 문자열)도 읽고, 다음 저장 때 같은 잠금 안에서 새 형식으로 바꿔 쓴다. 주소·토큰·사용자 ID는 저장하지 않는다.
- 맞추는 함수는 `refreshWorkStatus(home, work)` 하나다. 새 주기 작업은 없고 이미 있는 사건 지점에서만 부른다.

| 사건 | 부르는 곳 |
|---|---|
| 그 업무로 알림이 나갔을 때(글이 새로 생겼거나, 상태 메시지가 아직 없을 때 포함) | `user-notify.mjs` `sendForum`이 같은 잠금 안에서 |
| `kadan work update/execute/complete/cancel/reopen` | `work-command.mjs` |
| 그 업무에 연결된 실행의 `kadan done` | `commands/done.mjs` |

- 글이 아직 없는 업무(알림이 한 번도 안 나간 업무)는 `work update` 등이 있어도 아무것도 하지 않는다. 글은 알림이 만든다.
- 수정이 404(메시지 지워짐)이면 같은 글에 새 상태 메시지를 한 번 올리고 id를 바꾼다. 글까지 404이면 상태 메시지를 첫 글로 새 글을 만든다. 404가 아닌 4xx(400·403 등)·5xx·시간 초과는 더 시도하지 않고 **버린다**(상태는 다음 사건 때 다시 계산되므로 시스템 알림으로 대신하지 않는다).
- 공통 12초 예산과 장애 직후 60초 건너뛰기를 알림과 같이 쓴다. 건너뛰는 동안은 수정 요청도 나가지 않는다. 결과는 `notify-log.jsonl`에 `kind:"status"`로 남는다(중복 키 없음: 경보·우편의 중복 막기와 섞이지 않는다).
- 요청 0건인 경우: `KADAN_NOTIFY=off`, 디코 설정 없음, 그 레포의 포럼 웹훅 키 없음, 업무 글 없음.

### 경보를 업무 글로 (2단계)

감시기가 사용자에게 경보를 보낼 때(`@user` 전달과 RED·죽음 겹알림), 경보의 실행 키(`taskId`)를 `WorkStore`의 실행 목록에서 찾아 **업무가 하나로 정해지면** `work`로 넘긴다(`watch-runner.mjs` `workKeyOfAlert`). 그 업무의 레포 포럼 키가 있으면 업무 글로 가고, 업무를 못 찾거나 여러 업무에 걸치거나 역할 단위 경보(감독 멈춤·관계표 읽기 실패 등)면 지금처럼 #브리핑이다. 경보 원장 기록과 `status?super=` 응답은 바뀌지 않는다.

### 포럼 태그 조사 (구현은 3단계)

공식 문서(`discord-api-docs` 저장소의 `developers/resources/webhook.mdx`·`channel.mdx`, 2026-10-14 확인)로 확인한 사실이다.

| 질문 | 답 | 근거 |
|---|---|---|
| 웹훅으로 글을 만들 때 태그를 붙일 수 있나 | **된다.** 메시지 실행(Execute Webhook) 본문의 `thread_name`과 함께 `applied_tags`(태그 id 배열)를 줄 수 있다. 웹훅 채널이 포럼·미디어 채널일 때만이다 | webhook.mdx "Execute Webhook" JSON 매개변수 표 |
| 만든 뒤 웹훅으로 태그를 바꿀 수 있나 | **안 된다.** 웹훅 메시지 수정(Edit Webhook Message)은 메시지만 고친다. 글(스레드)의 `applied_tags` 변경은 채널 수정(`PATCH /channels/{글 id}`, 최대 5개)이고 웹훅 주소로는 부를 수 없다 | webhook.mdx "Edit Webhook Message", channel.mdx "Modify Channel (Thread)" |
| 필요한 권한 | 채널 수정 호출에는 봇 토큰이 필요하다. 스레드 수정 문서는 `MANAGE_THREADS`를 요구하고(보관·잠금 조건), 태그에 `moderated`가 켜져 있으면 `MANAGE_THREADS` 멤버만 붙이고 뗄 수 있다고 적혀 있다. 그 밖에 글쓴이 자격만으로 `applied_tags`를 바꿀 수 있는지는 문서에 명시가 없어 **미확인**이다 | channel.mdx "Modify Channel", "Forum Tag Object" (`moderated`) |
| 태그 id를 웹훅으로 알 수 있나 | **알 수 없다.** 태그 목록(`available_tags`)은 채널 객체에 있고, 채널 조회(`GET /channels/{포럼 id}`)는 일반 API라 봇 토큰이 필요하다. 토큰 없는 웹훅 조회(Get Webhook with Token)는 웹훅 객체만 주고 태그를 주지 않는다. 대안은 사람이 개발자 모드에서 태그 id를 복사해 설정에 적는 것이다 | channel.mdx "Channel Object"(`available_tags`), webhook.mdx "Get Webhook with Token" |

결론: 글을 **처음 만들 때** 정적 태그(예: 레포 구분)는 웹훅만으로 붙일 수 있다. 상태에 따라 태그를 **바꾸는 것**(열림→완료)은 봇 토큰이 들어오는 3단계에서 한다. `~/.kyle-secrets/discord/bot.env`는 읽지 않았다.

## 보내는 방식과 시간 상한

호출하는 쪽이 모두 동기라서 동기 API를 유지한다. 전송은 자식 프로세스(`src/discord-send.mjs`)를 `spawnSync`로 띄운다.

**한 알림 전체에 공통 종료 시각**이 하나 있다(알림 시작 + 12초). 잠금 대기, 각 요청의 재시도, 새 글 만들기, 상태 기록이 모두 이 남은 시간을 나눠 쓰고, 남은 시간이 1.5초 아래면 더 기다리거나 보내지 않는다(예전의 "최소 1초 다시 주기"는 없앴다). 자식 강제 종료는 남은 시간 + 2초라서 디스코드 쪽 최악은 약 14초이고, 시스템 알림(`osascript`)은 따로 3초 제한이다.

| 값 | 근거 |
|---|---|
| 한 알림 전체 12초 | 감시 주기를 막는 최대 시간을 15초 이하로 둔다는 기준. 강제 종료 여유 2초를 더해 약 14초 |
| 연결 시간 4초, 응답 대기 5초 (남은 시간이 더 짧으면 그만큼) | 디스코드 웹훅은 보통 1초 안에 응답. 둘을 따로 둬야 "보내지 않았음이 확실한 실패"와 "보냈을 수 있는 실패"를 가른다 |
| 시스템 알림 3초 | 멈춘 `osascript`가 감시 주기를 잡지 않게 |

**장애 직후 건너뛰기:** 디스코드 전송이 연결 실패·시간 초과(불확실)·429/5xx 소진으로 끝나면, 같은 프로세스는 **60초 동안** 다음 알림에서 디스코드를 시도하지 않고 바로 시스템 알림으로 보낸다(`outcome: skipped`가 `notify-log.jsonl`에 사유와 함께 남는다). 근거: 장애 때 알림 한 건이 최대 12초를 막아 경보 두 건인 감시 주기가 24초 걸렸다. 60초면 장애 중에는 1분에 한 번만 기다리고, 되살아나면 1분 안에 돌아온다. 4xx(설정·요청 문제)와 설정 오류는 장애가 아니라서 막지 않는다. 프로세스 안의 상태라 `decision request` 같은 단발 CLI에는 효과가 없다.

재시도는 같은 요청이 두 번 올라가지 않는다고 확신할 때만 한다.

| 상황 | 동작 |
|---|---|
| 연결 단계 실패(연결 거부·DNS·연결 시간 초과) | 최대 2회 재시도(0.4초, 0.8초 뒤) |
| 429 | `retry_after`를 지켜 1회. 대기가 남은 예산을 넘으면 포기 |
| 5xx | 1회(1초 뒤) |
| 400·401·404 등 4xx | 재시도 없음 |
| 연결된 뒤 응답 대기 시간 초과·끊김 | 재시도 없음, **불확실**로 기록 |

실패·불확실이면 시스템 알림으로 내려간다. 불확실한 키는 이미 올라갔을 수 있으므로 같은 키로 다시 보내지 않는다.

## 중복 막기

키·길(`discord`)·결과(`sent`/`uncertain`/`failed`/`config-error`)·사유 코드만 `$KADAN_HOME/notify-log.jsonl`에 한 줄씩 덧붙인다(권한 0600). 주소·ID·본문은 적지 않는다. `decision request`처럼 한 번 도는 CLI도 이 파일로 프로세스를 넘어 중복을 막는다. 경보 키는 같은 id가 해소됐다가 다시 뜰 수 있어서 10분 창 안에서만 중복으로 본다. 결정·우편 id는 한 번뿐이라 창이 없다.

한계: 확인과 기록 사이에 틈이 있어, 같은 키를 **동시에** 두 프로세스가 부르면 둘 다 보낼 수 있다. 결정·우편은 한 번만 부르고, 경보는 감시기 한 프로세스(`assertSingleWatch`)가 보내므로 현재 경로에서는 일어나지 않는다.

## 멘션 통제

결정 요청 본문만 `<@사용자ID>`로 시작하고 `allowed_mentions: {users:[ID]}`를 보낸다. 나머지는 모두 `allowed_mentions: {parse:[]}`라서 본문에 `@everyone`·`<@…>`가 섞여도 아무도 호출되지 않는다. 본문은 2,000자를 넘으면 앞을 줄이고 맨 끝 줄(맥 링크 `http://127.0.0.1:8790/#decision-<ID>`)은 남긴다. 포트는 대시보드 기본값 8790이며, 대시보드 포트를 저장하는 설정은 아직 없다.

## 공개 레포 주의

시험·예시에는 가짜 값만 쓴다. 오류 문구는 주소·ID를 가린 뒤(`scrubSecrets`) 기록하고, 자식 프로세스는 오류 원문 대신 오류 코드·HTTP 상태만 돌려준다. push 전에 `rg -n 'discord(app)?\.com/api/webhooks'`와 실제 사용자 ID가 변경분에 0건인지 확인하고 `npm run check:public`을 돌린다.
